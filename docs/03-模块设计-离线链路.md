## 0. 全局数据结构

以下结构贯穿所有模块，定义在 `agentic_rag/schema.py`。

```python
@dataclass
class Block:
    """解析器输出的统一中间表示单元（防腐层的核心）。"""
    type: str # heading | paragraph | table | list | image_caption | code
    text: str # 该块内容（表格为 Markdown 表格串）
    level: int = 0 # 标题层级；非标题块为 0
    path: list[str] = field(default_factory=list) # 到本块的标题路径
    page: int | None = None
    is_atomic: bool = False # True 表示切分时不可再分（表格）
    meta: dict = field(default_factory=dict)

@dataclass
class ParsedDocument:
    doc_id: str # sha1(文件内容)[:16]
    source: str # 文件名
    source_path: str
    blocks: list[Block]
    parser: str # 实际使用的解析器名
    page_count: int
    quality: "QualityReport"

@dataclass
class Chunk:
    chunk_id: str # 见下方 ID 规则
    doc_id: str
    parent_id: str | None # 子块指向其父块；父块与 structural 块为 None
    is_parent: bool = False # True = 仅供回填的父块，不进向量与 BM25 索引
    text: str # 入库文本 = 块头 + 原文（用于 embedding / BM25）
    raw_text: str # 不含块头的原文（用于 UI 展示）
    title_path: list[str]
    block_type: str
    is_atomic: bool
    page: int | None
    source: str
    tokens: int
```

**设计要点**：`text` 与 `raw_text` 分离。检索与生成用 `text`（含上下文），展示给用户的是 `raw_text`——否则用户会看到我们注入的标题路径，觉得答案里混进了奇怪的前缀。

### 0.1 chunk_id 与父子关系规则

**ID 格式**（加一个类型段，父子不共用 seq 空间）：

| 块类型 | 格式 | 进向量索引 | 进 BM25 | 落盘位置 |
| --- | --- | --- | --- | --- |
| 检索单元（子块 / structural 块） | `{doc_id}:c{seq:04d}` | ✅ | ✅ | 向量库 payload + `chunks.jsonl` |
| 父块（parent_child 策略） | `{doc_id}:p{seq:03d}` | ❌ | ❌ | `data/index/parents.jsonl` |

`seq` 在各自类型段内从 0 自增，与文档内块顺序一致。

**`chunk` 的返回契约**：`ParentChildChunker.chunk` 返回**父块与子块平铺在同一个 `list[Chunk]` 里**（每个 `ChunkPair` 展开为 `[parent, *children]`）。调用方按 `is_parent` 分流，不靠解析 ID 字符串——ID 类型段只是为了不撞号，不是路由依据。

**三种块的字段取值**：

| | `is_parent` | `parent_id` |
| --- | --- | --- |
| 子块 | `False` | 指向所属父块的 `chunk_id` |
| 父块 | `True` | `None` |
| `structural` 策略产出的块 | `False` | `None`（**没有父块可回填，rerank 回填时用它自身，见 04§6.5**） |

### 环境变量映射

README 的快速开始写了 `cp .env.example .env`，但配置树从未定义环境变量如何映射到 `Config`。补齐如下。

**顺带修正两处结构缺陷**：原文档称"全部 11 个配置类"，实际列出的只有 **10 个**；且只定义了子配置类，**从未定义顶层容器 `Config`**——接口里的 `get_config -> Config` 返回类型无处可依。补上：

```python
@dataclass
class Config:
    profile: str = "dev" # dev | eval
    dashscope: DashScopeConfig = field(default_factory=DashScopeConfig)
    quality: QualityConfig = field(default_factory=QualityConfig)
    ingestion: IngestionConfig = field(default_factory=IngestionConfig)
    index: IndexConfig = field(default_factory=IndexConfig)
    retrieval: RetrievalConfig = field(default_factory=RetrievalConfig)
    agent: AgentConfig = field(default_factory=AgentConfig)
    generation: GenerationConfig = field(default_factory=GenerationConfig)
    cache: CacheConfig = field(default_factory=CacheConfig)
    server: ServerConfig = field(default_factory=ServerConfig)
    observability: ObservabilityConfig = field(default_factory=ObservabilityConfig)
```

| 环境变量 | 映射到 | 默认值 |
| --- | --- | --- |
| `DASHSCOPE_API_KEY` | `cfg.dashscope.api_key` | 空 → 自动启用 Mock 全家桶 |
| `DASHSCOPE_BASE_URL` | `cfg.dashscope.base_url` | 兼容端点 |
| `DASHSCOPE_NATIVE_BASE_URL` | `cfg.dashscope.native_base_url` | 原生端点（rerank 走） |
| `AR_PROFILE` | 配置档：`dev` / `eval` | `dev` |

**约束：只有上表四项从环境读取，其余参数一律走配置树默认值或 CLI 显式参数。**

这不是偷懒，是可复现性要求。`retrieval_signature` 与 `EvalReport` 记录的是**配置树的序列化结果**；如果任何参数都能从环境变量悄悄注入，报告里就必须额外落一份环境变量快照，否则同一份报告无法复现。而环境变量恰恰是最容易"跑了三次、其中一次 shell 里多 export 了一个变量"的配置来源。

推论：**凭据这类不能硬编码的东西进 env，一切影响算法行为的参数进配置树。** 这条界限必须守死。

`AR_PROFILE=eval` 时额外启用两条硬校验（见下方启动校验项）：锁模型版本、缓存强制关闭。消融实验绝不能在缓存未清的状态下跑。

### 关键实现

**索引版本号 `index_version`** 是全局开关。

```python
def _chunk_factors(cfg: Config) -> str:
    """一切决定 chunk 内容与 chunk_id 的切分参数。
    漏掉任何一个，改了它却没重建索引都会静默降质。"""
    ing = cfg.ingestion
    return ":".join([
        ing.chunk_strategy,
        str(ing.parent_chunk_tokens),
        str(ing.child_chunk_tokens),
        str(ing.child_overlap_tokens),
        str(ing.atomic_max_tokens),
        str(ing.table_split_threshold_tokens),
    ])

def compute_index_version(cfg: Config) -> str:
    ds = cfg.dashscope
    key = f"{ds.embedding_model}:{ds.embedding_dim}:{_chunk_factors(cfg)}"
    return "v" + hashlib.sha1(key.encode).hexdigest[:8]
```

加载索引时若版本不匹配，直接抛错并要求重建。**这条规则是硬性的**：换 embedding 不重建索引会让所有向量相似度失效，且表现为"系统还能跑但效果变差"——最危险的一类故障。

**检索配置指纹 `retrieval_signature`**：把一切影响检索结果的配置序列化后取哈希。它有两个用途——缓存键的一部分，以及评测报告里的"实验配置存证"。**没有它，UI 上切换消融开关后缓存会返回上一个配置的答案**，而"现场切开关看指标变化"正是本 demo 的卖点。

切分参数进入指纹是同一个道理：切法变了而缓存键没变，返回的就是上一种切法算出的答案。

**完整因子清单**：

```python
def retrieval_signature(cfg: Config) -> str:
    r = cfg.retrieval
    ing = cfg.ingestion
    factors = [
        # 召回开关与融合
        r.use_vector, r.use_bm25, r.use_rerank,
        r.fusion_strategy, r.rrf_k, r.weighted_weights,
        r.vector_top_k, r.bm25_top_k, r.fusion_top_k,
        # 充分性判据
        r.min_candidates, r.sufficiency_vector_floor,
        # 加权与过滤
        r.table_boost, r.filter_tables_only,
        # 模型与切分
        cfg.dashscope.embedding_model, cfg.dashscope.embedding_dim,
        ing.chunk_strategy, ing.parent_chunk_tokens, ing.child_chunk_tokens,
        ing.child_overlap_tokens, ing.atomic_max_tokens, ing.table_split_threshold_tokens,
        # BM25 打分参数与用户词典指纹
        cfg.index.bm25_k1, cfg.index.bm25_b,
        user_dict_sha256(cfg.index.user_dict_path),
    ]
    return hashlib.sha1("|".join(map(str, factors)).encode).hexdigest[:12]

def user_dict_sha256(path: str) -> str:
    """词典不存在时返回 'none'，不抛异常——允许无词典运行，但指纹必须与有词典时不同。"""
    if not os.path.exists(path):
        return "none"
    return hashlib.sha256(open(path, "rb").read).hexdigest[:16]
```

`bm25_k1` / `bm25_b` 改变的是打分与排序，**它不进指纹的话，调完参数后缓存会把上一组参数排出来的顺序继续返回**——这正是"缓存键漏配置指纹"那次修掉的故障，只是换了一个字段。

`user_dict_sha256` 更隐蔽：词典是**文件**而不是配置树里的字段，改一个词（比如给"单卡上限"加一条自定义词）会改变 jieba 分词结果，进而改变整个 BM25 召回集，但配置树的序列化结果一个字都不会变——**纯字段级指纹在结构上就不可能发现它**，所以指纹里必须显式带一个文件摘要（05 §2 的字段完整性对账也覆盖不到这类变化）。

**生成侧指纹 `generation_signature`**：

```python
def generation_signature(cfg: Config) -> str:
    g = cfg.generation
    ds = cfg.dashscope
    factors = [
        ds.llm_main, ds.llm_light, g.temperature, g.max_tokens,
        g.lang, g.max_citations, g.max_context_chunks,
        # 这两项决定是否重生成，从而改变最终答案
        g.faithfulness_threshold, g.regenerate_on_unsupported,
        *[p.schema_version for p in all_prompts], # 05§0.2
    ]
    return hashlib.sha1("|".join(map(str, factors)).encode).hexdigest[:12]
```

`faithfulness_threshold` 与 `regenerate_on_unsupported` 的作用与充分性判据的 `min_candidates` / `sufficiency_vector_floor` 完全同型：**它们决定是否触发一次额外动作，从而决定用户最终看到的是哪一版答案**。缺了它们，"调低阈值让更多答案被判为不忠实"这个改动会在缓存面前完全失效。

### 启动校验项

| 校验 | 失败后果 |
| --- | --- |
| `child < parent ≤ atomic_max_tokens` | 抛 `ValueError` |
| `table_split_threshold ≤ atomic_max_tokens` | 抛 `ValueError` |
| `child_overlap ∈ (0, child_chunk_tokens)` | 抛 `ValueError` |
| `rerank_top_k ≤ fusion_top_k ≤ vector_top_k + bm25_top_k` | 抛 `ValueError` |
| `fusion_top_k ≥ max(vector_top_k, bm25_top_k)` | 抛 `ValueError` |
| `trace_keep_top_k ≥ fusion_top_k` | 抛 `ValueError`，**埋点窄于召回宽度会导致指标事后算不出**（见 §3） |
| `embedding_dim ∈ [64, 2048]` | 抛 `ValueError` |
| 质量阈值单调：`warn < reject` 且均 ∈ (0,1) | 抛 `ValueError` |
| `raw_char_min_for_check > 0` 且 `ocr_min_chars > 0` | 抛 `ValueError` |
| `unanswerable_rerank_floor ∈ (0, 1)` | 抛 `ValueError`，**等于 0 会让 06§6.4 的机器校验恒真** |
| `sufficiency_vector_floor ∈ (-1, 1)` | 抛 `ValueError`。**等于 -1 会让达标计数恒等于候选数、判据退化为恒真**；等于 1 则恒为 0 条达标、每次都跑满 3 轮 |
| `max_context_chunks ≤ rerank_top_k` | 抛 `ValueError` |
| `max_retrieve_iterations ≥ 1` 且 `max_generate_iterations ≥ 1` | 抛 `ValueError`；**两者语义均为"该动作最多执行几次"** |
| `max_retrieve_iterations ≤ 3` | 抛 `ValueError`。策略升级共三级（意图策略 → `rewrite` → `hyde`），超过 3 轮后升级序列已耗尽，再往上只会用同一个 hyde 反复重检，收益为负 |
| `max_sub_queries ≥ 1` 且 `≤ 8` | 抛 `ValueError`。超过 8 条子查询的延迟与"多跳"的定义都不成立 |
| `history_max_turns ≥ 0` | 抛 `ValueError`。`0` 表示不引入历史（等价单轮） |
| `generation.lang` 在 `{"zh", "en"}` 内 | 抛 `ValueError` |
| `max_citations ≥ 1` 且 `≤ max_context_chunks` | 抛 `ValueError`。引用数不可能多于送进生成的上下文块数 |
| `use_vector` 与 `use_bm25` 不得同时为 `False` | 抛 `ValueError`。两路都关则 `candidates` 恒空，链路必然降级，属于误配置而非实验变量 |
| `chunk_strategy` / `fusion_strategy` / `backend` 取值在白名单内 | 抛 `ValueError` |
| `backend=qdrant_server` 时 `url` 必填 | 抛 `ValueError`；**漏了会静默退回 local 模式，指向一个不存在的目录** |
| `max_concurrent_queries ≥ 1` | 抛 `ValueError` |
| `AR_PROFILE=eval` 时 `llm_main` / `llm_light` 不得为别名（`qwen-plus` / `qwen-flash`） | 抛 `ValueError`，要求锁版本号 |
| `AR_PROFILE=eval` 时 `cache.enabled` 必须为 `False` | 抛 `ValueError` |

后两条 `eval` 档校验来自 **实测**（见 `08-实测基线.md` §1.1）：别名（`qwen-plus`）与具体版本（`qwen3.7-plus`）实测同时在架，但别名会在官方升级时**静默漂移**到底层新模型。若 A2 组与 A3 组跑在两个不同的底层模型上，消融差异就分不清是配置带来的还是模型升级带来的——而这正是本项目最需要避免的"结论不可引用"。至于缓存，B6 组已经吃过一次亏（缓存键漏配置指纹），`eval` 档干脆强制关掉，代价只是慢一点。

**DashScopeEmbedding 实现要点**

- **必须显式传 `dimensions` 参数**：`text-embedding-v4` 支持 64–2048 维，不传则取默认 1024，与向量库定义一旦不一致就会在写入时报错

**MockEmbedding 实现要点**

不用随机向量——随机向量会让检索结果每次都不同，导致评测不可复现。改用**字符 3-gram 哈希投影**：

```python
def _pseudo_embed(text: str, dim: int) -> list[float]:
    vec = np.zeros(dim)
    for i in range(len(text) - 2):
        h = int(hashlib.md5(text[i:i+3].encode).hexdigest[:8], 16)
        vec[h % dim] += 1.0
    return l2_normalize(vec)
```

这样语义相近（字面重叠多）的文本确实会有更高相似度，Mock 模式下整个检索链路的行为是可信的，不是纯噪声。

## 3. 模块 `observability/trace.py`

### 职责

采集单次查询的全链路中间产物，落盘 JSONL，驱动 UI 决策可视化与评测数据源。

### 接口

```python
@dataclass
class TraceEvent:
    step: str # route | rewrite | retrieve | fuse | rerank | reflect | generate | verify
    ts: float
    duration_ms: float
    payload: dict # 各步骤结构化中间产物
    tokens_in: int = 0
    tokens_out: int = 0

class Tracer:
    def __init__(self, query_id: str, enabled: bool = True)
    def event(self, step: str, payload: dict, **kw) -> None
    @contextmanager
    def span(self, step: str) -> Iterator[None] # 自动计时
    def finalize(self, answer: str) -> dict
    def write(self) -> None # 追加写入 JSONL
```

### 记录内容（按步骤）

| step | payload 字段 |
| --- | --- |
| route | intent, confidence, reason, 是否跳过改写 |
| rewrite | original, sub_queries, strategy（改写/分解/HyDE） |
| retrieve | queries, intent, `vector_hits` / `bm25_hits`（**命中条数**，不是明细）, routes, filter_pushdown, durations, errors, sub_query_count, `fused`（chunk_id，保留 `trace_keep_top_k` 条）与对应 scores, retrieve_rounds, merged_from_prev |
| fuse | strategy, rrf_k, top-`trace_keep_top_k` 的 chunk_id 与 rrf 分数, merged_from_prev |
| rerank | 重排前后 rank 变化对, top-`trace_keep_top_k` 的分数, `dedup_collapsed` |
| reflect | `iteration`, `sufficient`, `reason`, `strong`, `min_candidates`, `sufficiency_basis`, `retrieve_rounds`, `merged_from_prev`, 动作 |
| generate | 输出长度, 首字延迟 |
| verify | 命题总数, 无支撑命题数, faithfulness |

> **已知的埋点边界**：`vector_hits` / `bm25_hits` 只记命中**条数**，不记 `[(chunk_id, score)]` 明细，
> 所以"单路 recall@K"无法事后从 trace 复原，要算只能重跑检索（本地计算，不花 API）；
> 融合后的 top-k 明细是完整的，对外指标都基于它。这是有意的取舍：单路明细会让 trace 体积
> 随子查询数与保留宽度相乘增长，而这些明细只在做分路归因时才用得上。

### 关键实现

- 落盘路径 `data/traces/{date}.jsonl`，追加写入，进程崩溃不丢已采集部分
- `span` 用 contextmanager 自动计时，避免每个节点手写 `time.perf_counter`
- trace 同时是评测数据源：延迟分布、token 成本、迭代次数直接从这里聚合

**埋点宽度 `trace_keep_top_k`（默认 50，等于 `fusion_top_k`）是一条锁死日后能力的配置。**

早期版本此处写的是"各路 top-3 预览""fuse top-10""rerank top-5"，够看、不够算：评测常报的 recall@20 / MRR@20 在这份数据上**永远算不出来**，而 trace 是**事后无法补采**的——想补报这个指标，只能全量重跑并重新花钱调 API。因此规则是：

> **埋点保留宽度必须 ≥ 评测打算上报的最大 K。** 写 trace 代码的那一刻，就决定了日后能回答哪些问题。

体积代价很小：每查询约 50 条 × (chunk_id + float) ≈ 1.5KB。相比"重跑一次消融"的成本，这个代价值得付。

## 4. 模块 `ingestion/quality.py`

> 本模块是架构文档之后补充的，用于回答"怎么保证文档识别无误"。

### 职责

三道关卡的质量校验，产出单文档质量报告与处置判定。

### 接口

```python

    parser: str
    page_count: int
    is_scanned: bool
    char_count: int # 解析结果字符数
    raw_char_count: int # raw 基线字符数（0 表示无基线）
    digit_count_raw: int # 原始抽取数字字符数
```

所有阈值从 `QualityConfig` 读取，**模块内不得出现数字字面量**。

### 关卡 1 · 解析前探测

```python
@dataclass
class ProbeResult:
    ok: bool
    encrypted: bool
    corrupted: bool
    is_scanned: bool
    chars_per_page: float
    table_density: float # 探测到的表格区域占比
    suggested_parser: str
```

**扫描件判定**（最关键）：逐页抽取文本，`chars_per_page < 50` 判定为扫描件，路由到 OCR 通道。

**表格密度估计**：统计 PDF 页面中表格线条对象占比，超过 `docling_table_density_threshold` 时建议 Docling。
（`pypdf` 后端对线条对象的统计能力弱于 `pymupdf`，此时 `table_density` 可能恒为 0 → `docling` 分支不可达。
这是切换后端的**已知代价**，写在 03§5 的降级链里：表格密集 PDF 在 `pypdf` 后端下退化为走 `PdfParser`。）

### 关卡 2 · 解析中结构校验

- **表格行列一致**：把 Markdown 表格解析回行列，检查每行单元格数是否等于表头列数
- **标题层级连续**：相邻标题层级差 > 1 计一次跳变，跳变过多说明漏解析了中间层级
- **图文关联**：`image_caption` 块必须紧邻其所属标题路径，孤立 caption 视为解析异常

### 关卡 3 · 解析后守恒检查

**3.0 先解决 `raw` 从哪来**

守恒检查的全部前提是存在一个"最粗暴但完整"的基线文本 `raw`。原文档没有定义它的取法，导致关卡 3 对非 PDF 格式根本跑不起来。`raw_baseline` 按格式分别取：

| 格式 | `raw` 取法 |
| --- | --- |
| PDF | 按 `PDF_BACKEND` 后端逐页抽取的**纯文本流** |
| DOCX | `python-docx` 遍历所有 `paragraph.text` + 所有表格单元格文本 |
| XLSX | `openpyxl` 遍历所有 sheet 的 `cell.value` |
| PPTX | `python-pptx` 遍历所有 shape 的 `text_frame.text` |
| HTML | 去标签后的 `inner_text` |
| MD / TXT | 原文件原文（此时 `raw` 与解析结果同源，守恒检查自动降级为"不适用"） |

**`raw` 为空或过短时，守恒检查必须自我声明不适用**，而不是算出一个假分数。扫描件 PDF 抽不出文本是**预期行为**（本来就该走 OCR），此时拿 `raw=0` 去算 `1 - parsed/max(raw,1)` 会得到 `1 - parsed` 的大负数，恒判通过——这个公式缺陷必须堵死。

**3.0.1 PDF 的 `raw` 与解析器同源，这条检查的强度弱于其他格式**

DOCX / XLSX / PPTX 的 `raw` 用的是**另一套库**（`python-docx` / `openpyxl` / `python-pptx`），
与解析器（markitdown）彼此独立，抽取路径不通，所以漏内容能被查出来。
PDF 不一样：`raw` 和 `PdfParser` 都是同一个后端库，只是调用方式不同（纯文本流 vs 版面分析转 Markdown）。

后果是**能查出来的漏项变窄**：只能查出版面分析阶段丢掉的内容（页眉页脚被判为噪声、表格转 Markdown 时丢单元格），
查不出底层抽取引擎本身就没抽到的内容（比如嵌在矢量图里的文字——两个调用都拿不到）。

这不构成"检查无效"，但**强度必须在文档里说清楚**，否则会误以为 PDF 的守恒关与其他格式等价。
缓解手段：`raw` 取到 words 级（`get_text("words")` 拼回文本，或直接 `rawdict`），
比 `get_text("text")` 更贴近"底层全量"，能覆盖更多版面分析丢失的情况。

```python
def _digit_loss(report) -> float | None:
    if report.digit_count_raw < cfg.digit_count_min_for_check:
        return None # 不适用：原文数字量太少，比值无统计意义
    return 1 - report.digit_count_parsed / report.digit_count_raw

def _text_coverage(report) -> float | None:
    if report.raw_char_count < cfg.raw_char_min_for_check:
        return None
    return report.char_count / report.raw_char_count
```

| 检查 | 公式 | 适用性判据 | 阈值 |
| --- | --- | --- | --- |
| 数字字符守恒 | `1 - parsed_digits / raw_digits` | `raw_digits ≥ digit_count_min_for_check` | > 0.10 → warn；> 0.30 → reject |
| 文本覆盖率 | `parsed_chars / raw_chars` | `raw_chars ≥ raw_char_min_for_check` | < 0.60 → warn；< 0.40 → reject |
| 表格还原度 | `parsed_tables / detected_tables` | `detected_tables ≥ 1` | < 0.80 → warn |

返回 `None` 的检查项记入 `report.not_applicable`，在 `inspect` 命令输出里显式展示"本项不适用"。**这比给出一个人为的 0 分诚实得多**——扫描件 OCR 后数字守恒不适用，但表格还原度仍可用，两项独立判定，不互相掩盖。

> 对 Markdown 源文件的额外注意：Markdown 化会插入 `|`、`#`、`-` 等标记字符，使 `char_count` 偏大，`text_coverage` 可能 > 1。此时该指标失去判别力，应在 `block_type` 分布中标注并对 md/txt 源直接置为不适用。

### 处置判定

```python
def _verdict(report: QualityReport, cfg: QualityConfig, ocr_available: bool) -> str:
    # 1. 扫描件但没有可用 OCR 通道 → 拒绝（注意判定发生在路由降级之后）
    if report.is_scanned and not ocr_available:
        report.issues.append("scanned_without_ocr")
        return "rejected"
    # 2. 扫描件走了 OCR → 守恒检查不适用，改看绝对量下限
    if report.is_scanned and ocr_available:
        if report.char_count < cfg.ocr_min_chars: # OCR 只吐出几十个字 = 失败
            report.issues.append("ocr_output_too_small")
            return "rejected"
    # 3. 严重项（仅当检查适用时才参与判定）
    if report.digit_loss is not None and report.digit_loss > cfg.digit_loss_reject:
        return "rejected"
    if report.text_coverage is not None and report.text_coverage < cfg.text_coverage_reject:
        return "rejected"
    # 4. 一般项
    if report.issues:
        return "warned"
    return "ok"
```

第 2 条的必要性：扫描件走 OCR 后，`raw` 基线为空、守恒检查整项不适用；若无兜底判据，一份 OCR 失败的文档会以 `ok` 入库。**因此补一个绝对量下限**（`ocr_min_chars`，默认 200）。

**核心原则：宁可拒绝入库，也不能带病入库。** 解析错误不会让系统报错，只会让答案悄悄变差，且事后无法定位。被拒绝的文档进入 `data/rejected/` 并记入摄取报告，等待人工介入。

### 路由逻辑

```python
def route(path: Path, probe: ProbeResult, cfg: IngestionConfig) -> BaseParser:
    ext = path.suffix.lower
    if ext in (".docx", ".doc"):
        return DocxParser
    if ext in (".xlsx", ".xls"):
        return XlsxParser
    if ext in (".pptx", ".ppt"):
        return PptxParser
    if ext in (".html", ".htm"):
        return HtmlParser
    if ext in (".md", ".markdown"):
        return MarkdownParser
    if ext == ".txt":
        return TextParser
    # ── 以下为 PDF 分支 ──
    if cfg.use_docling and probe.table_density > cfg.docling_table_density_threshold:
        return DoclingParser # 表格密集
    if probe.is_scanned:
        return DoclingParser # 扫描件走 OCR
    return PdfParser # 默认快速通道
    # 未知扩展名 → 走质量关卡的"不支持格式"，拒绝入库（不静默当成 txt）
```

### 降级链

```
DoclingParser 失败/未安装 → PdfParser
PdfParser 失败 → PdfPlainTextParser（仅抽文本，丢结构，记 warned）
PdfPlainTextParser 失败 → 拒绝入库
```

> 扫描件在 `docling` 未安装时的完整走向：`DoclingParser` 不可用 → 降 `PdfParser` → 抽不出文本 →
> 降 `PdfPlainTextParser` → 仍然为空 → **由关卡 3 的 `ocr_min_chars` 判为 OCR 失败并拒绝入库**（03§4）。
> 这条链路的终点是"拒绝入库"而不是"产出一个空文档"，与 01 §2「宁可拒绝入库，也不带病入库」一致。

降级发生时必须在 `QualityReport.issues` 中记录，否则调用方无从得知拿到的是降级结果。

### 表格处理约定

- 输出统一为 **Markdown pipe table**（chunker 与质量模块都按此格式解析）
- 表格块 `is_atomic = True`
- 超大表（> `table_split_threshold_tokens`）切分时按行组切且**每组重复表头**
- 表格的大小分级与上限豁免规则见 **§6.4**（原子性优先于子块粒度）

## 6. 模块 `ingestion/chunking/`

### 接口

```python
@dataclass
class ChunkPair:
    parent: Chunk
    children: list[Chunk]

class BaseChunker(Protocol):
    name: str
    def chunk(self, doc: ParsedDocument) -> list[Chunk]

class StructuralChunker: name = "structural" # 单层基线，用于消融对照
class ParentChildChunker: name = "parent_child" # 默认

def get_chunker(cfg: IngestionConfig) -> BaseChunker
```

> **Late Chunking 已明确移除，不作为第三种策略。** 原因：Late Chunking 需要先拿到整段的 **token 级 embedding** 再按边界池化，而 DashScope 的 OpenAI 兼容 `/embeddings` 端点只返回整段一个向量，不提供 per-token 输出。在"模型能力全部走云端 API"这一前提下它无法实现，硬做一个假的（比如用整段向量近似每个子块）只会让消融结论失真。
> 保留它的唯一正当路径是自建 embedding 服务（本地加载支持 `output_dim`/token-level 的开源模型），那已经超出本项目的选型边界。**明确写出"当前供给下做不了"，比做一个自欺欺人的实现更可信。**
> 因此切分是两策略，B2 消融组相应调整为 `structural vs parent_child`（对比的是"单层块检索"vs"子块检索 + 父块回填"这一检索粒度变量）。

### 6.1 上下文增强块头

所有切分策略共用：

```python
def with_header(chunk: Chunk) -> str:
    path = " > ".join([chunk.source, *chunk.title_path])
    return f"[{path}]\n{chunk.raw_text}"
```

零成本，解决 chunk 脱离文档后的指代丢失（"它的上限是多少？" —— "它"指谁？）。

### 6.2 StructuralChunker

- 按标题树的**最深层标题**切分子树
- 子树内若超 token 上限，按段落边界再切，切出的每段都保留完整标题路径
- 表格块整体不切

### 6.3 ParentChildChunker（默认）

```
文档 → 按标题树切出父块（≤1024 token），编号 {doc_id}:p{seq:03d}，is_parent=True
     → 每个父块内按段落切出子块（≤256 token，overlap 48），编号 {doc_id}:c{seq:04d}，parent_id=父块 ID
     → 子块 embedding + BM25 索引；命中子块后回填父块给生成
     → chunk 返回 [父块, *子块] 平铺列表，调用方按 is_parent 分流（见 §0.1）
```

Small-to-Big：子块向量语义集中召回准，父块保证生成时上下文完整。

**父块不重新编号自己内部的子块**：子块的 `seq` 是文档级自增而非父块内自增，这样 `chunk_id` 全局唯一且顺序稳定，B2 消融切换切分策略时 `parents.jsonl` 的键也不会与子块撞车。

### 6.4 表格块与子块上限的冲突规则

"表格永不切分"与"子块 ≤ 256 token"在中间地带直接打架：一个 400 token 的表，到底是原子不切（违反子块上限），还是按行组切（那 `table_split_threshold_tokens` 与 256 是什么关系）？原文档两处规则并存且没有优先级，实现时无从下手。现按 **原子性优先、上限分级** 定死：

| 表格 tokens | 处置 | `is_atomic` | 说明 |
| --- | --- | --- | --- |
| ≤ `child_chunk_tokens`(256) | 整个表作为一个子块 | True | 最常见情况 |
| 256 < t ≤ `table_split_threshold_tokens`(1024) | 整个表作为**一个超长子块** | True | 原子性优先，豁免子块上限；只要 ≤ `atomic_max_tokens` 就合法 |
| > `table_split_threshold_tokens`(1024) | 按**行组**切成多个块，每组重复表头 | True | 每组 ≤ 1024；组间靠重复表头保证列语义 |
| 单行就 > `atomic_max_tokens`(2048) | 放弃原子性，按字符切并记 issue | False | 极端宽表，降级并告警 |

三条硬规则：

1. **原子块的上限是 `atomic_max_tokens`，不是 `child_chunk_tokens`。** 原子性优先于粒度。
2. `table_split_threshold_tokens` 默认等于 `parent_chunk_tokens`（1024），语义是"超过父块大小的表格才需要拆"。
3. 按行组切出的每一块都保留完整表头，`title_path` 相同，`is_atomic` 仍为 True。

### 6.5 切分后完整性检查

```python
def validate_chunks(chunks: list[Chunk], cfg: IngestionConfig) -> list[str]:
    # parent_child 策略下：每个 child 必须有 parent，且 parent_id 可解析
    # parent_id 必须指向同文档内一个 is_parent=True 的块
    # is_parent=True 的块：parent_id 必须为 None，且不得被送进向量/BM25 索引
    # structural 策略下：所有块 is_parent=False 且 parent_id=None，允许（回填时用块自身）
    # 非原子块（is_atomic=False）：tokens ∈ [1, child_chunk_tokens]
    # 原子块（is_atomic=True）：tokens ∈ [1, atomic_max_tokens]，豁免子块上限
    # 每个 chunk 必须有非空 title_path 或能追溯到文档根
    # 表格原子块的行必须完整：每行的单元格数 == 表头列数
    # 同一切分组内，按行组切开的表格块数量 × 表头行数 ≤ 总行数（防止重复计数）
```

违反前三条返回 issue 列表，由调用方决定是修正还是拒绝入库；**不抛异常中断整个摄取批次**——单文档问题不应拖垮全量构建。

## 7. 模块 `index/`

### 7.1 `index/vector_store.py`

```python
@runtime_checkable
class VectorStore(Protocol):
    def create(self, dim: int, version: str) -> None: ...
    def upsert(self, ids: list[str], vectors: list[list[float]], payloads: list[dict]) -> None: ...
    def search(self, vector: list[float], top_k: int, flt: dict | None = None) -> list[tuple[str, float]]: ...
    def delete_by_doc(self, doc_id: str) -> None: ...
    def count(self) -> int: ...
    def load_meta(self) -> dict: ...
    def save_meta(self, meta: dict) -> None: ...

class QdrantStore: ... # local 模式与 server 模式共用，仅连接参数不同
class InMemoryStore: ... # 依赖不可用时的降级实现

def get_vector_store(cfg: Config) -> VectorStore
```

**`QdrantStore` 的实现要点**

1. **local 与 server 不分叉**：`get_vector_store` 只按 `backend` 决定构造
   `QdrantClient(path=...)` 还是 `QdrantClient(url=..., api_key=...)`，**其余代码路径完全一致**。
   这不是"顺手支持两种"，而是消除 02 §10 里那条永远无法验证的跨库迁移演进项。
2. **距离度量写死为 `Cosine`，不做成配置项**：`search` 返回的 score 必须是余弦相似度 ∈ [-1,1]，
   充分性判据直接消费它。留成配置项等于埋一个"改了度量、阈值静默失效"的坑——
   **`create` 时要断言已有集合的度量与预期一致**，不一致直接报错而不是继续用。
3. **payload 过滤下推**：`flt` 映射为 Qdrant filter（`block_type == "table"` / `doc_id == ...`），
   在 ANN 之前生效。这是 04§4 `filter_tables_only` 的实现落点，也是它与"融合后再筛"的语义差别。
4. **meta 仍单独落盘**：Qdrant 没有 collection 级 metadata API，`index_version` / `dim` / 构建时间
   照旧写 `data/index/meta.json`（与 BM25 索引同级），**不由向量库托管**。
   **因此 Qdrant local 的数据放在子目录 `data/index/qdrant/`**（实现期定案：
   Qdrant local 也会在它的 path 下写一个自己的 `meta.json`（内容是 `{"collections": ...}`），
   两者同路径会互相覆盖——后写的一方让先写的一方损坏。实测症状：Qdrant 启动时
   `KeyError: 'collections'` → 静默降级 InMemoryStore，从外面看只是"向量检索结果不对"。
5. **local 模式独占目录**：打开前检查目录是否被占用，占用则给出明确错误
   （"索引目录已被其他进程打开，请先停止服务"），而不是等文件锁超时——**server 常驻时不能后台重建索引**。
   占用判定只认 Qdrant 报的 `already accessed`，不认 `.lock` 文件存在与否。
6. **InMemoryStore 的意义**：qdrant-client 若在当前环境装不上，系统仍能跑通全流程（brute-force 余弦），
   持久化到 `memory_store.pkl`（单机 pickle，无并发访问）。这保证作品在任何环境可演示。
   降级时向量检索的 payload 来源仍是 `data/index/chunks.jsonl`。

### 7.2 `index/bm25.py`

```python
class BM25Index:
    def __init__(self, k1: float = 1.5, b: float = 0.75)
    def build(self, chunks: list[Chunk], user_dict: list[str] | None = None) -> None
    def search(self, query: str, top_k: int) -> list[tuple[str, float]]
    def save(self, path: Path) -> None
    @classmethod
    def load(cls, path: Path) -> "BM25Index"
```

**实现要点**

- 分词：jieba 精确模式 + 用户词典（领域术语从 `data/user_dict.txt` 加载）
- 倒排表：`term -> [(doc_id, tf)]`，查询时只对命中 term 的文档打分，保证亚线性
- 长度归一化：`b=0.75`，IDF 用 `log(1 + (N - df + 0.5)/(df + 0.5))`
- 持久化：pickle 存倒排表与文档长度表

**BM25 不支持增量（必须写进文档，否则实现会踩坑）**

IDF 依赖全语料的 `N` 与 `df`，插入少量文档会改变所有 term 的 IDF，因此**任何一次 `upsert_documents` 都会触发 BM25 全量重建**（向量库是增量的，BM25 不是，两者不对等）。相关约定：

1. `IndexStore.upsert_documents` 内部顺序为：向量 upsert（增量）→ BM25 `build`（全量）。
2. 全量重建的代价是 O(chunk 数)。**适用规模上限约 5 万 chunk**（实测目标：单次重建 < 30s）；超过后应换 Lucene/Tantivy 系或走 02 §10 的演进路线。
3. 因此"在线增量索引"在架构文档里被列为 Out of Scope——接口留了，但语义上是"增量向量 + 全量倒排"，这点必须如实说明，不能让人以为两边都是增量的。
4. **全量重建的数据源是 `data/index/chunks.jsonl`（全量检索单元物化视图，见 §7.3）**。
   重建不能直接拿 `upsert_documents` 的入参——那只是本次增量的 chunk，拿它重建等于把倒排表清空重来。
把 BM25 重建挂在逐文档并发摄取的路径上会同时犯两个错：数据源不对（只有本次增量的记录），且并发写同一个 pickle。

**用户词典缺失的处置**：`user_dict_path` 指向的文件不存在时，不得抛错——降级为 jieba 默认词典，
并在 `BuildReport.warnings` 里记一条 `user_dict_missing`。理由：词典是增强项不是前提，
但"悄悄不用"和"明确告警"是两回事，后者才能被 09 的集成测试断言住。

**为什么自研**：中文分词必须可控。通用向量库的 FTS 多基于 Lucene/Tantivy，中文默认按字切或需额外插件，效果不可控。

### 7.3 `index/store.py`（索引门面）

```python
@dataclass
class BuildReport:                    # 索引构建报告
    docs_ok: int = 0 # verdict ∈ (ok, warned) 且成功入库
    docs_rejected: int = 0 # verdict == rejected，已移入 data/rejected/
    chunks_indexed: int = 0 # 检索单元数（is_parent=False）
    parents_written: int = 0 # 父块数（is_parent=True）
    warnings: list[str] = field(default_factory=list) # 含 user_dict_missing
    probe_total: int = 0
    probe_hits: int = 0
    probe_failures: list[tuple[str, list[str]]] = field(default_factory=list)
    index_version: str = ""
    verified: bool = True # 探针通过率 ≥ min_hit_rate
    partial_failure: bool = False # 阶段 B 部分写入失败
    elapsed_s: float = 0.0

    @property
    def probe_hit_rate(self) -> float:
        return self.probe_hits / self.probe_total if self.probe_total else 1.0

class IndexStore:
    def __init__(self, cfg: Config)
    def build(self, chunks: list[Chunk]) -> BuildReport # 全量构建
    def upsert_documents(self, chunks: list[Chunk]) -> None # 增量
    def load(self) -> None # 加载并校验版本
    def get_chunks(self, ids: list[str]) -> list[Chunk] # 反查（含父块）
    def all_chunks(self) -> list[Chunk] # 全量检索单元视图，BM25 重建数据源
    def parent_of(self, child_id: str) -> Chunk | None
    def stats(self) -> dict
```

`BuildReport` 是摄取链路**对外唯一的结算凭证**——CLI 打印它、探针写入它、
`07§4` 的集成测试断言它。因此字段必须是**可断言的具体数值**而不是自由文本，
`probe_hit_rate` 用派生属性而不是落盘字段，避免两处数据不一致。

**版本校验（硬性）**

```python
meta = self.vector_store.load_meta
if meta.get("version") != cfg.index_version:
    raise IndexVersionMismatch(期望版本, 实际版本, 提示重建命令)
# 只比 version 不够：version 由 embedding 模型 + 维度 + 切分参数算出，
# 不含 BM25 打分参数与用户词典，改了这两项却不重建会静默加载旧索引。
if meta.get("bm25_signature") != cfg.bm25_signature:
    raise IndexVersionMismatch(BM25 参数/用户词典不一致, 提示重建命令)
if meta.get("degraded"):
    self.warnings.append("index_degraded：构建时向量路失败，当前只有 BM25 生效")
```

**两个指纹必须分开**

| 指纹 | 含什么 | 用途 |
| --- | --- | --- |
| `bm25_signature` | `bm25_k1` / `bm25_b` / 用户词典 sha256 | **加载校验**：这些变了，已落盘的 BM25 与分词就不是当前配置想要的东西 |
| `retrieval_signature` | 上面三项 **+** `use_bm25` / `use_vector` / `fusion_strategy` / 各 `top_k` / `min_candidates` / `sufficiency_vector_floor` | **结果缓存键**与 `EvalReport` 存证 |

判据一句话：**这个参数变了，已落盘的索引内容会变吗？** 会 → 进 `bm25_signature`；不会 → 只进 `retrieval_signature`。
拿整体签名做加载校验是错的：04§9.4 的 A1 变体只关 BM25 路，压根不需要重建索引，一拦消融就跑不起来。

**增量写入必须先去重**：`upsert_documents` 的物化视图是 `mode="a"` 追加的，
重复摄取同一文档会堆重复行（BM25 按全量视图重建 → 同一块被索引两次、IDF 与 docs 计数全错）。
因此要先按 `chunk_id` 过滤掉已存在的块，写完后回写 meta 的 `chunks` / `parents` 计数——
否则 `stats` 的数字会长期停在构建时，与磁盘上的 jsonl 不一致且不报错。

**父块单独存储**：父块不进向量索引（否则索引体积翻倍），存在 `data/index/parents.jsonl`，命中子块后按 `parent_id` 反查。

**检索单元物化视图 `data/index/chunks.jsonl`**：所有 `is_parent=False` 的块（`chunk_id: text/raw_text/source/title_path/block_type/is_atomic/page/tokens`）追加写一份。
它有三个用途：① BM25 全量重建的数据源；② `InMemoryStore` 降级时向量检索的 payload 来源；③ 索引损坏时的可重建基线。
代价是文本存两份（向量库 payload 里还有一份），按 5–8k chunk、每块 ~1KB 估约 5–8MB，可接受。

## 8. 离线链路执行流程

```
cli.ingest
  ├─ 阶段 A · 解析（无共享状态，可并发）───────────────────────────────
  │ 遍历 data/raw/，按扩展名过滤
  │ 线程池（workers=4），每篇独立：
  │ ├→ quality.raw_baseline # 取 raw 基线（可能为 ""）
  │ ├→ quality.probe_before_parse # 关卡 1
  │ ├→ router.route → parser.parse # 解析 + 降级
  │ ├→ quality.validate_structure # 关卡 2
  │ ├→ quality.check_conservation # 关卡 3（不适用项自我声明）
  │ └→ quality.build_report → verdict
  │ verdict == rejected → 移入 data/rejected/，本篇不产出 chunk
  │ verdict in (ok, warned) → chunker.chunk → validate_chunks
  │ 收集：all_chunks（父块与子块平铺）+ 每篇 QualityReport
  │
  ├─ 阶段 B · 索引（有共享状态，必须串行）─────────────────────────────
  │ IndexStore.build(all_chunks) # 一次性全批，单线程
  │ ├→ 按 is_parent 分流：父块 → parents.jsonl；检索单元 → 后续
  │ ├→ 检索单元写 chunks.jsonl（全量视图）
  │ ├→ embedding.embed(检索单元) # IO 并发：10 条一批 × N 路
  │ ├→ vector_store.upsert # 批量一次
  │ └→ bm25.build(all_chunks 的检索单元) # 全量重建，全程只此一次
  │
  └─ 阶段 C · 校验 ────────────────────────────────────────────────────
     probe.run(cfg) # 见 §10，默认开启
     未命中 → 记入 BuildReport.probe_failures，索引标记为 unverified
     输出 BuildReport：文档数 / 拒绝数 / chunk 数 / 告警数 / 探针通过率 / 耗时
```

### 8.1 为什么必须切成"并发解析 + 串行索引"两阶段

原流程图把 `IndexStore.upsert_documents` 画在 4 路并发分支内，而它内部要触发 BM25 全量重建。按原文实现会同时踩三个坑：

| 坑 | 后果 |
| --- | --- |
| 每篇文档触发一次 BM25 全量重建 | 72 篇 = 72 次 O(N) 重建，复杂度退化为 O(N²) |
| 并发写同一个 `bm25.pkl` | 后写的覆盖先写的，倒排表损坏且**不报错**——下一次查询才表现为召回莫名变差 |
| 重建的数据源只有本次增量 | 即便串行，每篇重建一次也等于把倒排表推倒重来，最终只剩最后一篇的内容 |

拆成两阶段后：并发只跑**无共享状态**的解析与切分（每篇只读写自己的文件），索引写入退化为一次单线程批量操作。
**embedding 的批处理仍是并发的**——它是纯 IO、无共享状态，不属于这里的"串行"约束；串行约束只针对"写向量库 + 写 BM25 + 写物化视图"这一组有共享状态的动作。

**探针内建在摄取流程里，不依赖人记得跑一次。** `run_probe_after_build=True` 时，索引构建完成后自动跑探针集并过滤到本次入库的来源。
探针问题必须带**可判定的字面锚**（编号 / 专名 / 参数名），否则"命中来源"的判定不稳定，探针会变成噪声源（§10）。

## 9. 错误处理总表

| 异常 | 处置 |
| --- | --- |
| 文件加密/损坏 | 拒绝入库，记入 rejected |
| 扫描件且无 OCR | 拒绝入库 |
| 解析器全部失败 | 拒绝入库 |
| 表格还原度 < 阈值 | warned，继续入库 |
| `raw` 基线为空 | 守恒检查置为不适用，记入 `not_applicable`，**不判 ok** |
| 扫描件 OCR 输出 < `ocr_min_chars` | 拒绝入库 |
| 表格单行 > `atomic_max_tokens` | 放弃原子性按字符切，记 issue，warned |
| Embedding 调用失败 | 重试 3 次；仍失败则该文档入库失败，不影响其他文档 |
| 向量库写入失败 | 降级 InMemoryStore 并告警 |
| BM25 全量重建失败 | 索引标记 `bm25_unavailable`，检索仅走向量路并告警 |
| 用户词典 `user_dict.txt` 缺失 | 降级 jieba 默认词典，记 `BuildReport.warnings: user_dict_missing`，不阻断 |
| 摄取阶段 B 部分失败 | 已写入的向量与 BM25 保持上一版，本次 `BuildReport` 标记 `partial_failure` 并列出失败 chunk |
| 探针问题未命中 | 索引标记 `unverified`，不阻断但必须在 BuildReport 中显式暴露 |
| 索引版本不匹配 | 抛错，拒绝加载 |

## 10. 模块 `eval/probe.py`（探针校验）

### 职责

用一批**答案位置已知**的问题，验证"解析 → 切分 → 索引 → 检索"整条链路是否真的通。它校验的不是单点，而是端到端连通性——这比任何单点质量检查都可靠。

### 接口

```python
@dataclass
class ProbeCase:
    question: str
    expect_source: str # 期望命中的文件名
    expect_sources: list[str] # 等价来源（任一命中即可）——同一开源文档在语料里有
                                  # md/docx/pdf/xlsx 多个副本，命中任一副本都算链路通
    expect_title_path: list[str] # 期望命中的标题路径（可选，用于更严的校验）
    expect_block_type: str | None # paragraph | table，用于单独校验表格链路
    expect_answer_contains: str | None # 期望答案中包含的字面片段（数值型尤其有效）

@dataclass
class ProbeRunResult:                 # 探针运行结果（与解析质量关卡的 ProbeResult 区分）
    total: int
    hit: int # 来源级命中：期望来源（或等价来源）出现在 Top-K 内
                                  # ——assert_healthy 只看它，这才是"连通性"
    content_hit: int # 内容级命中：期望片段出现在期望来源的 Top-K 块内
                                  # ——"表格没被切碎、数值没丢"的信号。来源对但内容块
                                  # 没进 Top-K 是排名问题（评测集的职责），不是连通性
                                  # 问题，混在一个数里会让探针报警报错对象
    failures: list[tuple[ProbeCase, list[str]]] # (用例, 实际命中的 Top-K 来源)
    content_failures: list[tuple[ProbeCase, list[str]]]

    @property
    def hit_rate(self) -> float:
        return self.hit / self.total if self.total else 1.0

def run(cfg: Config, k: int = 5) -> ProbeRunResult
def assert_healthy(result: ProbeRunResult, min_hit_rate: float = 0.9) -> None
```

### 探针集构成（`eval/probe_set.jsonl`）

| 类别 | 数量 | 作用 |
| --- | --- | --- |
| 正文事实 | 8 | 覆盖各文档的普通段落 |
| **表格数值** | 6 | 专门验证表格没被切碎、数值没丢 |
| 专有名词 / 编号 | 4 | 验证 BM25 路可用（关掉 BM25 后这组应当掉分，反过来证明混合检索有效） |
| 跨页 / 多跳 | 2 | 验证父块回填与多子查询合并 |

**必须包含表格数值类**，因为"表格被切碎 → 检索到表头拿不到数值"是本项目的头号失效模式，探针是唯一能在每次重建索引后自动发现它的手段。

### 触发时机与处置

1. `cli.ingest` 构建完成且 `run_probe_after_build=True` 时自动执行。
2. 命中率 < `min_hit_rate` → 索引标记 `unverified`，`BuildReport` 显式输出失败用例与实际命中列表。
3. **探针失败不阻断入库**——它是告警而非门禁，但必须"看得见"。
4. 单独执行：`python -m agentic_rag.cli probe [--k 5]`。

### 与评测集的区别

| | 探针集 | 评测集 |
| --- | --- | --- |
| 目的 | 链路连通性回归 | 检索与生成质量度量 |
| 规模 | ~20 条 | 60–100 条 |
| 判据 | 期望来源是否进 Top-K | Recall@K / NDCG@K / 忠实度 |
| 跑的时机 | 每次重建索引后 | 变更检索/生成配置后 |
