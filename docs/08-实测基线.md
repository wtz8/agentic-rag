# API 实测基线

> 目的：给出真实的延迟、token 与成本量级，作为架构预算与配置取值的依据。
> 环境：本地家用宽带 · 模型供给：阿里云百炼 DashScope。
> 口径：**单次采样，样本量偏小**，用于校准设计量级；正式指标由评测阶段的 trace 汇总产出。

---

## 0. 概览

| 项 | 设计初值 | 实测 | 结论 |
| --- | --- | --- | --- |
| qwen-flash 单次调用 | 200ms | p50 **412ms** | 低估约 2 倍 |
| qwen-plus 流式首字 | 800ms | **331–363ms** | 高估一倍 |
| simple 路径"到答案就绪" | 1.9s | **约 4.7s** | 低估 2.5 倍，原因见 §3.3 |

前两项误差方向相反、量级相当，端到端"到首字"的估算恰好接近实测；第三项是真实错误：原估算只计了"到首字"，漏掉终答全文生成的时间。

## 1. 连通性与在架核对

四个端点全部连通，Key 有效。

| 能力 | 端点 | 模型 | 结果 |
| --- | --- | --- | --- |
| 轻量 LLM | `/compatible-mode/v1/chat/completions` | `qwen-flash` | 在架 |
| 终答 LLM | 同上 | `qwen-plus` | 在架 |
| 备用终答 | 同上 | `qwen-max` | 在架 |
| Embedding | `/compatible-mode/v1/embeddings` | `text-embedding-v4` | 在架 |
| Rerank | `/api/v1/services/rerank/text-rerank/text-rerank` | `qwen3-rerank` | 在架 |
| 具体版本号 | 同上 chat | `qwen3.8-flash` / `qwen3.7-plus` | 在架 |
| — | 同上 chat | `qwen-turbo` | ⚠️ 返回 429 限流，**未能确认在架状态** |

`qwen-turbo` 的 429 是 `limit_requests`（QPS 超限），**不是**模型不存在。但这也说明该账号存在 QPS 闸门，实现时必须遵守 03§1 的 `max_concurrent_queries` 限流与 `retry_backoff` 退避——这两个配置项不是摆设。

### 一个必须现在定死的决策：用别名还是锁版本

配置树默认值是 `qwen-flash` / `qwen-plus`（**别名**）。实测别名与具体版本（`qwen3.8-flash` / `qwen3.7-plus`）同时在架，两者都能用，但语义完全不同：

| | 别名 `qwen-plus` | 固定版本 `qwen3.7-plus` |
| --- | --- | --- |
| 行为 | 官方升级后**静默漂移**到底层新模型 | 行为锁定 |
| 评测可复现 | ❌ 两次消融实验之间模型变了都不知道 | ✅ |
| 长期维护 | 自动跟上新版本 | 需手动跟进 |

**决策：评测与消融实验一律锁具体版本号，只有日常演示才用别名。** 理由是本项目最大的可信度风险就是"结论不可引用"——如果 A2 组和 A3 组跑在不同的底层模型上，整份消融报告的差异就分不清是配置带来的还是模型升级带来的。配置树里应保留别名为默认值（降低首次运行门槛），但 `EvalReport` 必须记录**实际生效的模型名**（响应体里的 `model` 字段），而不是配置里的请求值。

## 2. 接口契约核对（三处与文档不一致）

### 2.1 rerank 返回结构多了一层 `output` ⚠️

03§2.4 写的是"返回 `results[].index` 与 `results[].relevance_score`"。实测顶层结构是：

```jsonc
{
  "output": { "results": [ {"index": 0, "relevance_score": 0.859} ] },
  "usage": { "total_tokens": 96 },
  "request_id": "b66adf50-..."
}
```

**返回结构多了一层 `output`**：`relevance_score` 在 `output.results[]` 里，不在顶层 `results[]`。
按顶层结构实现会在图必经的精排节点上抛 `KeyError`，因此解析路径固定为 `d["output"]["results"]`（03§2.4）。

同一个请求里顺带确认了 `parameters.top_n` **生效**（传 2 返回 2 条），因此客户端不必自己截断。

### 2.2 embedding 的 `dimensions` 参数确实必需

实测 1024 / 768 / 2048 三档均返回对应维度。03§2.3 强调"必须显式传 `dimensions`"是正确的——不传则依赖服务端默认值，一旦与向量库 collection 定义不一致，报错会发生在写入阶段而非启动阶段。

### 2.3 流式协议符合 OpenAI 兼容格式

`data: {...}` 分片 + `data: [DONE]` 结尾，与 04§10.2 的 SSE 协议设计一致，前端 `EventSource` 可直接消费。

## 3. 延迟与 token 实测

### 3.1 逐项数据

| 项目 | 实测 | 原估算 |
| --- | --- | --- |
| qwen-flash 串行 10 次（短输出） | min 365ms · **p50 412ms** · p90 467ms | 200ms |
| qwen-flash 4 路并发 | 4/4 成功 · p50 431ms · 总 0.84s | — |
| qwen-flash 8 路并发 | 8/8 成功 · p50 399ms · 总 0.57s | — |
| embedding 单条（约 300 token） | 261ms · 313 token | 150ms |
| embedding 10 条批量 | 543ms（**54ms/条**）· 3130 token | — |
| embedding 单请求输入上限 | **33000**（超出报 `InvalidParameter: Range of input length should be [1, 33000]`） | 未估算 |
| rerank 10 条候选 | 242ms · 2120 token | — |
| rerank 20 条候选 | 256ms · 4250 token | — |
| rerank 50 条候选 | **294ms** · **10640 token** | 300ms · ~15k token |
| qwen-plus 流式首字 | 331–363ms | 800ms |
| qwen-plus 全文（155–285 字） | 2.6–4.5s | 未估算 |

### 3.2 三条从数据里读出来的设计结论

**① 批量 embedding 的收益是 4.8 倍，必须批量——但批量不能只看条数。** 单条 261ms vs 批量摊薄 54ms/条。离线摄取 5–8k chunk 的场景下，不批量要多花约 30 分钟。03§2.3 定的"10 条一批 + 并发"是正确的。

> **分批的两个上限**：单请求除条数外，还有**输入总长度** 33000 的硬上限。只按条数分批不够——本语料块长中位数 316 字符、最长 5.6 万字符，10 条长块凑一起照样超限，整批返回 400，这批块全部拿不到向量，而索引会带着 `degraded=true` 继续工作。
> 因此按"条数 ≤ 10 **且** 单批总长 ≤ 30000"双约束分批（留 10% 余量：本地按字符估、服务端按 token 计）；单条本身就超限的单独成批且不截断——截断后的向量不代表那段文本，宁可让它明确失败（03 §2.3）。

**② rerank 的延迟对候选数几乎不敏感，成本才是线性增长的。** 候选从 10 增到 50，延迟只从 242ms 涨到 294ms（+21%），token 却从 2120 涨到 10640（**5 倍**）。

这直接决定了 02 §7 演进路线里"把精排候选从 Top-50 收到 Top-20"的理由：**收缩省的是钱（约省 60% 精排 token），不是延迟（只省 40ms）**。反过来说，若为召回率放宽 `fusion_top_k`，代价可预测：每加 10 条候选约 +2100 token、+15ms。

**③ 终答全文生成是"到答案就绪"的主要成本，占近 60%。**

### 3.3 simple 路径预算重算

| 步骤 | 实测耗时 | 累计 |
| --- | --- | --- |
| 意图路由（qwen-flash） | 412ms | 412ms |
| 双路召回（embedding + BM25 并行，取 embedding 路） | 261ms | 673ms |
| RRF 融合（本地） | <5ms | 678ms |
| 精排（50 条候选） | 294ms | 972ms |
| 生成首字（qwen-plus 流式） | 340ms | **≈ 1.3s 到首字**（1312ms） |
| 生成全文（约 160 字） | 2600ms | 3.9s（3912ms） |
| 引用校验（qwen-flash × 2 次：命题抽取 + 出处核对） | 824ms | **≈ 4.7s 到答案就绪**（4748ms） |

- **到首字 ≈ 1.3s**：路由与生成首字的误差方向相反、量级相当，端到端恰好接近设计初值。
- **到答案就绪 ≈ 4.7s**：设计初值 1.9s，低估 2.5 倍。引用校验是**两次**模型调用，不是一次（04 §6.7）。

> 这个量级不改变架构决策，但决定产品形态：流式不是锦上添花，而是**必须**——用户在首字 1.3s 时就开始读答案，剩下 3.4s 由后台写完并完成校验。若改为非流式接口，用户要干等近 5 秒。

## 4.5 成本结构：一次全量摄取的量级

真实 API 全量摄取后的核算：

| 项 | 数值 |
| --- | --- |
| 检索单元 | 33,477 个（**父块 9,583 个不进向量路**，其字符量是单元的 0.81 倍） |
| 输入字符 | 11,558,196 |
| 折算 token | 578 万 – 1,156 万（1 字符 ≈ 0.5–1 token） |
| 费用（标准价 ¥0.0005/千） | **≈ ¥2.89 – ¥5.78** |
| 费用（Batch 接口，半价） | ≈ ¥1.44 – ¥2.89 |
| **免费额度** | **100 万 token**（百炼开通后 90 天内） |

**结论：一次全量摄取是免费额度的 5.8 倍**。所以"跑之前知道这一趟要花多少"
不是锦上添花，而是能不能开跑的前提——成本不可预知属于工程缺陷。

单价来源：百炼定价页 `text-embedding-v4` 中国内地 ¥0.0005/千 token，
Batch 接口 ¥0.00025/千；`qwen3-rerank` ¥0.0006/千。**LLM 单价未查实，不估。**

### 两条操作规程

1. **跑之前先估**：`python -m agentic_rag.cli ingest --dry-run` /
   `eval --dry-run` 只做本地解析与估算，不调用任何付费 API（`eval/cost.py`）。
2. **先小样本再全量**：`eval --limit N` 取前 N 条（固定子集，便于逐条对比），
   先用小样本确认链路与口径，再放全量。

> 估算按字符折算，真实消耗以 provider 回传的 `usage` 为准
> （`providers/base.record_usage` 的 `usage_total`）。两者偏差大时应回来修折算系数。

## 5. 本基线的边界（不要高估这些数字）

- **样本量小**：并发与串行各十余次，未覆盖 P95/P99；正式数字必须由 trace 汇总。
- **未测真实数据**：所有请求用的是人造文本，真实语料下 chunk 更长、命中更多，延迟会上升。
- **未测长尾**：跨页表、扫描件 OCR 后的超长块对 `rerank_max_tokens` 截断的触发概率未验证。
- **单价未核**：本文件只给 token 量级，金额一律以控制台为准（01 的既定原则）。
