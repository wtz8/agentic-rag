## 1. 在线链路数据结构

```python
@dataclass
class Candidate:
    """融合前的一路召回结果。

    `vector_score` / `bm25_score` 用 `float | None = None` 而非 `0.0`：
    `None` 只表示"这一路没产生分数"（`use_vector=False`，或该路调用失败），
    `0.0` 则既是合法的真分数又是"没走这一路"的默认值——两者无法区分，
    会让充分性判据的达标计数出现随机行为。判据一律写成 `is not None and score >= floor`。
    """
    chunk_id: str
    vector_score: float | None = None     # None = 向量路未产生分数
    vector_rank: int | None = None
    bm25_score: float | None = None       # 同上
    bm25_rank: int | None = None
    fused_score: float = 0.0
    rerank_score: float | None = None
    hit_routes: list[str] = field(default_factory=list) # 命中本候选的检索路径

@dataclass
class ScoredChunk:
    chunk: Chunk
    score: float
    rank: int
    hit_routes: list[str]

@dataclass
class Citation:
    index: int
    chunk_id: str
    source: str
    title_path: list[str]
    page: int | None
    quote: str
    score: float
```

## 2. 模块 `retrieval/query_transform.py`

### 职责

把用户原始问法转化为更适合检索的查询集合。

### 接口

```python
@dataclass
class TransformResult:
    queries: list[str]
    strategy: str # none | rewrite | decompose | hyde
    bm25_query: str # BM25 路专用 query；非 hyde 时 == 原 query

def transform_query(
    query: str,
    intent: str,
    llm: LLMProtocol,
    history: list[dict] | None = None,
    iteration: int = 0,
) -> TransformResult
```

### 四种策略

| 策略 | 触发条件 | 产出 |
| --- | --- | --- |
| `none` | `iteration == 0` 且 `intent=simple` 且 `skip_rewrite_for_simple=True` | 原 query |
| `rewrite` | `iteration == 0` 且 `intent=table_numeric`；**或 `iteration == 1`** | 1 条改写（`table_numeric` 侧重数值单位归一与指标名同义扩展，其余侧重指代消解与同义扩展） |
| `decompose` | `iteration == 0` 且 `intent=multi_hop` | 2–`max_sub_queries` 条**相互独立**的子查询 |
| `hyde` | **`iteration >= 2`** | 生成假设性文档段落作为检索输入 |

**升级规则只看 `iteration`，不看上一轮用了什么策略。**

`iteration=0` 用意图策略、`iteration=1` 用 `rewrite`、`iteration≥2` 用 `hyde`。
若把条件写成"上一轮已是 `rewrite`"，在 `multi_hop` 下首轮是 `decompose` 而非 `rewrite`，该条件永远不成立，第三次（hyde）也就永远轮不到。

`multi_hop` 在 `iteration == 0` 时命中 `decompose`（不是 `rewrite`），于是在 `iteration == 1` 时
"上一轮已是 rewrite"为假 → 落到 `rewrite` → 若此时预算已耗尽，
直接进入 `degrade`。**`hyde` 一次都轮不到**，而 07§4 那条"第 2 次升级到 hyde"的用例必然红。

这与计数器的问题同型：**测试绿、代码在，但没有任何一次执行会走到它。**

```python
def _pick_strategy(intent: str, iteration: int, cfg: Config) -> str:
    if iteration == 0:
        if intent == "simple" and cfg.agent.skip_rewrite_for_simple:
            return "none"
        if intent == "multi_hop":
            return "decompose"
        if intent == "table_numeric":
            return "rewrite"
        return "rewrite"
    if iteration == 1:
        return "rewrite" # 第一次重试：规范化表述 + 指代消解
    return "hyde" # 第二次重试：换一种检索范式，而不是再改一遍措辞
```

**为什么第一次重试统一用 `rewrite` 而不是沿用首轮策略**：首轮 `decompose` 没召回，
说明"拆成 2–4 条子查询"这个方向对这题不成立；此时再拆一次期望收益很低，
而改成单条规范化改写（把口语、缩写、指代换成语料里的说法）是成本最低的另一种假设。

**为什么第二次升级到 `hyde`**：前两次都是"换措辞"，它们共享同一个失效模式——
query 与语料的**用词**差太远，怎么改写都撞不上。HyDE 换的是范式：让模型先写一段
"假如语料里有答案，它大概长什么样"的文本，再用这段去检索，绕开用词差异。
**只有与前两次性质不同的动作才配叫"升级"**，第三次还用 rewrite 就只是重复。

**`max_retrieve_iterations` 取 3**，因为三级策略需要两次重试才能走完：

```
retrieve#1 (iter=1) ─不足─→ rewrite(iteration=1) ─→ retrieve#2 (iter=2)
                    ─不足─→ rewrite(iteration=2 → hyde) ─→ retrieve#3 (iter=3) ─→ degrade
```

把上限调成 1 或 2 是**合法的延迟取舍**（1 = 不反思；2 = 只到 rewrite 就耗尽预算），
但此时 `transform_strategy = "hyde"` 分支不可达，trace 里不会出现 hyde——
03§1 的启动校验只约束上界 ≤ 3，下界仍为 ≥ 1，不强制 3。

**`simple` 能否进入迭代 ≥ 1 由 `allow_reflect_for_simple` 决定，默认 `False`。** 02 §4.4 的路由图明确"simple 跳过改写与反思"，原 05 的图却让所有 intent 都能 `retry → rewrite`，两套状态机打架。现在统一为：默认 simple 走 `none` 且不进反思循环；把该开关打开即可作为消融变量观察"给简单问题也加反思，收益能否覆盖成本"。

### 关键实现

- **指代消解必须结合历史轮次**：多轮对话里的"它的上限是多少"没有历史上下文无法改写
- **子查询必须相互独立**：有依赖关系的子查询会强制串行，导致延迟叠加。提示词中显式约束这一点
- **迭代升级**：`iteration=1` 用 `rewrite`、`iteration≥2` 升级到 `hyde`，体现"策略升级"而非简单重复
- **多子查询要并发**：`decompose` 出的 2–4 条子查询之间必须并发执行（外层并发 query × 内层并发两路），否则多跳延迟会线性叠加。原文档只写了内层两路并发，外层漏了。并发编排见 §10.4
- **HyDE 段落只走向量路，BM25 路改用原 query**（第三轮复查 I3 补充）：假设文档是模型编出来的文本，拿它做字面精确匹配没有依据——编造的术语要么不存在于语料（零命中），要么恰好撞词（噪声命中），两者都会稀释 RRF 中真实命中的排名。因此 `strategy=hyde` 时：**向量路用假设文档段落，BM25 路仍用原始 query 分词检索**，两路照常融合。混合检索的互补性来自"同一真实意图的两种表达"，而不是来自编造文本
- **失败处理**：解析失败直接返回原 query，绝不让改写环节成为链路的单点故障

### 依赖

`providers.llm`、`config`

## 3. 模块 `retrieval/fusion.py`

### 接口

```python
def reciprocal_rank_fusion(
    rankings: list[list[str]], # 各路的 chunk_id 排名列表
    k: int = 60,
) -> list[tuple[str, float]]

def weighted_score_fusion(
    rankings: list[list[tuple[str, float]]],
    weights: list[float],
) -> list[tuple[str, float]]

def fuse(rankings, cfg: RetrievalConfig) -> list[tuple[str, float]]
```

### RRF 实现

```python
def reciprocal_rank_fusion(rankings, k=60):
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, chunk_id in enumerate(ranking, start=1):
            scores[chunk_id] = scores.get(chunk_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items, key=lambda x: x[1], reverse=True)
```

**为什么默认 RRF**：向量相似度 ∈ [0,1]，BM25 分数无上界且随语料长度分布漂移。直接加权相加等于让量纲大的一方支配排序；归一化又引入对异常值的敏感性。RRF 只依赖排名，天然免疫量纲问题。

`weighted_score_fusion` 保留为对照实现，用于消融实验中量化"RRF 比加权融合好多少"。

### 依赖

无（纯函数，便于单测）。

## 4. 模块 `retrieval/retriever.py`

### 接口

```python
class HybridRetriever:
    def __init__(self, cfg: Config, store: IndexStore, embedder: EmbeddingProtocol)
    def retrieve(self, queries: list[str], intent: str,
                 bm25_query: str | None = None) -> list[Candidate]
    def _vector_route(self, query: str, top_k: int) -> list[tuple[str, float]]
    def _bm25_route(self, query: str, top_k: int) -> list[tuple[str, float]]
```

### 执行流程

```
对每个 query：
  ├→ 线程池并发：
  │ ├→ _vector_route: embed(query) → vector_store.search(top_k)
  │ └→ _bm25_route: jieba 分词 → bm25.search(top_k)
  └→ 合并（多 query 时按 RRF 合并去重）
     └→ 取 top fusion_top_k → list[Candidate]
```

### 关键实现

- **两路必须并行**：串行会让召回耗时翻倍。用 `ThreadPoolExecutor(2)`
- **单路失败不阻断**：向量库不可用时仍返回 BM25 结果，反之亦然，并在 trace 中标记降级
- **表格加权**：intent=table_numeric 时，候选中 `block_type == "table"` 的 `fused_score *= table_boost`
- **元数据过滤下推**：intent=table_numeric 时可选只检索表格块。实现走
  `vector_store.search(..., flt={"block_type": "table"})`，**由 Qdrant 在 ANN 之前过滤**；
  BM25 路没有前置过滤机制，只能在打分后按 `block_type` 筛。
  **两条路的过滤位置天然不同，这个差异必须写进 trace**，否则 A2 消融里"过滤生效"到底作用于哪一层就说不清。
  作为消融变量，它必须能整体关掉（`filter_tables_only=False`）
- **HyDE 查询的两路分流**：`strategy=hyde` 的 query 只送 `_vector_route`；`_bm25_route` 改用原始 query（理由见 §2 关键实现，I3）
  - **接口落点**：原 query 通过 `TransformResult.bm25_query` 传下来，`retrieve(..., bm25_query=...)`。
    未传（`None`）时退化为"每条 query 各自走 BM25"，即 `decompose` 多子查询的原有行为不受影响。
    **只加一个 `TransformResult` 字段，不改 `queries` 的语义**——`queries` 始终是向量路的输入
- **`bm25_query` 与多 query 的优先级**：`bm25_query` 非空时，所有 query 的 BM25 路共用它（hyde 场景，queries 只有 1 条）

## 5. 模块 `agent/state.py`

```python
class AgentState(TypedDict, total=False):
    query: str
    history: list[dict]
    intent: str # simple | multi_hop | table_numeric | chitchat
    route_reason: str
    route_confidence: float # 路由置信度；与答案级 confidence 严格分离
    sub_queries: list[str]
    transform_strategy: str
    candidates: list[Candidate]
    sufficient: bool # 由 retrieve_node 判定并写入，条件函数只读
    reflect_strong: int # 达标候选数（向量余弦 ≥ floor），由 retrieve_node 写入
    sufficiency_basis: str # vector_score | candidate_count，降级时可见
    reflect_reason: str # query_expression | corpus_missing
    context: list[ScoredChunk]
    draft: str
    citations: list[Citation]
    retrieve_iterations: int # 已完成的检索轮数，自增在 retrieve_node
    generate_iterations: int # 已完成的生成次数，自增在 generate_node
    confidence: str # high | medium | low（答案级，唯一）
    answer: str
    claims: list[str] # verify_node 拆出的命题列表
    unsupported: list[int] # 无支撑命题下标
    faithfulness: float # 1 - len(unsupported)/len(claims)，代码按公式算
```

**`Tracer` 不放进 state。** 两个理由：

1. **与 checkpoint 冲突**。01 把"原生 checkpoint / 回放"列为选 LangGraph 的理由之一，而 `Tracer` 持有文件句柄与上下文管理器状态，不可序列化，塞进 state 后 checkpoint 会失败——两个设计目标互斥，必须二选一。
2. **语义不对**。trace 是旁路观测，不是 Agent 的业务状态。

走 LangGraph 官方的依赖注入通道：

```python
# 构建时传入 config，节点内从 RunnableConfig 取
graph.invoke(state, config={"configurable": {"ctx": ctx}})

def route_node(state: AgentState, config: RunnableConfig) -> dict:
    ctx: NodeContext = config["configurable"]["ctx"]
    ...
```

这样 state 保持纯数据（可序列化、可 checkpoint、可回放），tracer 仍按调用隔离，且 `query_id` 一次生成贯穿全程。

**迭代计数必须拆成两个。** 图里有两条独立的循环——检索侧 `retrieve → rewrite → retrieve` 和生成侧 `verify → generate → verify`。共用一个计数器会造成预算互相挤占：检索侧重试 2 次把额度用光后，生成侧重生成的机会直接归零，而这恰恰是最需要兜底的一环。

### 5.1 计数器语义与自增位置

**这条规则的隐含前提是"被回到的节点只在重入时才被走到"，而这个前提对 `rewrite_node` / `generate_node` 不成立——它们是首轮必经节点。**

后果在生成侧是致命的：若 `generate_node` 首轮就自增，那么 `verify` 判定 `generate_iterations < max_generate_iterations` 时左边已是 1、右边是 1，`1 < 1` 恒假。于是：

- `regenerate_on_unsupported=True` **永远触发不了重生成**
- B5 消融组（重生成开/关）两组的数字必然相同，实验直接失去意义
- SSE 的 `regenerate` 事件与前端"清空答案区"的逻辑成为死代码，而且**测试不会报错——它只是从不执行**

保留原规则里正确的部分（**绝不在条件函数里改状态**，这一点仍然成立），把自增挪到**执行该动作的节点**：

| 计数器 | 语义 | 自增位置 | 上限 | 耗尽后 |
| --- | --- | --- | --- | --- |
| `retrieve_iterations` | 已完成的**检索轮数**（首轮 = 1） | `retrieve_node` 末尾 | `max_retrieve_iterations = 3` | 带着已有证据进入生成；仅达标数 = 0 时走 `degrade_answer` |
| `generate_iterations` | 已完成的**生成次数**（首轮 = 1） | `generate_node` 末尾 | `max_generate_iterations = 2` | 标记 `confidence = "medium"` 并结束 |

三条由此确定的规则：

1. **自增写在"做这件事的节点"，不写在"被跳转到的节点"。** 检索一次就 +1、生成一次就 +1，计数与动作一一对应，不存在首轮/重入的歧义，也不需要靠 `state.candidates is not None` 这类痕迹去猜。
2. **两个上限的语义统一为"该动作最多执行几次"**，判据统一写成 `<`
   （`retrieve_iterations < 3` 允许第二、三轮；`generate_iterations < 2` 允许重生成一次）。
   `max_retrieve_iterations` 取 3 的理由见 §2——三级策略升级需要两次重检才能走完。
3. **`max_generate_iterations` 取 2**，语义是"生成总次数"（首生成 1 次 + 最多重生成 1 次）；取 1 会让重生成永远触发不了。

条件函数全程只读 state、不改 state、不推事件——见 §6.4 / §6.10。

## 6. 模块 `agent/nodes/`

### 节点构成（口径统一，原文档计数对不上）

| 类别 | 数量 | 成员 |
| --- | --- | --- |
| 主链路节点 | 6 | `route` / `rewrite` / `retrieve` / `rerank` / `generate` / `verify` |
| 终止应答节点 | 2 | `direct_answer` / `degrade_answer` |

共 **8 个节点 + 3 个条件函数**。

> 早期版本曾出现 `dispatch_by_intent` 指向 `direct_answer`、`is_sufficient` 指向 `degrade_answer`，
> 但这两个节点从未 `add_node`、也没有接口定义——图编译阶段会直接报 `NodeNotFound`（已由本节 6.8 / 6.9 补上）。

三条对条件函数的统一约束（**违反任何一条都属于破坏性变更**）：

1. 只读 state，**绝不修改 state**（自增一律在节点里，见 §5.1）。
2. 不调 LLM、不做 IO、不推 SSE 事件——判定所需的中间产物由上游节点写入 state。
3. 必须给出**完整的返回字面量集合**并与 `add_conditional_edges` 的映射键完全对应，且必须有一个无条件可达的回落分支。

> **签名约定**：本节所有节点与条件函数的签名统一为 `(state, config: RunnableConfig)`，
> 依赖从 `config["configurable"]["ctx"]` 取（04§7.1）。
> 因此下方伪代码里的 `cfg.xxx` 一律指 `ctx.cfg.xxx`，`llm` 指 `ctx.deps.llm_light` 或 `ctx.deps.llm_main`（按节点标注）。

### 6.3 `retrieve_node`

```python
def retrieve_node(state: AgentState, config: RunnableConfig) -> dict
# 输入: sub_queries, intent, retrieve_iterations, candidates(上一轮)
# 输出: candidates, reflect_strong, sufficient, reflect_reason,
# sufficiency_basis, retrieve_iterations(+1)
```

- 调用 `HybridRetriever.retrieve`，trace 记录各路命中数与耗时
- **在本节点内完成充分性预判**：算出 `reflect_strong` / `sufficient` / `reflect_reason` /
  `sufficiency_basis` 写入 state，并推送 SSE 的 `reflect` 事件。
  条件函数只做路由，见 §6.4。
- **在本节点末尾执行 `retrieve_iterations += 1`**，语义为"已完成的检索轮数"
- **跨轮候选必须 RRF 合并，不覆盖**：

  ```python
  prev: list[Candidate] = state.get("candidates") or []
  cur: list[Candidate] = retriever.retrieve(...)

  if not prev:
      candidates = cur # 首轮：没有可合并的
  else:
      # 两轮各自的 chunk_id 排名一起喂给 RRF；同一 chunk_id 取两轮中较高的 vector_score
      fused = reciprocal_rank_fusion([_rank(prev), _rank(cur)], k=r.rrf_k)
      candidates = _attach(cur + prev, fused)[: r.fusion_top_k]
  ```

  `_rank` 取 `[(c.chunk_id) for c in sorted(candidates, key=fused_score, reverse=True)]`；
  `_attach` 把融合分数写回 `Candidate.fused_score`，并按"同一 `chunk_id` 保留较高 `vector_score`"
  合并两轮的 `Candidate`。两者都是 `retrieval/fusion.py`（§3）里已有的纯函数的薄封装，
  **不新增算法**——跨轮合并与单轮两路合并用的是同一份 RRF 实现。

  **为什么不能覆盖**：若第二轮直接替换第一轮，"反思"就变成一次赌博——
  第二轮是换了策略（rewrite / hyde）的检索，它可能更好，也可能更差；
  一旦更差，第一轮已经召回的好候选就白白丢掉，反思循环的期望收益变成可正可负。
  **RRF 合并保证结果单调不退化**：第二轮只能往里加东西、把排名往上推，不会把首轮的命中挤掉。

  **这改变了 A4 消融测的是什么**，必须写清楚：A4 测的是
  "多轮检索 + 跨轮 RRF 合并"的收益，而不是"用第二轮结果替换第一轮"的收益。
  后者不是一种有意义的系统设计，只是把第一次检索的结果扔了。

  合并后 `vector_score` 的取值：同一 `chunk_id` 若两轮都命中，取**较高者**
  （更乐观地估计其相关性，避免第二轮分数低就把首轮的高分候选判成不达标）。
  trace 记录 `retrieve_rounds`（实际参与合并的轮数）与 `merged_from_prev`（上一轮候选中**进入最终 Top-K** 的条数）。

  ⚠️ `merged_from_prev` 的口径不能写成"合并结果里有多少条来自上一轮"——
  RRF 的输入就是 `[prev, cur]` 两个排名，合并结果必然包含 prev 的全部 id，
  那个计数**恒等于 `len(prev)`**。埋点一旦是常量，A4 就永远测不出东西，而且不会报错。

- **`reflect_reason` 的判定规则**：

  ```python
  # 纯规则，不调 LLM —— 充分性判定在本节点内完成，这里没有模型调用
  strong = [c for c in candidates if _reaches_floor(c, r)] # r = ctx.cfg.retrieval

  if r.use_vector:
      sufficiency_basis = "vector_score"
  else:
      sufficiency_basis = "candidate_count"
      strong = candidates # 降级：没有向量分数，用候选数判据

  if len(strong) == 0:
      reflect_reason = "corpus_missing" # 一条达标的都没有
  else:
      reflect_reason = "query_expression" # 有达标，但不足 min_candidates
  ```

  判 `corpus_missing` 的依据是**向量路对表述不敏感**：同一意思换说法，向量仍然相近。
  若所有候选的向量相似度都低于 `sufficiency_vector_floor`，说明语料里语义相关的东西一条都没有，
  换表述重试的期望收益很低。

- **与 `unanswerable` 机器校验的分工**（两者都判"语料里没有"，但层次不同）：

  | | 判据 | 发生位置 | 处置 |
  | --- | --- | --- | --- |
  | `corpus_missing` | 达标候选数 = 0 | `retrieve_node` | 走降级应答 |
  | unanswerable | rerank `relevance_score < unanswerable_rerank_floor`（0.35） | 评测 / 06§6.4 | 计入 unanswerable 指标 |

  前者是"召回来的一条都不相关"（粗筛层，向量余弦），后者是"精排后仍然不相关"（精筛层，cross-encoder）。
  **前者不能替代后者**——两层用的是不同模型、不同量纲，各自挡住不同性质的漏网。
  正常语料下绝大多数"语料无答案"走的是后者（粗筛阈值更松），这也是为什么 unanswerable 必须独立建指标。

- **本字段当前不驱动路由**：`is_sufficient`（§6.4）只读 `sufficient`，`reflect_reason` 目前只进 trace
  与 `degrade_answer_node` 的文案（§6.9）。这是刻意保留的余量，不是遗漏。

### 6.4 `is_sufficient`（条件边函数，不是节点）

```python
def is_sufficient(state: AgentState, config: RunnableConfig) -> Literal["sufficient", "retry", "degrade"]
# 纯读取 retrieve_node 写入的 sufficient / reflect_strong / retrieve_iterations
# 判定顺序（短路）：
# 1. sufficient is True → "sufficient"
# 2. reflect_strong == 0 → "degrade" # 一条达标都没有
# 3. 不允许反思（simple 且 not allow_reflect_for_simple） → "sufficient"
# 4. retrieve_iterations >= max_retrieve_iterations → "sufficient"
# 5. 否则 → "retry"
```

这是**循环边的终止条件**，也是成本控制的关键节点：迭代达上限后立即进入生成，绝不无限循环。

#### 为什么第 3 / 4 条是 `sufficient` 而不是 `degrade`

**"不重试"不等于"拒答"。**

```
# 原稿
# 2. intent == "simple" 且 not allow_reflect_for_simple → "degrade"
# 3. retrieve_iterations >= max_retrieve_iterations → "degrade"
```

走一遍最常见的场景就看出问题：**"XX 产品的单卡上限是多少？"** 语料里这个数字
只在一个表格的一行里出现过，达标候选 = 1 条。1 < `min_candidates`(3) → 第 2 条命中 →
`degrade_answer` → 用户看到"语料中未找到"。**但系统明明把答案握在手里。**

根因是把两个不同的问题混成了一个判据：

| 问题 | 该用什么判据 | 答"否"时的后果 |
| --- | --- | --- |
| **值不值得再检索一轮** | 达标数 < `min_candidates` | 再花一轮时间，可能召回更好 |
| **能不能回答** | 达标数 == 0 | 一条证据都没有，答了就是编 |

`min_candidates = 3` 是第一个问题的答案——它定的是"证据够不够多、要不要再找找"。
把它当成第二个问题的阈值，等于宣布"少于 3 条证据就必须闭嘴"，这对简单事实题是错的：
**一个数字、一个日期、一个条款编号，本来就只需要一条证据。**

现拆开：`reflect_strong == 0` 才拒答（第 2 条）；有证据但不足、且无法或不再重试时
（第 3 / 4 条）**照常生成**，把"证据偏少"交给 `verify_node` 的忠实度与 `confidence` 表达。

这不是放宽标准——**拒答是一种更重的判断，它应当要求更强的证据**；
"少"和"没有"是两件事，用同一个阈值表达它们，必然在某一头出错。

配套地，`AgentState` 增一个字段 `reflect_strong: int`（达标候选数），由 `retrieve_node` 写入。
`is_sufficient` 读它，而不是自己重算一遍——**判据只写一次**，与事件发送方归属是同一条规矩。

> **对"证据偏少"路径的置信度处置见 §6.7 的 `confidence` 完整定义。**
> 简单说：达标数 ∈ [1, `min_candidates`) 时，`confidence` 最高只能到 `medium`。
> 这样"少证据"这件事既没有触发拒答，也没有被悄悄当成"证据充分"。

**本函数不自己判定充分性。** 它是条件边函数，
按 §6 的三条约束它不能推事件——于是 04§10.2 的 SSE 协议里列了 `event: reflect` 却**没有任何发送方**。
职责划分：`retrieve_node` 算并写 state、推事件，本函数只做读取与路由。

**判定里不含 `min_top_score`。** 它默认是 `0.0`，而 RRF 分数恒为正（`1/(60+rank) ∈ (0.008, 0.0167]`），
所以 `最高分 >= 0.0` **恒真**——这一项从写下之日起就从未起过作用，充分性判定实际退化成只看候选数。
更根本的问题是量纲：RRF 分数不是相似度，它没有绝对含义，给它配一个绝对阈值是无意义的标定。

处置：

1. **充分性判据 = 向量相似度达标计数**，由 `retrieve_node` 计算并写入 `state.sufficient`：

   ```python
   strong = [c for c in candidates
             if c.vector_score is not None
             and c.vector_score >= cfg.sufficiency_vector_floor]
   sufficient = len(strong) >= cfg.min_candidates
   ```

   **为什么不是"只看候选数"**：`candidates` 是融合后的 Top-50，语料有数千 chunk 时它恒为 50，
   `50 >= min_candidates(3)` **恒成立** → `sufficient` 恒 True → `retry` 分支永不返回
   → rewrite→hyde 策略升级永不发生 → **整个检索侧反思能力一次都不会触发，A4 消融空转**。
   候选数回答的是"召回了多少条"，而充分性要回答的是"召回了多少条**真的相关**"——前者在语料够大时恒满，
   是个没有区分度的量。

2. `min_top_score` 从 `RetrievalConfig` **删除**。
3. 需要"相关性够不够"的绝对判据的场景只有一个——06§6.4 的 unanswerable 机器校验。
   它改用 **rerank 的 `relevance_score`**（`qwen3-rerank` 输出，∈ [0,1]，有绝对量纲），
   阈值是新配置 `RetrievalConfig.unanswerable_rerank_floor`（默认 0.35，**必须 > 0**）。

# cfg 来自 ctx.cfg；所有字段均已在 03§1 配置树声明
r = ctx.cfg.retrieval

if not r.use_vector: # 关掉向量路：没有余弦分数可用
    sufficient = len(candidates) >= r.min_candidates
    sufficiency_basis = "candidate_count" # 降级依据写进 trace，不要静默
else:
    strong = [c for c in candidates if _reaches_floor(c, r)]
    sufficient = len(strong) >= r.min_candidates
    sufficiency_basis = "vector_score"

def _reaches_floor(c: "Candidate", r: "RetrievalConfig") -> bool:
    """单路失败时 vector_score 为 None，此时不能算达标，也不能当成 0.0 参与比较。"""
    return c.vector_score is not None and c.vector_score >= r.sufficiency_vector_floor
```

**`vector_score` 用 `float | None` 而不是 `float = 0.0`。** 若默认值是 `0.0`，
它同时表示"没走向量路"和"余弦恰好为 0"，与判据里的 `is not None` 语义直接冲突：
关掉向量路时 0.0 会被当成真分数，达标数取决于 `floor` 的正负——行为随机。
类型必须是 `float | None = None`，`None` 只表示"这一路没产生分数"。

`sufficiency_basis` 进 `reflect` 事件的 payload。理由和本项目所有降级一样——**降级必须可见**，
否则消融报告里会出现"关掉向量后延迟翻倍"这种找不到原因的数字。

**阈值不能沿用设计初值，必须实测标定。** `sufficiency_vector_floor` 的设计初值是 0.35。
标定动作排在 **P3**（与检索指标、trace 埋点同一阶段，早于 P5 首跑消融），方法：度量
text-embedding-v4 在本语料上的相似度分离度（正样本 = 同父块兄弟块，负样本 = 跨文档随机对），
取 Youden's J 最大点，再按"宁可多检索一轮、不可误判充分"的方向微调——判据过松的代价是
反思永不触发，即充分性判据本身失去意义。

标定由 `scripts/calibrate_k1.py` 完成（离线、零 API 花费：直接复用索引里已落盘的向量）。
在本语料 33,477 条真实向量上，参考区间落在 **0.47–0.54**；同一分布下无关样本的
p75 ≈ 0.40 已高于现行 0.35，即**初值偏松而非偏紧**——偏松的后果是反思轮次被系统性压低。
config 默认值仍保留 0.35，理由是既有结果都在该值下取得，改默认值会让前后不可比；
**换语料、换 embedding 模型或重跑评测前，先重标一次。**

**这条判据与 `min_top_score` 的历史关系**：`min_top_score` 错在量纲；改看候选数又错在无区分度

### 6.5 `rerank_node`

```python
def rerank_node(state: AgentState, config: RunnableConfig) -> dict
# 输入: candidates（Top-50）
# 输出: context（Top-rerank_top_k 子块 → 去重回填后 ≤ max_context_chunks 个上下文块）
```

- **请求 `top_n = fusion_top_k`（50），本地只取前 `rerank_top_k`（5）条子块**：
  原文档只写"取 `rerank_top_k` 条"，没说请求时要多少——若按 5 去请求，第 6 名以后的排序结果根本不存在，
  去重后的"顺位补齐"就无从补起。**多排序不花钱**（08§3.2 实测：候选 10→50，延迟仅 +21%），
  但补齐需要池子，所以请求侧给足、本地侧截断。
- **父子块回填 + 去重**：按 `parent_id` 把命中子块映射到父块；
  **同一父块只保留一次**（保留其中 rerank 分数最高的那个子块的得分作为该父块的得分），
  去重后若不足 `max_context_chunks`，按 rerank 排名顺位取下一个**父块不同**的子块补齐。
- **`parent_id is None` 时用它自身**（`structural` 策略产出的块没有父块，见 03§0.1），
  这条分支让 B2 消融的两组走同一段回填代码，而不是在策略里分叉
- rerank 失败则直接用 RRF 排序结果，不阻断
- trace 记录重排前后的 rank 变化与 `dedup_collapsed`（被折叠掉的同源子块数），UI 可展示"精排把第 12 名提到了第 2 名"

#### 为什么必须去重

Top-5 子块里出现 3 条同属一个父块，不是边缘情况——同一节内的相邻段落本就高度相关，混合检索又倾向于扎堆命中。
不去重就会把**同一段 1024 token 的父块重复送三遍**给生成模型：

- 白吃掉约 2 份 × 1k ≈ 2k 输入 token（实测单次生成输入约 4k，即多花 50%）
- 更糟的是稀释：同一内容占掉 3/5 的上下文槽位，真正互补的证据只剩 2 个位置

这条规则也定死了两个容易混淆的配置的边界：

| 配置 | 语义 | 默认 |
| --- | --- | --- |
| `rerank_top_k` | 重排后保留多少**子块** | 5 |
| `max_context_chunks` | 去重回填后送生成的**上下文块**上限 | 5 |

两者默认相等是巧合而非等价——去重后上下文块数只会 ≤ 重排子块数，所以启动校验要求 `max_context_chunks ≤ rerank_top_k`。

**`rerank_top_k` 必须真的被用上**：它是"回填与顺位补齐的池子深度"，
实现里要显式按 `min(len(ordered), rerank_top_k)` 截断。若只靠 `max_context_chunks` 截断，
因为校验保证了 `max_context_chunks ≤ rerank_top_k`，结果看起来等价，
但**单独调 `rerank_top_k` 就变成死配置**（静默无效）——trace 里记 `pool_depth` 以便核对。

**`retrieve_rounds` 与 `sub_query_count` 是两个量**：前者是**实际参与本次跨轮合并的轮数**（1 或 2），
后者是子查询条数（decompose 下可能是 3、5）。`retrieve_rounds` 不能取 `len(diag["durations"])`——那是子查询条数，
那是子查询条数，两者混用会让 04§9.4 的 A4（跨轮合并）归因彻底错位。

### 6.7 `verify_node`

```python
def verify_node(state: AgentState, config: RunnableConfig) -> dict
# 输入: draft, context, generate_iterations, reflect_strong
# 输出: confidence, faithfulness, claims, unsupported
```

**本节点是 2 次 LLM 调用，不是 1 次**——这一点被 02 §7 与 §12 的延迟表漏算过：

| 步 | 模板（05§1.x） | 模型 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| ① 命题拆分 | `claim_extract` | `llm_light` | 去角标后的答案正文 | `{"claims": [...]}` |
| ② 逐条支持判定 | `claim_verify` | `llm_light` | `claims` + 生成时用的 context | `{"unsupported": [下标]}` |

流程：

- 把 draft 拆成**原子命题**列表（一句话一条事实）
- 逐条判断该命题是否被 context 支持
- **`faithfulness = 1 - len(unsupported)/len(claims)`，由代码按公式算，不采信模型自报的数字**（05§1.7）
- 低于 `faithfulness_threshold` 且 `generate_iterations < max_generate_iterations` 且 `regenerate_on_unsupported=True` → 由 `need_regenerate` 路由回 `generate`
- 已达上限或开关关闭 → 仍输出答案，但 `confidence` 降为 `medium`，UI 显示低置信提示
- 任一步调用失败 → `confidence = "medium"`，**不阻断答案输出**

**`confidence` 的完整定义。**
`confidence` 是**答案级**的唯一置信度字段，
由 `verify_node` 在本节点末尾统一计算，其他任何节点都不得写它：

```python
def _decide_confidence(state: AgentState, cfg: Config) -> str:
    if state.get("degraded"): # 走了 degrade_answer
        return "low"
    if state.get("verify_failed"): # verify 调用失败，无判定结果
        return "medium"
    if state.get("faithfulness", 1.0) < cfg.generation.faithfulness_threshold:
        return "medium" # 有据可依，但部分命题无支撑
    if state.get("reflect_strong", 0) < cfg.retrieval.min_candidates:
        return "medium" # 证据偏少
    return "high"
```

四条分支覆盖了全部终止出口，`done` 事件里的 `confidence` 因此**总有确定取值**：

| 出口 | `confidence` | 含义 |
| --- | --- | --- |
| `degrade_answer` | `low` | 一条达标证据都没有，系统选择不编 |
| verify 调用失败 | `medium` | 无法给出判定，如实标注"未校验" |
| faithfulness 未达标 | `medium` | 答案成立，但有命题未找到出处 |
| 达标证据 < `min_candidates` | `medium` | 答案成立，但支撑偏薄 |
| 其余 | `high` | 证据足且命题均有出处 |

**为什么按命题拆分**：给整段答案打一个总分无法定位是哪一句在编。按命题拆分后能明确指出"第三句无出处"，这对企业场景的信任建立至关重要。

**`regenerate_on_unsupported` 默认关闭。** 流式场景下 token 已经推给用户，此时触发重生成意味着用户会看到答案被整体重写一次，观感很差。默认行为是**只标记不重生成**：答案照常输出，附低置信提示与"以下命题未找到出处"清单——把判断权交给人，这比偷偷重写一遍更符合企业场景的信任逻辑。该开关在评测时打开，用于量化重生成的收益。

### 6.8 `direct_answer_node`

```python
def direct_answer_node(state: AgentState, config: RunnableConfig) -> dict
# 输入: query, intent, route_reason
# 输出: answer, confidence="high"
```

`intent == "chitchat"` 或判定为越界问题时的出口。**不检索、不调生成模型**，直接用固定话术说明能力边界并引导用户提出文档相关问题。

设计要点：

- 这是**成本控制的第一道闸门**——闲聊与越界问题在企业助手里占比不低，为它们付一次 embedding + rerank + 生成毫无意义。

- trace 记录 `intent=chitchat` 与 `route_reason`，UI 展示"系统判断这不是文档问题，未启动检索"。

### 6.9 `degrade_answer_node`

```python
def degrade_answer_node(state: AgentState, config: RunnableConfig) -> dict
# 输入: query, candidates, retrieve_iterations, reflect_reason, reflect_strong
# 输出: answer, confidence="low"
```

**唯一入口条件：`reflect_strong == 0`（一条达标候选都没有）。**

注意不是"迭代耗尽"——预算耗尽但手里有证据时，走的是生成而不是本节点（§6.4 第 4 条）。
拒答是比"少证据地回答"更重的判断，它应当要求更强的证据：
**一条都没有才叫"语料里没有"，只有 1–2 条叫"证据偏薄"，后者应当照常回答并如实标注置信度。**

设计要点：

- **输出必须是诚实的"未找到"，绝不让模型基于空上下文硬编。** 这是 02 §5.2 的核心取向，本节点是它在代码里的落点。
- 若 `candidates` 非空（但全部未达 `sufficiency_vector_floor`），给出"找到以下近似内容，但不确定是否回答了你的问题"并附上候选片段——**比直接说没有更有用，也比装作知道更诚实**。
- `reflect_reason` 用于选文案：
  - `corpus_missing`（达标数 = 0）→ "语料中未找到相关信息"
  - `query_expression`（达标数 ≥ 1 但 < `min_candidates`，且不重试）→ 本节点实际不会被走到，该文案由 `verify_node` 的 `confidence="medium"` 承担
- 与 `direct_answer_node` 的区别：前者是"不该检索"，后者是"检索了但一条相关的都没有"。两者都不调生成模型。
- trace 记录 `reflect_strong` / `sufficiency_basis` / `retrieve_iterations`，便于事后判断"这次拒答是因为阈值太严还是语料真的没有"

### 6.10 `dispatch_by_intent`

```python
def dispatch_by_intent(state: AgentState, config: RunnableConfig) -> Literal["chitchat", "simple", "multi_hop", "table_numeric"]
# 1. intent 为空 / 为 None / 不在 cfg.agent.intents 内 → "simple"（回落分支，无条件可达）
# 2. 否则返回 intent 本身
```

- **回落选 `simple` 而非 `chitchat`**：路由失败的代价不对称。误判成 chitchat 会把一个本该检索的问题直接挡在门外（用户得到"这不是文档问题"）；误判成 simple 只是多花一次检索。这与 05§1.1 里 `route` 模板的回落取向一致。
- 不修改 state，不推事件（`route_node` 已经推过 `route` 事件）。
- **它是图里第一个被执行的分支函数**，也是唯一一个"意图决定整条路径"的地方——02 §4.4 的自适应路由在代码里的落点就是它。

### 6.11 `need_regenerate`（条件边函数）

```python
def need_regenerate(state: AgentState, config: RunnableConfig) -> Literal["accept", "regenerate", "low_confidence"]
# 判定顺序：
# 1. faithfulness >= cfg.generation.faithfulness_threshold → "accept"
# 2. not cfg.generation.regenerate_on_unsupported → "low_confidence"（默认路径）
# 3. generate_iterations >= cfg.agent.max_generate_iterations → "low_confidence"
# 4. 否则 → "regenerate"
```

与 §6.4 同为纯读取函数：`faithfulness` 由 `verify_node` 写入 state，`generate_iterations` 由 `generate_node` 写入。

**默认路径是 2 而不是 4**（`regenerate_on_unsupported=False`）：流式下 token 已推给用户，重写一遍的观感很差。
`regenerate` 分支只在开关显式打开时可达，UI 必须实现 `regenerate` 事件的"清空答案区"语义才允许打开（04§10.2）。

### 图定义

```python
@dataclass
class GraphDeps:
    llm_light: LLMProtocol # 路由 / 改写 / 校验
    llm_main: LLMProtocol # 终答生成
    retriever: "HybridRetriever"
    reranker: RerankProtocol
    store: "IndexStore" # rerank 节点回填父块时用

@dataclass
class NodeContext: # 每次 invoke 构造一次，放进 configurable
    cfg: Config
    deps: GraphDeps
    tracer: "Tracer"
    query_id: str

def build_graph(cfg: Config, deps: GraphDeps) -> CompiledGraph:
    g = StateGraph(AgentState)

    # 注册的是函数本身，不用 partial —— 原因见下方"依赖注入"
    # 主链路 6 个
    g.add_node("route", route_node)
    g.add_node("rewrite", rewrite_node)
    g.add_node("retrieve", retrieve_node)
    g.add_node("rerank", rerank_node)
    g.add_node("generate", generate_node)
    g.add_node("verify", verify_node)
    # 终止应答 2 个 —— 早期版本引用了却从未注册，图编译会失败
    g.add_node("direct_answer", direct_answer_node)
    g.add_node("degrade_answer", degrade_answer_node)

    g.set_entry_point("route")

    # 路由分流
    g.add_conditional_edges("route", dispatch_by_intent, {
        "chitchat": "direct_answer",
        "simple": "rewrite",
        "multi_hop": "rewrite",
        "table_numeric": "rewrite",
    })

    g.add_edge("rewrite", "retrieve")

    # 反思循环：这里的条件边就是成本控制的核心
    g.add_conditional_edges("retrieve", is_sufficient, {
        "sufficient": "rerank",
        "retry": "rewrite", # retrieve_iterations += 1 在 retrieve_node 内完成
        "degrade": "degrade_answer",
    })

    g.add_edge("rerank", "generate")
    g.add_edge("generate", "verify")

    g.add_conditional_edges("verify", need_regenerate, {
        "accept": END,
        "regenerate": "generate", # generate_iterations += 1 在 generate_node 内完成
        "low_confidence": END,
    })

    g.add_edge("direct_answer", END)
    g.add_edge("degrade_answer", END)

    return g.compile
```

调用侧构造 `NodeContext` 注入 `configurable`，**不进 state**：

```python
ctx = NodeContext(cfg=cfg, deps=deps, tracer=tracer, query_id=qid)
graph.invoke(
    {"query": q, "history": hist, "retrieve_iterations": 0, "generate_iterations": 0},
    config={"configurable": {"ctx": ctx}},
)
```

### 7.1 为什么不能用 `partial` 注入依赖

原图定义写的是 `g.add_node("route", partial(route_node, cfg=cfg, llm=deps.llm))`，而 §5 又要求节点写成
`def route_node(state, config: RunnableConfig)` 以便从 `config["configurable"]` 取 tracer。**这两件事互相排斥。**

`inspect.signature` 对 `functools.partial` 的处理是**把已绑定的参数从签名里移除**：

```python
def route_node(state, cfg, llm): ...
inspect.signature(partial(route_node, cfg=cfg, llm=llm)) # → (state) ← config 没了
```

LangGraph 正是靠检查这个签名里有没有第二个位置参数来决定"要不要把 `RunnableConfig` 传进去"。
签名里没有 → 它只会调用 `func(state)` → 节点函数体里的 `config` 取不到值 → **trace 注入静默失效**。

这类故障特别难查：它报的不是"tracer 未定义"，就是 trace 一直为空、或者某个参数位置错位成 `cfg` 拿到了 config 对象。

**定案：节点与条件函数统一签名 `(state, config)`，一切依赖从 `config["configurable"]["ctx"]` 取，不使用 `partial`。**
`cfg` 也在 ctx 里，于是"配置"和"运行期依赖"走同一条注入通道，节点签名全项目只有一种。

**判据只写一次。** 凡是同时被节点、条件函数、SSE 事件需要的量
（`sufficient`、`reflect_strong`、`sufficiency_basis`、`faithfulness`、`need_regenerate`），
一律由**产生它的那个节点**算出来写进 state，其余各方只读：

```python
# agent/conditions.py —— 与节点共用同一份判据实现，不各写一遍
def should_regenerate(state: AgentState, cfg: Config) -> bool:
    g = cfg.generation
    return (
        state.get("faithfulness", 1.0) < g.faithfulness_threshold
        and g.regenerate_on_unsupported
        and state.get("generate_iterations", 0) < cfg.agent.max_generate_iterations
    )
```

这条规矩不是风格偏好：`need_regenerate` 若由 `verify_node` 自己再实现一遍三重判据，
那么改判据时**条件函数与节点必然漂移**——表现为"UI 上显示了 `regenerate` 事件，但图其实走了 END"
这类极难定位的不一致。

### 循环边说明

图中存在**两条循环**，各有独立计数器：

1. `retrieve → rewrite → retrieve`：检索侧反思（CRAG 思路），由 `retrieve_iterations` 与 `max_retrieve_iterations` 保护
2. `verify → generate → verify`：生成侧反思（Self-RAG 思路），由 `generate_iterations` 与 `max_generate_iterations` 保护

计数自增写在**执行该动作的节点**里（`retrieve_node` / `generate_node`），语义是"该动作已执行几次"，
而不是"被回到的节点"——后者是首轮必经节点，会让生成侧重生成永远触发不了。
条件函数只读取计数，绝不修改。

### 图可视化

`g.get_graph.draw_mermaid` 导出，供文档与 UI 展示。

**"仅 BM25"（A0′）当前不在矩阵里。** `RetrievalConfig.use_vector` 已声明（03§1），
与 `use_bm25` 对称，用于两种场景：① 后续想补 `A0′ = 仅 BM25` 与 A0 对照，
量化"向量路"的边际收益；② 向量路 API 故障时的运行期降级。
**关掉它必须同步触发充分性判据降级**（达标计数 → 候选数），否则每次查询都会跑满 3 轮检索。

**运行时机补充，与 06§7、02 §9 一致）**：A0–A4 的**首次**运行安排在 **P5**（生成链路打通后），用 mini 评测集（20–25 条）跑，而不是等 P8 的完整集。

理由不是"早跑早省心"，而是**消融的结论必须有机会改变设计**。A0–A4 是本项目最核心的说服点；若等到 P8 才第一次跑出"rerank 收益不显著"或"反思循环的成本高于收益"，此时架构与提示词都已冻结，唯一能做的只是把数字写进报告——实验就从"用来做决定"退化成"用来填数字"。

P8 用完整集（60–100 条）复跑一次。两次结论的对比本身也是一份有价值的结果：**mini 集上的排序能否在完整集上复现**，直接说明了 25 条样本得出的结论有多大可信度。若复现不了，报告里应当写明，而不是只报完整集那一次。

#### 差值显著性判据（

mini 集 20–25 条的规模下，1–2 条之差就是 4–8 个百分点，而 LLM judge 本身有波动。
没有判据的话，A0–A4 的排序可能只是采样噪声，消融从"用来做决定"退化成"用来讲故事"。

**定案：两级判据。第一级必报，第二级用于中间地带。**

**第一级 · 逐条配对比分（必报）**

对每一条评测题比较变体 X 与 Y 的指标——`recall@K` 取该条是否命中（0/1），
`faithfulness` 取该条的忠实度分数——记录 win / loss / tie（差值绝对值 < 0.02 记为 tie）：

```
net_win_rate = (win - loss) / N
```

| `|net_win_rate|` | 结论 |
| --- | --- |
| ≥ 0.20 且符号检验 p < 0.05 | **有差异**，可据此下结论 |
| < 0.10 | **噪声**，不论总分差多少，一律不写进结论 |
| 中间地带 | **弱证据**，只陈述数字，不下因果判断 |

符号检验临界值（双侧 p < 0.05）：**N = 20 需 ≥ 15 条方向一致；N = 25 需 ≥ 18 条。**

**为什么是符号检验而不是 t 检验**：25 条样本、指标是 0/1 或有界分数，正态假设不成立。
符号检验只要求配对独立，且能直接给出"在多少条题上赢"这个可解释的量——对消融报告来说，
这句话比一个 p 值更有用。

**第二级 · 重复跑估计方差（用于中间地带）**

同一配置重复跑 3 次，报 `均值 ± 标准差`；若两组的 `均值 ± 2σ` 区间重叠，判定不可区分。

**前置动作：先测仪器精度，再测样品。** 正式消融前先跑一次"同配置重复 3 次"的空转，
得到 judge 自身的方差 `σ_judge`；**任何小于 `2·σ_judge` 的组间差值直接判为噪声**，
不再进入第一级判据。这一步约 20 分钟，省不得——不知道尺子精度就去量东西，
量出来的数字没有任何意义。

**对报告的要求**：每一条"A 比 B 好"的结论，必须同时给出 `net_win_rate` 与 N。
只报总分差的结论不得写进摘要。

### 9.5 Mock 模式下的评测有效性（必须写进报告，不得含糊带过）

项目最核心的说服点是消融实验，而最可能跑起来的环境恰恰是 Mock 模式——但 Mock 下这个实验的结论**天然不可信**：

| 组件 | 真实模式 | Mock 模式 |
| --- | --- | --- |
| 向量路 | 语义相似 | 字符 3-gram 哈希投影 ≈ 字面重合 |
| BM25 路 | 字面精确 + IDF 加权 | 字面精确 |
| Rerank | query-doc 联合编码 | 字面重合度 |

**三路在 Mock 下高度同构**，A1（混合检索）的互补增益会被严重低估，A2（rerank）的增益几乎全是噪声。若不声明，等于拿一个失真数字去支撑核心结论，一复核就露馅。

因此定三条硬规矩：

1. `EvalReport` 必须携带 `provider_mode: "mock" | "dashscope"` 与 `retrieval_signature`，**没有这两项的报告不得对外引用**。
2. Mock 模式下**只公布工程性指标**（各阶段延迟、召回路径连通性、token 计数、引用链路完整度、探针通过率），**不公布检索质量结论**（Recall / NDCG / 忠实度的绝对值与增益）。
3. Mock 模式的定位是**验证链路跑得通、UI 演示得起来**，不是验证检索做得好。这一点要在 README 与评测报告顶部写明。

若最终拿不到 API Key，诚实做法是：评测报告改为"链路验证报告"，把 A0→A4 的结论明确标为"待真实模型验证"，而不是硬给出一组漂亮数字。

> **状态**：Key 已取得并实测连通（见 `08-实测基线.md`），但**本节三条硬规矩依然有效**。因为评审者 clone 本仓库时通常没有自己的 Key，Mock 仍会是最常见的运行方式——这条规矩针对的是"别人跑这个项目时会不会得出错误结论"，与本地是否有 Key 无关。

### 9.6 输出

- `eval/results/{timestamp}.json`：原始逐条结果
- `eval/results/summary.md`：指标对比表 + 延迟 P50/P95 + token 成本

**报告必须携带的存证字段**（三条合并起来才能回答"这份数字是在什么条件下跑出来的"）：

| 字段 | 内容 | 为什么必须有 |
| --- | --- | --- |
| `provider_mode` | `mock` / `dashscope` | 见 §9.5，Mock 下的检索质量结论不可引用 |
| `retrieval_signature` | 检索配置指纹 | 见 02 §5.4，否则消融组之间无法区分 |
| `models_actual` | **响应体返回的模型名**（如 `qwen3.7-plus`） | 请求值可能是别名（如 `qwen-plus`），实测别名与固定版本同时在架，**别名会静默漂移**。若两次消融跑在不同底层模型上而报告只记了请求值，差异归因就是错的（见 `08-实测基线.md` §1.1） |
| `user_dict_sha256` | 分词词典文件摘要（无词典时为 `none`） | 词典直接改变 jieba 分词 → 改变 BM25 召回集，但它**不在配置树里**，字段级指纹结构上不可能发现它 |

`models_actual` 取自每次响应体的 `model` 字段，而非配置树的请求值——这两者可能不同，且**不同之处恰恰是关键信息**。

**`unanswerable` 类型必须包含**：语料中不存在答案的问题，用于检验系统会不会硬编。这是区分"真 RAG"和"会编的 RAG"的关键测试。

### 9.7 `EvalReport` 与 `Pipeline` 的契约

```python
# eval/report.py
@dataclass
class VariantResult:
    variant: str # A0 / A1 / ... / B5
    retrieval_signature: str
    metrics: dict[str, float] # recall@5 / recall@20 / mrr / ndcg@5 / hit_rate

    latency: dict[str, float] # p50 / p95（到首字、到就绪分别记）

@dataclass
class EvalReport:
    created_at: str
    provider_mode: str # mock | dashscope —— 必带
    retrieval_signature: str # 整体指纹 —— 必带
    models_actual: dict[str, str] # 响应体里的实际模型名 —— 必带

    prompt_schema_versions: dict[str, int] # 05§0.2
    index_version: str
    variants: list[VariantResult]
    unresolved_anchors: list[tuple[str, object]] # (question, 锚点)；解析失败的锚点记在这里
    case_count: int
    notes: str

# pipeline.py —— 在线链路的单一入口，server 与 eval 共用同一条执行路径

@dataclass
class Event:                          # SSE 事件对象
    type: str # cache_hit | route | rewrite | retrieve | reflect |
                                      # rerank | token | citation | verify | regenerate |
                                      # degrade | done
    data: dict

    def to_sse(self) -> str:
        return f"event: {self.type}\ndata: {json.dumps(self.data, ensure_ascii=False)}\n\n"

@dataclass
class RunResult:                      # Pipeline 的返回值
    query_id: str
    query: str
    intent: str
    answer: str
    confidence: str # high | medium | low，取值见 §6.7 的完整定义
    citations: list[Citation]
    context: list[ScoredChunk]
    claims: list[str]
    unsupported: list[int]
    faithfulness: float
    retrieve_iterations: int
    generate_iterations: int
    weak_evidence: bool = False # 达标证据 ∈ [1, min_candidates)
    degraded: bool = False # 走了 degrade_answer
    cache_hit: bool = False
    trace_id: str = ""
    latency_ms: dict[str, float] = field(default_factory=dict)

class Pipeline:
    def __init__(self, cfg: Config, deps: GraphDeps, store: "IndexStore")
    def run(self, query: str, history: list[dict] | None = None) -> RunResult
    def run_stream(self, query: str, history: list[dict] | None = None) -> Iterator[Event]
```

`Event` 与 `RunResult` 补齐后，`04§10.2` 的协议、`07§4` 的集成测试断言、
`Pipeline` 的返回类型三者指向同一组具体字段——不再有"协议里写了、代码里没定义"的悬空引用。

**`Pipeline` 必须是 server 与 eval 的唯一入口**（04§10.4 的 SSE handler 与 §9.3 的 `run_suite` 都调它）。
这不是为了整洁：如果评测跑的是一条自己组装的链路、UI 跑的是另一条，那么"评测数字"和"演示效果"之间
就没有任何保证它们描述的是同一个系统——而这恰恰是最经不起复核的地方。

### 10.2 SSE 事件协议

不只是推 token，而是推**结构化事件**：

```
event: cache_hit data: {"cached_at": "...", "source_query_id": "..."}
event: route data: {"intent": "multi_hop", "reason": "..."}
event: rewrite data: {"queries": ["...", "..."], "strategy": "decompose"}
event: retrieve data: {"vector_hits": 50, "bm25_hits": 47, "fused": 50}
event: rerank data: {"changes": [{"from": 12, "to": 2}], "top": 5, "dedup_collapsed": 1}
event: reflect data: {"iteration": 1, "sufficient": false, "reason": "query_expression",
                        "strong": 1, "min_candidates": 3,
                        "sufficiency_basis": "vector_score"}
event: token data: {"text": "根据..."}
event: citation data: {"index": 1, "source": "...", "page": 12, "quote": "..."}
event: verify data: {"claims": 6, "unsupported": 1, "faithfulness": 0.83}
event: regenerate data: {"iteration": 1, "reason": "命题 3 无出处"} # 前端必须清空答案区
event: degrade data: {"reason": "corpus_missing", "candidates": 2}

                        "weak_evidence": false}
```

前端据此渲染 Agent 决策时间线，这是本作品最直观的展示点。

#### 事件 → 发送方对照表

每个事件有且只有一个发送方、且发送方只能是节点——这条规矩决定了
三个事件都必须有明确发送方：`reflect` 由 `retrieve_node` 发出，`verify` 由 `verify_node` 发出，`regenerate` 由 `verify_node` 发出。

不能顺手把它派给 `verify_node` 了事——那样做等于把 `need_regenerate` 的三重判据
（忠实度未达标 ∧ 开关打开 ∧ 生成预算未耗尽）在节点里再实现一遍，
日后改判据时条件函数与事件必然漂移，表现为"UI 上跳了 regenerate，图其实走了 END"。

定案：**判据实现只存在一份**，放在 `agent/conditions.py`，节点与条件函数共用：

```python
def should_regenerate(state: AgentState, cfg: Config) -> bool:
    g = cfg.generation
    return (
        state.get("faithfulness", 1.0) < g.faithfulness_threshold
        and g.regenerate_on_unsupported
        and state.get("generate_iterations", 0) < cfg.agent.max_generate_iterations
    )
```

- `need_regenerate(state, cfg)` 调它，返回路由字面量
- `verify_node` 也调它，命中则在返回前推一个 `regenerate` 事件
- **事件与路由因此由同一份代码决定，不可能不一致**

| 事件 | 唯一发送方 | 备注 |
| --- | --- | --- |
| `cache_hit` | `Pipeline.run_stream`（图执行前，I4） | 唯一一个非节点发送方，因为此时图尚未执行 |
| `route` | `route_node` | 含 `route_confidence` |
| `rewrite` | `rewrite_node` | 含 `strategy`，取值见 §2 |
| `retrieve` | `retrieve_node` | 各路命中数 + 耗时 |
| `reflect` | `retrieve_node` | 含 `strong` / `min_candidates` / `sufficiency_basis` |
| `rerank` | `rerank_node` | 含 `dedup_collapsed` |
| `token` | `generate_node` | 流式 |
| `citation` | `generate_node` | 逐条 |
| `verify` | `verify_node` | 含 `claims` / `unsupported` / `faithfulness` |
| `regenerate` | `verify_node` | **判据共用 `should_regenerate`，不另写一份** |
| `degrade` | `degrade_answer_node` | |
| `done` | `Pipeline.run_stream` | **必须在 trace 落盘之后** |

> `cache_hit` 与 `done` 由 Pipeline 发送而非节点，理由是它们描述的是**图的边界之外**的事件
> （缓存命中发生在图执行之前、结束发生在图执行之后）。这两个例外要在测试里显式列出，
> 07§4 的"事件有发送方"用例据此断言：除这两者外，每个事件类型必须能追溯到唯一一个节点。

**每个事件必须有且只有一个发送方，而发送方只能是节点**。
原协议里的 `reflect` 就是反例：充分性判定被明确为条件边函数（02 §4.3 / §6.4），
条件函数不注册进图、不持有 `configurable`、也拿不到 SSE 队列——它在物理上无法推事件。
职责划分：**`retrieve_node` 算 `sufficient`、推 `reflect` 事件、并把结果写进 state；条件函数只读**（§6.3 / §6.4）。
`verify` 事件同样由 `verify_node` 发出，与 trace 的 `verify` 步一一对应。

**`regenerate` 事件解决"流式下重写"的协议缺口。** `verify` 可以触发重生成，而 token 已经流式推给用户，协议里必须有"撤回"语义，否则前端会把两段答案拼在一起。规定：前端收到 `regenerate` 后**清空当前答案区**并展示 `reason`（如"第 3 句未找到出处，正在重写"）。

由于 `regenerate_on_unsupported` 默认关闭，默认路径不会出现这个体验；开启后前端必须有对应处理，否则不要开。

`degrade` 事件用于 `degrade_answer_node`，前端不渲染答案正文，只展示"未在语料中找到"及近似候选（若有）。

**`cache_hit` 事件与命中缓存时的事件序列**（第三轮复查 I4 补充，原协议缺这条路径）：
result 缓存的命中检查发生在 **pipeline 入口、图执行之前**（02 §5.4 的"0 次模型调用"）。
命中时图根本不执行，因此不可能有 `route` / `retrieve` 等节点事件——原协议没有定义这条路径，
前端时间线会永远停在"等待"上。定案：

- 事件序列：`cache_hit` → `token`（**完整答案一条推完**，不逐字重放，无意义地模拟打字是欺骗）→ `citation`（逐条）→ `done`
- 前端时间线只渲染**一个**"缓存命中"节点，展示 `cached_at` 与 `source_query_id`，不伪造检索过程
- **命中也要写一条 trace**（`cache_hit=true` + 缓存键指纹）：否则评测统计和线上排查时，这次查询会凭空消失——
  "缓存命中率"这个指标本身也依赖这条记录
- `done` 规则不变：仍在这条简版 trace 落盘之后推送

**`done` 事件必须在 trace 落盘之后推送**——否则用户立刻点进 `/api/trace/{id}` 会查不到。即：图执行结束 → `tracer.finalize` → `tracer.write` → 推 `done`。

### 10.4 并发与异步模型

**问题**：SSE endpoint 必须是 `async def`（否则 FastAPI 会占用线程池、无法并发），而 LangGraph 图是**同步**的（内部是 httpx 同步调用 + jieba + 线程池）。在 `async def` 里直接调用同步图，会**阻塞 event loop**，导致所有请求串行——01 §9 宣称的"并发友好"就成了空话。

**方案**：线程池执行图 + 队列桥接 token + 信号量限流。

```python
@app.post("/api/ask")
async def ask(req: AskRequest):
    async with SEMAPHORE: # 并发闸门，见 ServerConfig.max_concurrent_queries
        q: asyncio.Queue = asyncio.Queue
        loop = asyncio.get_running_loop

        def _run: # 在线程池里跑同步图
            try:
                for ev in pipeline.run_stream(req.query, req.history):
                    loop.call_soon_threadsafe(q.put_nowait, ev) # 跨线程安全投递
            finally:
                loop.call_soon_threadsafe(q.put_nowait, _SENTINEL)

        task = loop.run_in_executor(_POOL, _run)
        while True:
            ev = await q.get
            if ev is _SENTINEL:
                break
            yield _sse(ev) # 标准 SSE 格式
        await task
```

四条约定：

1. **`Semaphore` 必须有**。线程池大小有限（默认 4），超出的请求若不排队会在线程池里堆积，表现为"第 5 个请求卡死而不是排队"。宁可让前端转圈，也不要静默挂起。
2. **跨线程投递只能用 `call_soon_threadsafe`**，直接在子线程 `await q.put` 会抛错。
3. **这是 demo 级的取舍，不是生产方案。** 生产环境应把 provider 层换成 `httpx.AsyncClient`、图改为 `ainvoke` 全链路异步，去掉线程池这一层。因为这个局限写进文档，是因为被问"能扛多少并发"时，正确答案是"单进程 4 路，再高要改异步"，而不是含糊其辞。
4. `GET /api/stats` 等轻量接口保持普通 `async def`，不占用线程池。

## 12. 在线链路执行时序

>已用真实 API 实测校正（原为估算），详见 `08-实测基线.md`。

```
用户提问
  → [route] 412ms qwen-flash（实测 p50）
  → [rewrite] 412ms qwen-flash（simple 时跳过）
  → [retrieve] 261ms 向量 ‖ BM25 并行（embedding 路实测）
  → [sufficiency] <5ms 节点内预判 + 条件边只读
  → [rerank] 294ms qwen3-rerank（50 条候选实测）
  → [generate] 340ms→首字，全文另需 ~2600ms qwen-plus，流式
  → [verify ① 拆分] 412ms qwen-flash · claim_extract
  → [verify ② 判定] 412ms qwen-flash · claim_verify
  → 输出答案 + 引用 + trace
```

- simple 路径到**首字**约 **1.3s**（412 + 261 + 5 + 294 + 340）。
- 到**答案完全就绪**约 **4.7s**（再加终答全文 2600ms + 校验两次 824ms）。

这两个数字在评测报告里要分开报——用户感知的是首字，系统承诺的是完整性。

**反思循环的增量**：每多一次重检 = `rewrite 412ms + retrieve 261ms ≈ 0.67s`。

| 路径 | 到答案就绪 | 模型 API 调用数 |
| --- | --- | --- |
| simple（不反思） | ≈ 4.7s | 5 |
| multi_hop + 1 次重检（`rewrite`） | ≈ 5.4s | 6 |
| multi_hop + 2 次重检（`rewrite` → `hyde`，跑满） | ≈ 6.7s | 7 |

## 13. 在线链路错误处置

| 环节 | 故障 | 处置 |
| --- | --- | --- |
| route | LLM 失败 | 回落 simple |
| rewrite | LLM 失败 | 用原 query |
| retrieve | 向量路失败 | 仅用 BM25 结果 |
| retrieve | BM25 索引缺失 | 仅用向量结果 |
| rerank | API 失败 | 用 RRF 排序 |
| generate | 流式中断 | 返回已生成部分 |
| verify ① 命题拆分 | LLM 失败 | 跳过校验，标记 `confidence="medium"`，不阻断 |
| verify ② 支持判定 | LLM 失败 | 同上；已拆分出的 claims 仍进 trace |
| 全局 | 未捕获异常 | 返回结构化错误 + trace_id，UI 可查 |
