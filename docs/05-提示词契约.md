# 提示词契约

> 定位：提示词模板是本项目的独立资产，存放于 `src/agentic_rag/prompts/`。
> **本文档不含任何模板正文**，只定义每个模板的契约：用途、输入变量、输出 schema、失败回落、模型与温度。
> 原因：设计文档应保持专业性与稳定性，模板正文属于频繁迭代的实现细节；但**契约必须落在文档里**，否则改模板会静默破坏下游解析与 Mock 匹配。
> 关联：`03§2.1 providers/base.py`（`extract_json`）、`03§2.2 MockLLM`、`04§6 各节点`。

---

## 0. 通用约定

### 0.1 六条硬规矩

1. **每个模板一个文件**，文件名即模板名（`route.md` / `rewrite.md` / …），放在 `prompts/` 下，由 `prompts/loader.py` 统一加载。
2. **所有结构化输出必须走 JSON**，并配合 `response_format={"type": "json_object"}`（`json_mode=True`）。解析一律经 `extract_json`，不得裸 `json.loads`。
3. **输出 schema 变更即破坏性变更**：改了 schema 必须同步改本文档、改对应节点解析代码、改 Mock 的固定返回。
4. **失败回落优先于重试**：解析失败时不重试整条链路，直接走该节点声明的回落值（见每个模板的"失败回落"栏）。
5. **不得在模板里写死业务常量**（阈值、模型名、top_k）。这些走配置，通过输入变量注入——否则改配置要改提示词。
6. **`<system>` 与 `<user>` 两段都会被渲染**，共用同一批注入变量；字面花括号（JSON 示例）必须写成双花括号 `{{…}}`，否则加载期直接报错。
   占位符写在哪一段都必须生效：把 `{max_citations}` 写进 system 却只渲染 user，模型会原样收到花括号——
   而模型照常回答、测试照常绿，只有读提示词原文才看得出来。

### 0.2 版本标记

每个模板头部必须有 `<!-- schema_version: 1 -->`。加载器记录版本，输出 schema 变更时递增。**索引版本号不含 prompt 版本**（prompt 变化不影响已入库向量），但 **trace 与评测报告要记录它**，否则无法解释"同样的配置，换了提示词后指标变了"。

**只改正文、不改输出 schema 时，不递增版本号**——版本号描述的是"解析代码能不能对上"，不是"提示词内容有没有变"。因此有一类改动需要额外处置：**修的是正文里的错，却会让同版本号的输出变好**（例如把没渲染的 `{var}` 修成真值）。
这类提交要在提交信息里写明，并**清掉本地结果缓存**（`data/cache/`），否则旧缓存会以"同签名"复用到新行为上；
对外分发的结果缓存本来就不入库，影响范围限于本地。

## 1. 在线链路模板

> **模型命名约定实测后补充）**：下表出现的 `llm_light`（qwen-flash 系）/ `llm_main`（qwen-plus 系）指配置树里的默认**别名**。**评测与消融一律锁具体版本号**（`qwen3.8-flash` / `qwen3.7-plus`）——实测别名与固定版本同时在架，别名会在官方升级时静默漂移，两次实验跑在不同底层模型上而报告只记了别名，归因就错了。详见 `08-实测基线.md` §1.1。

### 1.1 `route` · 意图路由

| 项 | 内容 |
| --- | --- |
| 调用节点 | `route_node`（04§6.1） |
| 模型 | `llm_light`（qwen-flash 系） |
| temperature | 0.0（分类任务，要稳定） |
| 输入变量 | `query`、`history`（最近 `history_max_turns` 轮，来自 `AgentConfig`，默认 3，可空）、`intents`（合法取值清单，来自 `AgentConfig.intents`） |
| 输出 schema | `{"intent": str, "confidence": float, "reason": str}` |
| 校验 | `intent` 必须落在 `intents` 内，否则回落 |
| **失败回落** | `intent="simple"`，`confidence=0.0`，`reason="route_failed_fallback"` |
| **落点** | `intent`+`reason` → `state.intent`/`state.route_reason`；**`confidence` → `state.route_confidence`，绝不写进 `state.confidence`**——后者是答案级的 `high/medium/low`，两者同名不同义 |
| 说明 | 路由错了只是多花一次检索，不会答错；所以回落选"simple"而非拒绝——**宁可多检索一次，也不要把该检索的问题当成闲聊打发掉** |

### 1.2 `rewrite` · 查询改写

| 项 | 内容 |
| --- | --- |
| 调用节点 | `rewrite_node`（04§6.2） |
| 模型 | `llm_light` |
| temperature | 0.3（需要一点多样性做同义扩展） |
| 输入变量 | `query`、`history`、`intent`、`iteration`（第几轮改写，用于策略升级提示） |
| 输出 schema | `{"queries": list[str], "strategy": str}` |
| 校验 | `queries` 非空且长度 ≤ 4；`strategy ∈ {rewrite, hyde}` |
| **失败回落** | `queries=[原始 query]`，`strategy="none"` |
| 说明 | `table_numeric` 走这一模板时，输入变量额外注入"数值/单位归一"的要求说明（作为 `intent` 的分支提示，不单开模板） |

### 1.3 `decompose` · 多跳分解

| 项 | 内容 |
| --- | --- |
| 调用节点 | `rewrite_node`（intent=multi_hop 时） |
| 模型 | `llm_light` |
| temperature | 0.2 |
| 输入变量 | `query`、`history`、`max_sub_queries`（来自 `AgentConfig`，默认 4） |
| 输出 schema | `{"queries": list[str], "strategy": "decompose"}` |
| 校验 | `2 ≤ len(queries) ≤ max_sub_queries`；**每条子查询必须独立**（不含"它/上述/该"等跨句指代） |
| **失败回落** | `queries=[原始 query]`，退化为单跳检索 |
| 说明 | 独立性约束必须写进模板正文——有依赖的子查询无法并行，延迟会线性叠加 |

### 1.4 `hyde` · 假设性文档

| 项 | 内容 |
| --- | --- |
| 调用节点 | `rewrite_node` |
| 模型 | `llm_light` |
| temperature | 0.4 |
| 输入变量 | `query`、`history` |
| 输出 schema | `{"queries": list[str], "strategy": "hyde"}`，`queries` 只有一个元素：假设性文档段落 |
| 校验 | 生成的段落长度在 100–800 字符之间（过短无信息量，过长稀释向量） |
| **失败回落** | 退回 `rewrite` 策略的结果；若 rewrite 也失败，用原 query |
| 说明 | HyDE 是**策略升级**而非兜底：只有改写一次仍不足时才用，因为它引入的语义漂移风险更大 |

### 1.5 `answer` · 答案生成与引用标注

| 项 | 内容 |
| --- | --- |
| 调用节点 | `generate_node`（04§6.6） |
| 模型 | `llm_main`（qwen-plus 系） |
| temperature | 0.1（事实类文档，抑制发散） |
| 输入变量 | `query`、`context`（带 `[1] [2] …` 编号的上下文块，由 `build_context_block` 生成）、`max_citations`（来自 `GenerationConfig`）、`language`（由 `GenerationConfig.lang` 映射为「中文」/「English」后注入，模板里不直接读配置值） |
| 输出 schema | 纯文本（非 JSON），要求**每个事实命题句末带 `[n]` 角标** |
| 解析 | `parse_citations`（04§8.1）把 `[n]` 映射为 `Citation` 列表并归一化编号 |
| **失败回落** | 引用标记无法映射的编号**直接丢弃**，不把裸 `[n]` 暴露给用户；生成中断则返回已生成部分 |
| 说明 | 上下文编号顺序即引用序号，编号必须从 1 连续；模板正文要约束"不得引用编号之外的来源" |

### 1.6 `claim_extract` · 命题拆分

| 项 | 内容 |
| --- | --- |
| 调用节点 | `verify_node`（04§6.7）第一步 |
| 模型 | `llm_light` |
| temperature | 0.0 |
| 输入变量 | `answer`（去掉角标后的正文） |
| 输出 schema | `{"claims": list[str]}` |
| 校验 | 每条 claim 是单句、含一个原子事实；`len(claims) ≥ 1` |
| **失败回落** | 拆分失败 → 跳过校验，标记 `confidence="medium"`，**不阻断答案输出** |
| 说明 | 拆分的粒度决定忠实度的含义——一句话一条事实，不能一条 claim 里塞两个判断 |

### 1.7 `claim_verify` · 命题支持判定

| 项 | 内容 |
| --- | --- |
| 调用节点 | `verify_node` 第二步 |
| 模型 | `llm_light` |
| temperature | 0.0 |
| 输入变量 | `claims`、`context`（用于生成答案的那几块） |
| 输出 schema | `{"unsupported": list[int], "faithfulness": float}`，`unsupported` 是 claims 的下标 |
| 校验 | 下标在范围内；`faithfulness = 1 - len(unsupported)/len(claims)`（以代码计算为准，模型给的值仅作参考） |
| **失败回落** | `confidence="medium"`，不触发重生成 |
| 说明 | **忠实度由代码按公式算出，不采信模型自报的数字**——模型自报的分数没有校准， drifting 严重 |

## 2. 评测用模板（LLM-as-judge）

| 模板 | 输入变量 | 输出 schema | 说明 |
| --- | --- | --- | --- |
| `judge_faithfulness` | `answer`、`claims`（代码按句末标点拆分的命题列表，带下标渲染进 prompt）、`context` | `{"supported": list[int], "unsupported": list[int]}`，下标指向 `claims` | 与在线链路的 `claim_verify` 同源，但**独立一份**：评测的判据要稳定，不能随在线模板改动而漂移。命题拆分由代码确定性完成而非让裁判自己数句子——两侧（渲染与解析）必须用同一条拆分规则，否则下标错位且不报错。schema_version 2：v1 的下标没有指向对象，属于契约缺口 |
| `judge_relevance` | `question`、`answer` | `{"score": int}`（1–5） | 只判"是否回应了问题"，不判对错 |
| `judge_citation` | `answer`、`citations`、`context` | `{"correct": list[int], "wrong": list[int]}` | 判"引用是否真的支持了它标注的那句话"。**与答案正确性分开统计**。下标指向输入的引用列表 |

> 评测模板与在线模板**刻意分开维护**。在线模板为了效果会频繁调；评测模板一改，历史数据就不可比。

## 3. Mock 关键词契约（关键）

`MockLLM` 靠匹配 user prompt 中的**场景关键词**返回对应结构（03§2.2）。这意味着 **prompt 正文与 Mock 之间存在隐式耦合**——改了模板、关键词消失，Mock 就会返回错结构，而这件事不会报错，只会让整条链路静默跑歪。

因此把这张表定为契约。**任何模板修改，只要影响下表左列的关键词，必须同步更新 `MockLLM` 的匹配规则，否则视为破坏性变更。**

| 模板 | 必须包含的稳定关键词 | Mock 返回 |
| --- | --- | --- |
| `route` | `intent` | `{"intent": "simple", "confidence": 0.9, "reason": "mock"}` |
| `rewrite` / `decompose` / `hyde` | `queries` | `{"queries": ["<原 query>"], "strategy": "rewrite"}` |
| `claim_extract` | `claims` | `{"claims": ["<按句号拆分的答案句>"]}` |
| `claim_verify` | `unsupported` | `{"unsupported": []}` |
| `judge_*` | `score` / `supported` / `correct` | 对应的满分结构 |
| 兜底 | 均不匹配 | 确定性文本（非随机） |

三条约束：

1. **关键词用英文标识符**（`intent` / `queries` / `claims`），不依赖中文表述——中文措辞调整频繁，英文 schema 字段名稳定。
2. **Mock 返回必须是合法 schema**，字段齐全、类型正确，让下游解析代码在 Mock 下和真实下走同一条路径。
3. **Mock 不得返回随机内容**，否则评测不可复现。

## 4. 变更检查清单

改动任一模板时，逐项确认：

- [ ] 输出 schema 是否变化 → 若是，同步改本文档、改节点解析代码、递增 `schema_version`
- [ ] 是否影响 Mock 关键词 → 若是，同步改 `MockLLM`
- [ ] 是否引入新的输入变量 → 若是，确认所有调用点都传了
- [ ] 是否把业务常量写进了正文 → 若是，改回配置注入
- [ ] 失败回落路径是否仍然成立 → 用 Mock 强制触发一次解析失败来验证
