# 技术选型报告

> 目标定位：面向 **AI 应用 / LLM 应用工程** 岗位的可演示作品。
> 语料场景：企业内外部异构文档（PDF / Word / Excel / PPT / Markdown / HTML），含表格、多栏排版、扫描件。
> 模型供给：阿里云百炼 DashScope（纯云端 API）。
> 调研时间：2026-10。

### 关于本文中的数字

| 类型 | 处理方式 | 例子 |
| --- | --- | --- |
| **可实测的** | 由本项目的评测集跑出来，进评测报告 | Recall@K、NDCG@5、P50/P95 延迟、各组件增益 |
| **厂商公开的** | 直接引官方在架文档，注明来源 | 模型上下文窗口、单价、模型下线公告 |
| **行业经验值** | 标注为经验值，**不作为结论依据** | "生产环境 60–70% 查询为简单单跳" |
| **待核实的** | 明确标注，落地前必须查控制台确认 | embedding 单价的具体数值 |

早期版本写过"第三方 2026-04 基准 94.2%"这类具体但无出处的数字——**引用一个自己无法出示来源的数字，被追问时的伤害远大于不引用**。已全部删除或降级为定性描述。同理，"0.6 元/百万 token"这类价格一律标注为"按公开价目量级估算，以控制台为准"。

一个额外要求：**行业经验值要能被本项目自己验证**。"60–70% 查询是简单单跳"是自适应路由的立论前提，那么评测集就应该统计出这个分布并写进报告——用自己跑出来的数字替代借来的数字。

## 0. 选型总原则

技术选型不是"选最火的"，而是**让每一个选择都能说清代价和边界**。本项目遵循四条原则：

| 原则 | 含义 | 在本项目中的体现 |
| --- | --- | --- |
| **口径可控优于开箱即用** | 关键链路的**口径**自己掌握，而不是依赖框架默认值；但默认立场是"有成熟库的用库" | 检索打分与融合、切分、质量判定、评测口径自研；解析、分词、向量库、编排**一律用库** |
| **可解释优于黑盒** | 每个决策都要能追溯到中间产物 | 全链路 trace + UI 可视化 Agent 决策轨迹 |
| **可降级** | 任何外部依赖失效时系统仍能给出结果，**但降级的产物必须有来源** | 解析：Docling → PyMuPDF4LLM → 纯文本 → 拒绝入库；检索：双路任一失败仍出结果并标记；模型：LLM 失败回落到规则判定或诚实应答 |
| **可测量** | 说"更好"必须给出数字 | 自建评测集 + 消融实验，每个优化点都有对应指标 |

**一条不能采纳的降级路径**：把 Mock 当作“LLM → 缓存 → Mock”三级降级的终点是不能要的——**Mock 返回的是确定性假内容，把它作为生产降级路径，等于在系统最脆弱的时候给用户编一个看起来合理的答案**。这与 02 §5.2"宁可诚实说没有，也不让模型硬编"的取向正面冲突。

正确的降级终点只有两个：**规则回落**（用确定性逻辑给出保守结果）或**诚实应答**（说明未能完成）。Mock 的定位被严格限定为"无 API Key 时的开发/演示替身"，只在本项目本地环境启用，永远不会作为运行期降级目标。

一句话概括技术栈：

> **LangGraph 做编排（控制流） + 自研检索内核与质量关卡（数据流） + DashScope 做模型供给
> + FastAPI/SSE 做交付 + 自研评测闭环。**
>
> 反过来，解析、中文分词、向量库、HTTP、Web 服务**一律用成熟库**——见下方"自研边界"。

### 自研边界：什么用库，什么自己写

**默认立场：有成熟库的用库。** 这是工程常识，不是让步。本项目不会为了"自己写过"而重写任何一个已有成熟实现的组件。

自研只发生在三种情况，且必须满足对应判据：

| 情况 | 判据 | 本项目的自研项 |
| --- | --- | --- |
| **现成库给不了** | 需求是领域特定的，没有对应库，或库的抽象与需求不匹配 | 结构感知切分（标题树 + 表格原子化 + 父子映射）、解析质量三关卡、引用溯源与命题级忠实度校验 |
| **口径必须可控** | 该环节的输出要作为其他环节的判据或消融变量，口径必须逐项可调、可解释 | BM25 打分、RRF 融合、评测指标与 LLM-judge、trace 埋点 |
| **外部依赖必须可控** | 用库会引入部署 / 许可 / 成本负担，而需求规模远小于库的设计目标 | 查询结果缓存（键的构成要精确控制）、轻量 JSONL trace |

**一律用库、不再自研**：文档解析、中文分词、向量库与 ANN、编排框架、HTTP 与模型接入、Web 服务。

#### 关于自研检索内核（BM25 约 150–200 行 + RRF 约 30 行）

这两块保留下来，**理由是可控性，不是"自己写更有技术含量"**——BM25 与 RRF 都是标准算法，把它们实现一遍本身不产生任何技术增量：

1. **要能改每一路的分数与过滤时机**：`table_numeric` 意图下表格块加权（`table_boost`）、过滤下推到 ANN 之前，
   都要求拿到每路的**原始分数**并控制过滤发生的层。
2. **每一路必须是独立消融变量**：`use_bm25` / `use_rerank` / `fusion_strategy` / `rrf_k` 要能单独开关与调参，
   用于量化每一路的边际收益——这件事依赖对打分口径的逐项控制。
3. **分词器注入点可控**：领域词典（`data/user_dict.txt`）要能注入到分词器。库的 BM25 实现通常把分词器
   封装在内，注入点与打分后处理都受限。

前两条是本项自研的**实测支撑**：混合检索的增益集中在**表格数值类查询**——财务数字、公司名、专有名词
靠语义向量几乎匹配不上，打开字面匹配这一路后命中率明显上升。这个增益正是"每路原始分数可控 + 每路可独立开关"
带来的，没有这两条就量不出它的边际贡献。**性能数字不随仓库分发**（与语料快照、模型版本强耦合，重跑才有意义）。
**第 3 条目前不作为立论依据**——有注入点不等于注入了就有用，见下方"关于领域词典"。

**关于领域词典（不作为立论依据）**

自维护词典不是本项目的独特做法：RAGFlow 随仓库分发 `huqie.txt`（词 / 词频 / 词性，并预编译为 trie），
并在此基础上实现自己的中文分词器，而不是直接用 jieba（见其 `rag/nlp/rag_tokenizer.py`）。
真正的差异不在"有没有词典"，而在"词典内容从哪来"——他人是静态维护，本项目是脚本从语料抽取 + 入库 + 进指纹。
而这一步的产出，本项目已实测判定为**负增益**：

| 口径 | 结果 |
| --- | --- |
| 查询侧 | 78 条评测问题中只改变 **2** 条分词结果，**两条都变差** |
| 索引侧 | 275 条含词典词的单元中，**44 条被切得更碎、仅 1 条切得更整** |

根因是抽取方法与词典目标方向相反：TF-IDF Top-N 抽出的是高频**短碎片**
（`Qwen2` / `GLM` / `Milvus`，词典平均词长 5.6 字），而词典的目标是保护**长复合词**；
短词作为长词的子串优先级更高，于是 `Qwen2MoeSparseMoeBlock` 被切成 `Qwen2 / Moe / SparseMoeBlock`。
这一方向性错误靠人工过筛挡不住——过筛只删得掉"参见""合计"这类噪声词，删不掉子串。

因此自研的正当性写在上面的第 1、2 条，不写在词典上。词典现版本状态为
**"增强项，且实测为负增益"**，不在外部叙述中作为自研理由引用。

**代价与已知边界**（一并写清，否则就是造轮子而不自知）：

- **生产规模下不应自研**：chunk 到百万级，纯 Python 的倒排与打分扛不住，应换 Elasticsearch / OpenSearch / Qdrant 稀疏向量。
  本项目是 10² 篇 / 10³–10⁴ chunk，落在该实现的有效区间内。
- **换掉的收益很小**：两块合计约 230 行，占全量代码约 **2%**。
- **已评估过的库替代路径**：`rank_bm25` 省约 150 行，但词典注入与打分加权受限；
  LangChain `EnsembleRetriever`（内置 RRF）省约 30 行，但要求两路都走它的 retriever 接口、
  与 `VectorStore` Protocol 冲突，且不支持过滤下推。
- **结论**：保留自研；**若语料规模上升或需要多进程共享索引，优先换库，而不是优化自研实现。**

## 1. 编排层：为什么是 LangGraph，而不是纯手写循环或 LlamaIndex

### 候选对比

| 方案 | 优势 | 劣势 | 适配度 |
| --- | --- | --- | --- |
| **LangGraph**（LangChain 系） | 显式状态机、条件边、循环边；原生 checkpoint / 回放；LangSmith 可观测 | 检索侧抽象弱，需要自己补；代码量偏大 | ★★★★★ |
| LlamaIndex Workflows | 检索默认质量高，代码量少，LlamaParse 解析强 | 编排能力弱于 LangGraph；深度定制时仍需跳出框架 | ★★★★ |
| Haystack 2.x | 引用溯源是一等公民（Citation 独立于 Answer 建模），类型安全，适合合规场景 | 生态活跃度与社区规模小于前两者 | ★★★ |
| 手写 while 循环 | 零依赖，完全可控 | 需要自己实现持久化、回放、中断、并发；这些与检索质量无关，不产生技术增量 | ★★★ |

### 决策

**LangGraph 作为编排层，检索内核自研。**

### 依据

1. **岗位匹配**：AI 应用工程岗考察的是"Agent 控制流设计能力"——状态如何流转、失败如何回退、循环如何终止。LangGraph 的图语义天然对应这套思维，控制流可以直接用状态机表达。
2. **可解释性**：LangGraph 的 `StateGraph` 可导出为 Mermaid / PNG，demo 的 UI 里能实时展示"当前在哪个节点、走了哪条边"，这是可解释性最直观的体现。
3. **生态位互补**：2026 年生产环境的共识是 *LlamaIndex 管检索 + LangGraph 管编排*。本项目保留这一组合形态，
   检索层不用 LlamaIndex 的默认检索器。原因**不是"默认实现不够好"**，而是它的抽象与本项目三个需求不匹配：
   ① 打分后处理的注入点受限（词典注入点另见 §0"关于领域词典"，不作为立论依据）；② 表格块加权与过滤下推要求拿到每路原始分数并控制过滤时机；
   ③ 每一路要作为独立消融变量单独开关。三者都要求对打分口径的逐项控制（完整判据见 §0"自研边界"）。
4. **不选 LlamaIndex 单栈**：它能让 demo 更快跑通，但会把最有价值的检索细节藏在库里，与"体现技术深度"的目标相悖。

### 设计要点

- 讲清 **LangGraph 与 LlamaIndex 的分工边界**：前者是控制流（orchestration），后者是数据流（retrieval primitives）。
- 讲清 **循环边的终止条件设计**：反思节点最多迭代 N 次，避免无限循环导致成本失控（Agentic RAG 的 token 成本是普通 RAG 的 3–10 倍）。

## 2. 文档解析层：分层路由，而不是单一解析器

### 核心认知

> RAG 的上限由解析质量决定。表格被切碎 → 数值与表头分离 → 检索到表头却拿不到数值 → 模型编造数字。这是企业文档场景最常见的失效模式。

### 候选对比（2026 现状）

| 工具 | 许可 | 强项 | 弱项 |
| --- | --- | --- | --- |
| **Docling**（IBM/DS4SD） | MIT | 版面分析 + 表格结构还原最强，内置 OCR，可输出无损 JSON 文档模型 | 依赖重（PyTorch 生态，数 GB），CPU 上偏慢 |
| **MarkItDown**（Microsoft） | MIT | Office 全家桶 → Markdown，极轻量 | 无版面感知，复杂扫描 PDF 不适用 |
| **PyMuPDF4LLM** | AGPL | 速度最快（200+ 页/分钟），依赖小（~120MB） | 无版面分析，表格需按坐标抽取 |
| MinerU（OpenDataLab） | AGPL-3.0 | 学术论文、公式、多栏 SOTA | 需要 GPU 才有实用速度 |
| LlamaParse | 商业 API | 复杂 PDF 准确率高 | 文档需上传第三方，成本随量增长 |

### 决策：**解析器路由（Parser Router）+ 三级降级**

```
文件格式 → 启发式探测（表格密度 / 是否扫描件 / 图片占比）
        ├─ .docx / .xlsx / .pptx / .html → MarkItDown（轻量，Office 兼容最佳）
        ├─ .pdf + 表格密集 → Docling（可选 backend，需显式开启）
        ├─ .pdf + 纯文本 → PyMuPDF4LLM（默认，速度优先）
        └─ .pdf + 扫描件 → Docling OCR 通道（可选）
        降级链：Docling 失败/未安装 → PyMuPDF4LLM → pypdf 纯文本
```

### 依据

1. **默认路径轻量**：`pymupdf4llm` + `markitdown` 两个包即可覆盖 90% 场景，保证 demo 在任意环境 5 分钟装完、能复现。
2. **重型路径可选**：Docling 作为 `heavy` backend 通过配置项开启，用于表格密集与扫描件场景，把"表格是难点"这件事落到具体实现上。
3. **统一中间表示**：无论哪个解析器，输出统一为 **Markdown + 结构标注（标题层级 / 表格块 / 图片说明）**，下游切分与引用溯源只认这一层契约。这是典型的 **防腐层（Anti-Corruption Layer）** 设计。

### 一个必须挑明的许可风险（原文档漏了）

`pymupdf4llm` 依赖 `PyMuPDF`，后者是 **AGPL-3.0**；`MinerU` 同为 AGPL-3.0。AGPL 的传染性对要公开的项目是实实在在的问题——一旦项目本身以宽松许可（MIT/Apache）开源，却在依赖树里挂着 AGPL 组件，法律上讲整个衍生作品需要以 AGPL 开放。

处置方案（三选一，本项目选第二）：

| 方案 | 说明 |
| --- | --- |
| 全项目以 AGPL-3.0 开源 | 最省事，与依赖一致，但会劝退部分企业评审者 |
| **默认用 PyMuPDF4LLM，同时提供 `PDF_BACKEND=pypdf` 切换项** | **本项目采用**。保留 AGPL 依赖的速度优势，同时给出规避该风险的切换路径 |
| 默认换成 `pypdf`(BSD) / `pdfplumber`(MIT) | 最干净，但速度慢一个量级、无版面分析，与"表格保结构"的目标冲突 |

README 的许可章节必须如实写明：**本仓库代码采用宽松许可，但默认依赖链中包含 AGPL-3.0 组件（PyMuPDF），商业使用需自行评估或切换 `PDF_BACKEND`**。把风险写在明处，比等人发现强。

### 设计要点

- 讲一个真实失败案例：财报 PDF 用 PyPDF 解析 → 表头与数值被拆到不同 chunk → 问"营收多少"得到幻觉数字 → 换成保留表格结构的解析 + 表格整体入块后修复。
- 讲**表格不要被切分**：对表格块做原子化处理，整表进一个 chunk，切分时标记 `is_atomic=True`。

## 3. 切分策略：两策略并存，可 ablation

> 早期版本列了三种策略（含 Late Chunking）。Late Chunking 已**明确移除**，理由见下。

### 决策

| 策略 | 适用场景 | 说明 |
| --- | --- | --- |
| **父子切分（Small-to-Big）**（**默认**） | 绝大多数场景 | 按标题树切父块（≤1024 token），父块内按段落切子块（≤256 token）；子块做检索，命中后回填父块给生成 |
| **结构感知切分** | 消融对照 / 无父子需求时 | 按 Markdown 标题树递归切分，单层块，块内保留完整标题路径 |

**默认策略是父子切分**（01 早期版本误标为"结构感知默认"，与 03§6 冲突，已统一）。

### 为什么明确不做 Late Chunking

Late Chunking 的思路是对的：先对整段做 embedding，再按边界切分取片段向量，让每个片段继承全局上下文。但它有一个**硬前提**——必须能拿到 **token 级 embedding**（每个 token 一个向量），才能按切分边界做池化。

而 DashScope 的 OpenAI 兼容 `/embeddings` 端点只返回**整段一个向量**，不提供 per-token 输出。本项目的选型前提是"模型能力全部走云端 API、不自建模型服务"，在这个前提下 Late Chunking **无法实现**。

可以想到的"变通"只有一条：把整段向量直接赋给每个子块。但那等于让所有子块共享同一个向量，检索时完全丧失区分度，比不用还差——**这是一个自欺欺人的实现，不如不做**。

真正能做的路径是自建 embedding 服务（本地加载支持 token-level 输出的开源模型），那已经超出本项目的选型边界。**把它写进"明确不做"并说明原因，比做一个假的 LateChunker 更有价值**——知道它好、同时知道它在当前模型供给下做不到、并说清为什么做不到，这才是完整的技术判断。

### 两条策略的对比变量要干净

结构感知切分与父子切分不是并列关系——父子切分内部就包含了"按标题树切父块"。所以 B2 消融组实际对比的是 **检索单元粒度**：

| | 结构感知 | 父子切分 |
| --- | --- | --- |
| 检索单元 | 单层块（≤1024） | 子块（≤256） |
| 送生成的上下文 | 该块本身 | 回填的父块（≤1024） |
| 索引体积 | 1× | 子块 1× + 父块单独存（不进向量索引） |
| 向量语义 | 块内主题可能被稀释 | 子块语义集中 |

变量只有一个：**用多大的块去检索**。这是干净的单变量实验。

### 关键设计：**上下文增强块头（Contextual Chunk Headers）**

每个 chunk 入库时，在其文本前注入其文档级上下文路径：

```
[文档: 2025年度产品白皮书 > 第三章 部署方案 > 3.2 网络拓扑]
<chunk 原文>
```

- 这是 Anthropic Contextual Retrieval 思路的**低成本版本**：不必为每个 chunk 调 LLM 生成上下文（成本高），而是直接复用文档的标题树，几乎零成本。
- 解决的核心问题：**chunk 脱离文档后语义不完整**（"它的上限是多少？"——"它"指谁？）。

### 设计要点

- 讲清楚两者的 trade-off：结构切分省事、索引体积小，但对无标题文档失效；父子切分召回更准、上下文更完整，代价是"命中子块 → 回填父块"这一步会让 rerank 打分对象与生成时实际看到的文本不一致（rerank 对子块打分，生成看父块）。这个不一致是 Small-to-Big 的固有代价，要主动讲。
- 讲清楚**为什么不做 Late Chunking**（token 级 embedding 的前提 + 云端 API 供给的限制）——这是"知道边界"的体现。
- **用评测数据说话**：两种策略在自建评测集上的 Recall@5 差异，直接列进评测报告；B3 组再单独量化"父块回填"这一动作的收益。

## 4. Embedding 模型

### 候选（DashScope 在架）

| 模型 | 维度 | 最大 token | 定位 |
| --- | --- | --- | --- |
| `text-embedding-v4` | 64–2048（默认 1024） | 8,192 | 通用文本检索主力 |
| `qwen3.7-text-embedding` | 256–2560（默认 1024） | 131,072 | 超长文本、高精度 |
| `qwen3.7-text-embedding-flash` | 256–1024 | 131,072 | 成本与吞吐优先 |

### 决策

**`text-embedding-v4`，维度 1024**，作为默认；`qwen3.7-text-embedding` 作为长文本场景的可切换项。

### 依据

1. 8,192 token 的窗口对切分后的 chunk（256–1024 token）绰绰有余。
2. 1024 维是官方推荐的精度/存储平衡点；demo 规模下存储不是瓶颈。
3. 单价按 DashScope 公开价目量级估算（约 0.5–1 元/百万 token，**落地前以控制台为准**），demo 全量索引成本在几元以内。原版本曾拿另一款产品的公开价目推测 DashScope 定价，这是不严谨的——价格一律以厂商控制台为准，估算只用于量级判断。
4. **维度必须显式指定并与向量库 collection 定义一致**——这是生产环境最常见的低级故障（改了 embedding 维度却没重建索引），本项目把它做进配置项并在启动时校验。

### 设计要点

- 讲 **embedding 版本迁移的代价**：换模型 = 全量重建索引，所以要在抽象层做 `EmbeddingProvider` 接口 + 索引版本号，支持双索引灰度切换。

## 5. 向量库

### 候选

| 方案 | 部署形态 | 特点 |
| --- | --- | --- |
| **Qdrant** | **嵌入式 local 模式** / 服务模式 | 同一 client API 覆盖两种形态；原生 payload 过滤；Apache-2.0 |
| LanceDB | 嵌入式（本地文件） | 列式存储，Python 友好；生产服务形态需依赖云产品 |
| Milvus | 服务（K8s） | 亿级向量、企业级 |
| pgvector | Postgres 扩展 | 与业务库同栈，事务一致 |

### 决策

**默认 Qdrant（local 模式，嵌入式）。** `VectorStore` Protocol 保持不变、可替换实现；
`backend=qdrant_server` 时只换连接配置（`url` / `api_key`），**代码路径完全不分叉**。

### 依据

1. **零运维 = 可复现**：local 模式下 `QdrantClient(path=...)` 不起服务、
   不需要 Docker，使用者 clone 下来 `pip install` + 一条 ingest 命令就能跑。这一点决定了项目能否被他人独立验证。
2. **local 与 server 是同一套 API**——**这是换掉 LanceDB 的决定性理由**。切换只发生在配置层：
   `path=` 换成 `url=`，`QdrantStore` 内部无分支。"演示用嵌入式、生产用服务"不再是一次跨库迁移，
   而是同一实现的两种部署形态。02 §10 里"向量规模破千万 → 迁移到另一个库"这条**永远无法被验证的演进项因此被消除**，退化为一次配置切换。
3. **原生 payload 过滤可下推**：`filter_tables_only`（table_numeric 意图的消融变量）能在 ANN 之前完成过滤，
   而不是融合后再筛。前置与后置过滤的召回分布不同——下推让这个消融的语义干净（见 04§4）。
4. **余弦分数口径直接可用**：Qdrant 以 `COSINE` 为度量时返回的 score 就是余弦相似度 ∈ [-1,1]，
充分性判据（`vector_score ≥ sufficiency_vector_floor`）可以直接消费。
   LanceDB 默认返回 L2 距离、需要自行换算——**换算错一处就会让阈值标定整体失效**，而这个阈值正是反思循环的开关。
5. **不依赖向量库的检索能力不变**：关键词检索完全自研（jieba + 自研 BM25）。
   **Qdrant 自带的全文检索与稀疏向量同样不使用**，理由与稀疏路一致：分词与打分口径必须可控。
   这一条必须在文档里写明，否则"自研检索内核"的立意会被自己拆掉。

### 代价与约束（一并写清）

- **local 模式独占数据目录**：同一时刻只允许一个进程打开索引目录。
  **server 常驻时不能后台重建索引**，摄取必须在服务未持有该目录时执行（CLI 与 server 互斥）。
  这是 local 模式的硬限制，不是实现缺陷，实现时要用启动期检查把它变成明确报错而不是文件锁死等。
- 依赖体积比 `lancedb` 大；装不上时仍降级 `InMemoryStore`（brute-force 余弦），保证全流程可跑通。
- **`sufficiency_vector_floor` 的标定值与具体库实现绑定**：换库必须重标。
  该阈值本就在 P3 用 mini 集标定，不额外增加工作，但标定结论不能沿用换库前的数字。

## 6. 关键词检索（稀疏检索）：自研 BM25

### 决策

**自研 BM25，jieba 中文分词，pickle 持久化**，不依赖任何库的 FTS。

### 依据

1. **中文是硬骨头**：通用向量库的 FTS 多基于 Tantivy/Lucene，中文分词默认按字切或需要额外插件，效果不可控。
   需要说明的是：**自研的目标是"分词与词典可控"，不是"自己实现 BM25 公式"**——公式是标准的，
   实现它不产生技术增量（§0 自研边界）。
2. **向量检索的固有盲区**：专有名词、型号、缩写、金额、法条编号（"第 3.2 条"）等**字面精确匹配**场景，向量会失效，BM25 能救回来。这是混合检索存在的根本理由。
3. **算法本身可控可调**：BM25 的 IDF 饱和与长度归一化，是它区别于 TF-IDF 的关键。
   `k1` / `b` 与分词词典都要能调、且要能作为消融变量单独量化——这正是把它纳入"口径可控"类自研项的原因。

实现要点：

- 分词：jieba 精确模式 + 用户词典（注入领域术语，如产品名、部门名）
- 参数：`k1=1.5, b=0.75`（经典值，作为可调项）
- 倒排索引：`term -> [(doc_id, tf)]`，查询时只对命中 term 的文档打分，保证亚线性复杂度
- 与向量检索**并行执行**，用线程池并发，不增加端到端延迟

## 7. 融合与精排

### 7.1 融合：RRF（Reciprocal Rank Fusion）

### 决策

**RRF 作为默认融合策略，加权分数融合（Weighted Score Fusion）作为对照项。**

### 依据

- RRF 公式为 `score(d) = Σ 1/(k + rank_i(d))`（k 默认 60），
- 核心优势：**无需归一化**。向量相似度（余弦，[0,1]）与 BM25 分数（无上界，量纲随语料长度变化）不可直接相加，必须先归一化（min-max / z-score），而归一化对异常值敏感。RRF 只用排名，天然免疫量纲问题。
- 结论：两种分数不可直接相加，这不是调参能绕过的——它由两侧分数的量纲决定，也正因如此融合策略只能在"用排名"与"先归一化"之间二选一。

### 7.2 精排：Cross-Encoder Rerank

### 候选（DashScope 在架）

| 模型 | 单条最大 token | 备注 |
| --- | --- | --- |
| `qwen3-rerank` | 4,000 | **本项目默认** |
| `qwen3.7-text-rerank` | 30,000 | 超长片段场景 |
| `gte-rerank-v2` | 4,000 | ⚠️ 官方公告 2026-05 下线 |

### 决策

**`qwen3-rerank`**，对 RRF 融合后的 Top-50 重排，取 Top-5 送生成。

### 依据

1. **两段式检索是工业标准**：bi-encoder（向量）负责从千万级召回百级，cross-encoder 负责从百级精排出个位数。cross-encoder 对 query 与 doc 做全注意力交互，精度远高于向量相似度，但无法离线预计算 doc 向量，所以只能用于小候选集。
2. 这个 **"召回-精排"漏斗** 是两段式检索的标准结构，本项目把它显式实现并可单独开关，用于消融实验。
3. 注意 `gte-rerank-v2` 已下线——**选型必须核对官方在架状态**，这是工程素养的细节。

### 设计要点

- 讲清 **bi-encoder vs cross-encoder 的本质区别**（是否对 query-doc 对做联合编码、能否预计算）。
- 用评测数据证明：rerank 带来 NDCG@5 提升 X%，代价是延迟 +Yms、成本 +Z 元/千次查询。

## 8. 生成模型：分级供给

### 决策

| 用途 | 模型 | 理由 |
| --- | --- | --- |
| 意图路由 / 查询改写 / 引用校验（×2） | **qwen-flash**（评测锁 `qwen3.8-flash`） | 高频、低复杂度，成本与延迟敏感 |
| 最终答案生成 | **qwen-plus**（评测锁 `qwen3.7-plus`） | 质量优先，用量少 |

> **别名 vs 锁版本实测后补充）**：别名与具体版本实测**同时在架**。配置树保留别名为默认值以降低首次运行门槛，但**评测与消融一律锁版本号**——别名会在官方升级时静默漂移到底层新模型，两次实验跑在不同模型上而无人察觉，消融差异就分不清是配置带来的还是升级带来的。`EvalReport` 必须记录响应体返回的**实际模型名**而非请求值。详见 `08-实测基线.md` §1.1。

### 依据

1. **一次用户查询会触发 4–7 次 LLM chat 调用**（路由 1、改写 0–2、校验 2、生成 1（+重生成 0–1））。全部用旗舰模型，成本直接翻数倍。分级供给是 Agentic RAG 成本控制的第一手段。

   > **口径说明（避免与 02 §7 打架）**：本表只数 **LLM chat 调用**，不含 embedding 与 rerank。
   > 02 §7 的"单次查询 5 次模型 API 调用"= route + **rerank** + generate + verify×2，含 rerank、不含 embedding。
   > 两个数都对，只是各自数了不同的东西——引用时要把口径说全，报其中一个数字时顺带说明含不含 rerank。
   >
   > 改写的 0–2 次来自 L2 的三级升级：首轮按意图走 `none` / `rewrite` / `decompose`
   > （simple 透传，不调模型），若不足则 `iteration=1` 用 `rewrite`、`iteration=2` 用 `hyde`。

2. 参数策略：生成 `temperature=0.1`（制度/事实类文档，抑制发散）；改写 `temperature=0.3`（需要一点多样性做查询扩展）。
3. **JSON 容错**：模型输出结构化内容时小概率产出非法 JSON，业务侧必须做**解析异常捕获 + 原样回灌让模型自修复**，而不是直接崩。这个细节来自官方生产避坑建议。

## 9. 服务与前端

### 决策

**FastAPI + SSE 流式 + 单页原生 HTML/JS（无构建）。**

### 对比

| 方案 | 优势 | 劣势 |
| --- | --- | --- |
| **FastAPI + SSE** | 标准 HTTP、浏览器原生 EventSource 支持、可写进简历的后端能力、并发友好 | 需要自己写前端 |
| Streamlit / Gradio | 10 分钟出界面 | 简历价值低，UI 定制受限，流式与并发较弱 |
| WebSocket | 双向 | RAG 是单向推送，SSE 更贴合语义、更轻 |

### 依据

1. **SSE 优于 WebSocket**：QA 场景只需服务端推送，SSE 走标准 HTTP、自动重连、无需额外协议，工程上更简洁。这是有理由的选择，不是随意的。
2. **无构建前端**：一个 `index.html` + 少量 JS/CSS，零 npm 依赖，评审者无需装 Node 即可看到完整界面。
3. **流式 + 事件化**：SSE 不只推 token，还推**结构化事件**（`route` / `rewrite` / `retrieve` / `rerank` / `reflect` / `answer` / `citation`），前端据此渲染 Agent 决策时间线。这是 demo 的视觉核心。

## 10. 评测

### 决策

**自研评测为主（Recall@K / MRR / NDCG@K / 命中率 / 忠实度），RAGAS 作为可选对照。**

### 指标体系

| 层次 | 指标 | 计算方式 |
| --- | --- | --- |
| 检索 | **Recall@K**（主指标） | 标注的黄金 chunk 是否被召回 |
| 检索 | **MRR** | 首个相关结果的排名倒数 |
| 检索 | **NDCG@K** | 考虑排序位置折扣（专用于衡量 rerank 收益） |
| 生成 | **Faithfulness（忠实度）** | LLM-as-judge：答案中可溯源命题占比 |
| 生成 | **Answer Relevance** | LLM-as-judge：答案对问题的回应度 |
| 工程 | P50/P95 延迟、token 成本、迭代次数 | 由 trace 自动汇总 |

### 依据

1. **忠实度必须按命题拆分**：给整段答案打一个 0–100 分没有意义。正确做法是把答案拆成原子命题，逐条判断"是否被 context 支持"，再算支持率。这样能定位是哪一句话在幻觉。
2. **自研 LLM-judge 优于直接引 RAGAS**：RAGAS 与 DashScope 的接入存在兼容成本，且 judge 逻辑藏在库里无法解释。自研可以完全控制评分口径，并且**能把这个口径讲清楚**（这正是自研的意义）。
3. **必须有消融实验**：单一终态指标没有说服力。要证明"Agentic 不是噱头"，就要列出逐个开关组件后的指标变化。
4. **必须声明结论成立的前提（Mock 陷阱）**：Mock 模式下向量路、BM25 路、rerank 全是字面匹配，三路同构，A1/A2 的增益必然失真。评测报告必须带 `provider_mode` 与配置指纹；Mock 下只公布工程性指标，不公布检索质量结论。详见 04§9.5。**这是本项目最大的可信度风险**——最核心的说服点最容易在最常跑的环境里失真。

### 计划中的消融组合

| 实验组 | 配置 |
| --- | --- |
| A0 基线 | 向量检索 only（`use_bm25=False`） |
| A1 | + BM25 混合（RRF） |
| A2 | + Rerank |
| A3 | + 查询改写 |
| A4 | + 反思循环（完整 Agentic） |
| B1 | 融合策略：RRF vs 加权 |
| B2 | 切分：**structural vs parent_child**（对比检索粒度） |
| B3 | 父子块回填 开 / 关 |
| B4 | simple 是否进检索侧反思循环（`allow_reflect_for_simple`） |
| B5 | 生成侧重生成 开 / 关（`regenerate_on_unsupported`） |

> 每组消融对应的**具体配置字段**见 04§9.4 的"对应开关"列——那里是唯一权威口径，
> 本文档这张表只用于说明实验意图，避免两处字段口径打架。

## 11. 可观测性

### 决策

**自研轻量 trace，结构化 JSONL 落盘 + 前端时间线渲染。**

### 记录内容

```
query_id / 时间戳 / 路由结果及其置信度 / 改写后的子查询 /
每路召回的候选数与耗时 / RRF 融合结果 / rerank 前后排名变化 /
反思迭代次数与判定理由 / 生成耗时 / token 消耗 / 引用列表
```

### 依据

1. 生产环境建议 Langfuse / Phoenix（Arize），本项目自研 trace：记录哪些字段由检索与编排的诊断需求决定，且零外部依赖。
2. trace 直接驱动 UI 的决策可视化，一份数据两处复用。
3. **错误归因（Error Attribution）**：答案出错时，trace 能定位是"路由错 → 检索策略错 → 上下文不足 → 幻觉"链路的哪一环，这是 Agentic RAG 调试的关键方法论。

## 13. 选型决策一览

| 层 | 选型 | 关键理由（一句话） |
| --- | --- | --- |
| 编排 | LangGraph | 显式状态机 = 可解释 + 可回放，Agent 控制流的行业标准表达 |
| 文档解析 | 路由 + 三级降级（PyMuPDF4LLM / MarkItDown / Docling） | 表格是 RAG 的头号杀手，必须保留结构 |
| 切分 | 父子切分（默认）/ 结构感知 | 两策略可 ablation（对比检索粒度）；**Late Chunking 明确不做**（需 token 级 embedding，云端 API 不提供） |
| Embedding | `text-embedding-v4` (1024d) | 通用主力，维度显式声明并与索引校验 |
