# 测试设计

> 定位：01 §10 强调"可测量"，但原文档只有评测（检索与生成质量），没有测试（工程正确性）。本文档补齐这一层。
> **测试与评测是两件事**：测试判"代码对不对"（确定性、可断言），评测判"效果好不好"（统计性、有波动）。两者都要有。
> 关联：`03§3 trace`、`06-语料方案`（测试用的 fixture 语料）。

---

## 1. 四层结构

| 层 | 对象 | 依赖外部服务 | 运行耗时 | 数量级 |
| --- | --- | --- | --- | --- |
| **L1 纯函数** | 无状态算法 | 无 | 毫秒级 | ~50 例 |
| **L2 组件** | 单模块 + 本地文件 | 无（用 Mock provider） | 秒级 | ~40 例 |
| **L3 集成** | 跨模块链路 | 无（全 Mock） | 十秒级 | ~15 例 |
| **L4 回归** | 端到端 + 探针 | 可选 | 分钟级 | 2 套 |

**L1–L3 必须能在无 API Key 的机器上全绿**。这既是工程要求，也是可复现性要求——使用者 clone 下来跑 `pytest` 应该一次通过。

## 2. L1 · 纯函数测试

| 模块 | 用例要点 |
| --- | --- |
| `retrieval/fusion.py` | ① RRF 手算验证（两路各 3 条，k=60，逐条核对分数）；② 只在单路出现的候选中奖；③ 两路都命中的排名靠前；④ 空输入返回空；⑤ 加权融合的权重归一化 |
| `eval/metrics.py` | ① Recall@K 的 K 大于列表长度时的行为；② MRR 首个相关在第 1 位 = 1.0、不出现 = 0；③ NDCG@K 的顺序敏感性（同一集合不同排序应得不同分）；④ golden 为空的处理 |
| `generation/citation.py` | ① `[1] [2]` 解析与编号归一化；② 重复引用去重；③ **越界编号（如 `[9]` 但只有 5 块）必须丢弃而非保留**；④ 无引用标记的答案返回空列表 |
| `ingestion/chunking` 的 `with_header` | 标题路径拼接格式、空路径退化 |
| `config.py` | ① `compute_index_version` 对**每一个**哈希因子的敏感性（embedding 模型 / dim / 切分策略 / 四个切分尺寸参数）；② `retrieval_signature` 对每个消融开关的敏感性——**漏一个都会让缓存返回错结果，这条必须逐项测**；③ 启动校验表每一条都有对应的"应当抛错"用例；④ **配置树字段完整性对账**：扫描 03/04 正文里所有 `cfg.<X>` 引用，断言每个都能在配置树上取到属性——凭空引用的字段只有这类对账能发现 |
| `providers/base.py` 的 `extract_json` | ① 裸 JSON；② 带 ```json 代码块包裹；③ 前后有解释文字；④ 非法 JSON 应抛出并由调用方回落 |
| `index/bm25.py` 打分 | 构造 5 篇微型语料，**手算 BM25 分数**与实现对照（IDF 与长度归一化的符号最容易写反） |
| **文档契约**（`tests/unit/test_contract_audit.py`） | 把"文档与实现同源"从人工纪律变成断言，四条对账：① **配置树 ↔ `config.py` 双向**（代码有、文档没写也要红）；② **提示词 ↔ 05**（每个模板都要有契约、每个 `{var}` 都要在文档里出现）；③ **依赖 ↔ `pyproject`**（直连 import 必须在 dependencies 或 extra 里）；④ **Markdown 链接与 README 索引**（删文档、改标题必红） |

## 3. L2 · 组件测试

| 模块 | 用例要点 |
| --- | --- |
| `ingestion/chunking` | **表格四档规则（03§6.4）逐档验证**：≤256 整表一块 / 256–1024 超长子块豁免 / >1024 按行组切且每组有表头 / 单行超 2048 放弃原子性。② 父子映射每个 child 都有 parent；③ `validate_chunks` 对每种违规都能报出对应 issue |
| `ingestion/parsers` 路由 | ① 扩展名 → 解析器的路由表全覆盖；② Docling 未安装时降级到 PdfParser；③ 降级必须写进 `QualityReport.issues`（**不记录的降级等于静默降质**） |
| `ingestion/quality.py` | ① `raw_baseline` 对 8 种格式都能取到非空值（对 md/txt 标注不适用）；② **raw 为空时守恒检查返回 `None` 且进 `not_applicable`**（这是修掉的公式缺陷，必须有用例锁住）；③ 扫描件 + 无 OCR → rejected；④ 扫描件 + OCR 且输出过少 → rejected；⑤ 各阈值的 warn/reject 边界值 |
| `index/vector_store.py` | ① `QdrantStore` 与 `InMemoryStore` 对同一批向量检索结果一致（允许浮点误差）；② `delete_by_doc` 后 `count` 正确；③ meta 存取往返；④ **已有集合的度量不是 `Cosine` 时 `create` 报错**；⑤ `backend=qdrant_server` 且 `url` 为空时启动校验抛错 |
| `index/bm25.py` | `save` → `load` 后检索结果完全一致（pickle 往返） |
| `observability/trace.py` | ① `span` 自动计时；② 崩溃时已采集部分不丢（追加写）；③ `finalize` 汇总字段齐全 |
| `providers/*` Mock | ① `MockEmbedding` 确定性（同输入两次结果完全相同）；② 字面重叠多的文本相似度更高（这是它被选中的理由，要锁住）；③ `MockLLM` 每种关键词返回结构合法 |

## 4. L3 · 集成测试

| 场景 | 断言 |
| --- | --- |
| **离线端到端** | fixture 语料 → `ingest` → 索引非空 → `probe` 命中率 100% → `stats` 中文档数与 chunk 数符合预期 |
| **拒绝入库** | 放入一个损坏/加密文件 → 该文件出现在 `data/rejected/` 且不进索引 → `BuildReport.rejected == 1` |
| **版本校验** | 构建索引后改 `embedding_dim` → `load` 抛 `IndexVersionMismatch` |
| **在线端到端（Mock）** | 跑完整图，断言 ① 8 个节点按预期路径被走到；② 每类 intent 走对分支（chitchat 不检索、simple 不反思）；③ `trace` 中各步骤齐全 |
| **循环终止** | 构造"永远检索不到"的查询（达标候选恒为 0）→ 断言恰好检索 `max_retrieve_iterations` 轮后走 `degrade_answer`，**不无限循环** |
| **循环终止·有证据** | 构造"达标 1–2 条但恒不足 `min_candidates`"的查询 → 断言跑满 `max_retrieve_iterations` 轮后**进入生成**（不是拒答），且 `confidence == "medium"` |
| **生成侧预算独立** | 让检索侧耗尽预算，再断言生成侧仍有自己的重生成机会（验证计数器已拆分） |
| **首轮不自增** | ① simple 一次跑通后断言 `generate_iterations == 1`、`retrieve_iterations == 1`；② **打开 `regenerate_on_unsupported` 并注入一份故意含无支撑命题的答案，断言 `regenerate` 分支真的被走到**——"测试全绿但代码从不执行"这类问题只能靠这条用例抓住 |
| **父块回填去重** | 构造 Top-5 子块中有 3 条同属一个父块的场景 → 断言送生成的上下文块数 = 3 而非 5，且其中无重复 `chunk_id`；断言 trace 记录 `dedup_collapsed == 2` |
| **事件有发送方** | 断言 SSE 协议里每一个事件类型都能在实际事件流中被观察到——尤其 `reflect` 必须出现在 `retrieve` 之后、`rerank` 之前。孤儿事件（协议里有、代码里没人发）只能靠这条测出来 |
| **SSE 协议** | 事件序列合法；`done` 在 trace 落盘之后；开启重生成时 `regenerate` 事件出现在 token 之后 |
| **缓存键** | 同一 query 在切换 `use_rerank` 后**不应命中**缓存；切换 `llm_main` 或递增 prompt `schema_version` 后同样不应命中 |
| **充分性判据有区分度** | ① 构造"候选恒满（≥ `fusion_top_k`）但余弦全部低于 floor"的场景 → 断言 `sufficient == False` 且 `retry` 分支被走到；② 断言**在候选数恒满的语料下反思循环确实能被触发**——判据若只数候选数，`sufficient` 恒真、反思永不执行，而所有用例仍然全绿 |
| **充分性降级可见** | `use_vector=False` 时断言 ① 判据降级为候选数（`sufficiency_basis == "candidate_count"`）；② **不会**因为达标数恒 0 而每次跑满 3 轮；③ `basis` 出现在 `reflect` 事件 payload 里 |
| **反思策略升级** | 断言三轮检索的 `transform_strategy` 依次为 `decompose`（multi_hop 首轮）→ `rewrite`（iteration=1）→ `hyde`（iteration=2），且写进 trace。**这条用例必须能真的走到 hyde**，否则"升级链走满"只是纸面能力 |
| **跨轮合并** | 构造"第二轮召回更差"的场景 → 断言首轮的高分候选仍在最终 `candidates` 里（合并而非覆盖），且 trace 记录 `merged_from_prev > 0` |
| **缓存键含 history** | 同一 query、不同 history → 断言**不命中**；同一 query + 同一 history（内容相同但顺序一致）→ 命中 |
| **指纹含 BM25 参数与词典** | 改 `bm25_k1` / `bm25_b` / 词典文件任一字节 → 断言 `retrieval_signature` 变化 |
| **指纹含生成侧判据** | 改 `faithfulness_threshold` / `regenerate_on_unsupported` → 断言 `generation_signature` 变化 |
| **充分性降级不失真** | `use_vector=False` 且候选非空但不足 → 断言 `reflect_reason == "query_expression"` 而不是 `corpus_missing` |
| **confidence 全覆盖** | 五条终止出口各跑一次，断言 `done` 事件的 `confidence` 取值符合 04§6.7 的取值表，**无未定义分支** |
| **事件发送方唯一** | 断言除 `cache_hit` / `done` 两个 Pipeline 级事件外，每个事件类型都能追溯到唯一一个节点 |

## 5. L4 · 回归测试

| 套件 | 触发时机 | 判据 |
| --- | --- | --- |
| **探针集** | 每次重建索引 | 命中率 ≥ 0.9，失败用例列出实际 Top-K |
| **配置快照** | 每次评测 | `EvalReport` 携带 `retrieval_signature` + `generation_signature` + `provider_mode` + `prompt schema_version` + `user_dict_sha256`，五者齐全才可与历史对比 |
| **消融显著性** | 每次消融 | 每条结论必须带 `net_win_rate` 与 N；`|net_win_rate| < 0.10` 的结论不得进入摘要；中间地带标"弱证据" |
| **I5 第二级（σ_judge）** | 需要判断差值是否超过仪器精度时 | `run_suite(repeats=N)` 重复跑同配置，`EvalReport.repeat_stats` 给出每个指标的 `均值 ± 2σ`；**`repeats=1`（默认）时该字段为空，报告不得声称做过显著性检验** |

**不做"指标数值硬断言"**。检索质量的绝对值会随语料与模型漂移，把它写进 CI 只会得到一堆随机失败的红。回归测试锁的是**链路与配置**，不是分数。

**唯一的例外是显著性本身**：`net_win_rate` 的阈值（0.10 / 0.20）是一条**硬断言**，
因为它是"这个结论能不能被写进报告"的判据。如果它随语料漂移，报告就没有可信度可言。
这也正是 I5 必须在 P5 首跑前定案的原因——**判据不能和数据同时产生**。

## 6. 可复现性约定（评测可信的前提）

| 约定 | 理由 |
| --- | --- |
| Mock 全部确定性，禁止 `random` | 随机向量会让检索结果每次不同，评测不可复现 |
| jieba 用户词典固定并入库 | 词典变化会改变分词与 BM25 结果 |
| 评测单线程或固定并发数 | 并发会引入顺序不确定性，影响 P50/P95 外的指标可比性 |
| 每次评测输出带配置指纹 | 否则无法解释"同配置不同结果" |
| trace 落盘保留 | 出问题时能回放到具体某次调用 |

## 7. 运行方式

```bash
pytest tests/unit # L1 + L2，无 Key 可跑，秒级
pytest tests/integration # L3，无 Key 可跑（全 Mock）
python -m agentic_rag.cli probe # L4 探针
python -m agentic_rag.cli eval # 评测（属另一条线，见 04§9）
```

**CI 只跑 L1–L3**，因为它们无外部依赖、结果确定。评测（需要真实 API）手动触发，结果入库比对。

## 8. 覆盖率目标与不测的部分

| 部分 | 目标 |
| --- | --- |
| `retrieval/` `eval/metrics.py` `config.py` | ≥ 90%（纯逻辑，是本项目的技术含量所在） |
| `ingestion/` | ≥ 70%（解析依赖第三方库，以契约测试为主） |
| `providers/` | ≥ 70%（真实 API 部分不测，只测容错与 Mock） |
| `generation/` | ≥ 70% |
| `server/` | ≥ 50%（SSE 与前端以手工验证为主） |
| `agent/nodes` | 每个节点至少一个用例（走对分支 + 失败回落） |

**明确不测的**：第三方解析器本身的正确性（那是上游的事）、真实 API 的可用性、前端视觉呈现。把这些写清楚，避免为了凑覆盖率去写没有意义的断言。

## 9. 环境与安装（一条独立的测试线）

L1–L4 都假设"代码在工作区里、依赖已装好、输出能打出来"。这三条假设本身需要被测，否则
"本机绿"会被当成"可交付"。这条线补的正是"离开本机之后"才会暴露的问题：

| 检查 | 命令 | 锁住什么 |
| --- | --- | --- |
| 可构建 | `pip wheel . --no-deps` | `pyproject` 的 setuptools schema 合法（`where` 必须是数组）；wheel 里含 `prompts/*.md` |
| 可安装 | 在**仓库外的干净导出**里 `pip install -e ".[dev]"` | 依赖声明完整（`pydantic` / `pymupdf` 这类直连 import 的不能靠传递依赖） |
| 干净跑 | 同一目录里 `pytest ... --basetemp=.pytest_tmp/ci` | 不依赖工作区残留（`.pytest_tmp/` 的父目录由 conftest 补） |
| 原生控制台 | Windows 中文控制台直接 `python -m agentic_rag.cli probe` | 输出字形必须能在 cp936 下编码，不能崩在最后一行 |
| CI 工作流本身 | `tests/unit/test_contract_audit.py::test_ci_workflow_is_valid_yaml` | `ci.yml` 不是合法 YAML 时 GitHub 会直接拒绝运行，本机全绿也看不出来。同一文件还断言 Test 步骤显式传空 key，避免 CI 里混进 secret 后"无 Key 验证"失效 |

**规矩**：工作区通过不算通过。`.pytest_tmp/`、已装依赖、已建索引这三样会把缺失伪装成正常——
要证明"可交付"，只在仓库外的干净导出里装一遍、跑一遍、用一遍。
