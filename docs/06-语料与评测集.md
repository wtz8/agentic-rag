# 语料与评测集

> 定位：演示效果、探针集与评测集全部押在语料上。
> 本文档给出**来源渠道、覆盖矩阵、筛选标准、标注方法与构建顺序**。

---

## 1. 选语料的三条原则

1. **公开、可再分发、无版权风险**——项目要公开到 GitHub，语料必须能一并公开或至少能给出获取方式。
2. **要难**——语料太平庸，系统的设计（表格原子化、混合检索、OCR 通道）就无从体现。**必须主动包含会触发边界条件的文档**：扫描件、跨页表、合并单元格、多栏排版。
3. **中文为主**——自研 BM25 + jieba 分词的价值只有在中文语料上才讲得清楚。

## 2. 来源渠道

| 渠道 | 典型内容 | 格式 | 为什么选它 |
| --- | --- | --- | --- |
| **巨潮资讯网**（cninfo） | 上市公司年报、招股书 | PDF | 表格极度密集、含跨页表与复杂表头，是"表格被切碎"这个头号失效模式的最佳素材 |
| **国家统计局 / 地方统计局** | 统计年鉴、月度数据 | PDF / XLSX | 纯数值表格，适合验证表格数值问答与 `table_numeric` 路由 |
| **监管部门公开文件** | 规则、制度、指引 | PDF / DOCX | 条款编号（"第 3.2 条"）密集，正好验证 BM25 的精确匹配价值 |
| **政府部门公开政策文件** | 通知、办法、规划 | PDF / DOCX | 长文档、标题层级深，适合验证结构感知切分与上下文增强块头 |
| **开源项目文档** | README、docs 目录 | Markdown | 标题树深、含代码块，验证 `native` 解析器与深层级 `title_path` |
| **产品帮助中心 / 技术博客** | 使用说明、API 文档 | HTML | 含表格、代码块、深层导航，验证 HTML 解析路径 |
| **老扫描文档**（自制或公开档案） | 纸质件扫描 | PDF（无文本层） | **必须至少 2–3 份**，否则 OCR 通道与"扫描件探测"永远无法被触发和验证 |

**获取与留存方式**：只下载明确允许公开使用的文件；每篇在 `MANIFEST.md` 里记录来源 URL、获取日期、许可/公开性质。**不入库任何含个人隐私或未公开信息的文件**。

## 3. 格式与难点覆盖矩阵（目标 ~70 篇）

| 格式 | 目标数量 | 必须包含的特征 | 要触发的链路 |
| --- | --- | --- | --- |
| PDF · 文本版 | 20 | 多栏排版、3 级以上标题、图文混排 | `pymupdf4llm` 默认通道、上下文增强块头 |
| PDF · 表格密集 | 12 | 复杂表头、跨页表、合并单元格 | 表格原子化、Docling heavy 通道对比、探针集表格题 |
| PDF · 扫描件 | 3 | 无文本层 | 关卡 1 扫描件探测 → OCR 通道 → `ocr_min_chars` 判据 |
| DOCX | 12 | 标题样式、嵌套列表、内嵌表格 | `markitdown` 通道、标题层级连续性校验 |
| XLSX | 8 | 多 sheet、合并单元格、数值与单位 | `markitdown` 通道、数值问答 |
| PPTX | 6 | 图文混排、要点列表 | `markitdown` 通道、`image_caption` 块 |
| HTML | 6 | 表格、代码块、深层导航 | HTML 解析路径、去标签 raw 基线 |
| Markdown | 5 | 深标题树（≥4 级） | `native` 解析器、深层级 `title_path` |
| **合计** | **约 72** | | |

**规模校验**：按平均每篇 60–120 个 chunk 估，总 chunk 数约 **5–8k**，落在 02 §1 声明的 `10³–10⁴` 约束内，也远低于 BM25 全量重建的 5 万 chunk 上限。

**必须至少 1 篇"会被拒绝"的文档**（比如极端损坏的加密 PDF），用来验证"宁可拒绝入库"这条原则真的会执行——**一个从不触发的拒绝逻辑，等于没有**。

## 4. `data/raw/MANIFEST.md`

语料清单是项目资产的一部分，每篇一行：

```markdown
| 文件 | 格式 | 来源 | 许可/公开性质 | 页数/大小 | 预期难点 | 预期 verdict |
| --- | --- | --- | --- | --- | --- | --- |
| xxx_2024年报.pdf | PDF | 巨潮资讯网 | 上市公司公开披露 | 180p / 4.2MB | 跨页表、复杂表头 | ok |
```

`预期 verdict` 这一列很重要：它把质量关卡变成**可验证的预期**。如果一篇标注"预期 ok"的文档被拒了，说明阈值定得太严；如果标注"预期 rejected"的加密 PDF 竟然入库了，说明关卡根本没生效。

## 5. 评测集构建

### 5.1 规模与分布

目标 **60–100 条**，按 `kind` 分布：

| kind | 占比 | 说明 |
| --- | --- | --- |
| `single_hop` | 40% | 答案在单一块内 |
| `multi_hop` | 25% | 需要跨块/跨文档组合 |
| `table` | 25% | 答案在表格内，含数值计算 |
| `unanswerable` | 10% | **语料中确实没有答案** |

`unanswerable` 必须包含——它是区分"真 RAG"和"会编的 RAG"的关键测试。这类问题的期望行为是走 `degrade_answer`，**答出来了反而是失败**。

### 5.2 标注格式（关键设计：不绑死 chunk_id）

**标注用文档级锚点，不在标注里写死 `chunk_id`。** `chunk_id` 依赖切分策略，写死它等于把标注与某一版切分绑定——切分策略一变，整份标注就失效。

标注格式为「来源文件 + title_path + 原文片段」，运行时把锚点解析成 `chunk_id`：

```json
{
  "question": "2024 年华东区带宽采购单价是多少？",
  "intent": "table_numeric",
  "kind": "table",
  "golden_anchors": [
    {
      "source": "xx网络_2024年报.pdf",
      "title_path": ["第三章 采购情况", "3.2 分区域明细"],
      "quote": "华东区 ... 单价 ...",
      "block_type": "table"
    }
  ],
  "golden_answer": "…",
  "notes": "答案在该表第 4 行"
}
```

解析规则（三级回退）：

1. 先按 `source + title_path` 精确匹配所有 chunk
2. 若有多个，用 `quote` 做字符级包含校验，取包含该片段的 chunk
3. 若仍为空，记 `anchor_unresolved` 并**在评测报告中显式列出**——**绝不静默跳过**，否则 Recall 会被虚高分母稀释

这样切分策略怎么换，标注都还能用；而且 `title_path + quote` 本身是人类可读的，评审者能一眼看出这条标注对不对。

### 5.3 探针集

从评测集中挑 **约 20 条**（另存 `eval/probe_set.jsonl`），构成见 03§10：正文 8 条 + **表格数值 6 条** + 专有名词/编号 4 条 + 跨页/多跳 2 条。

探针与评测集的区别：探针只判"期望来源是否进 Top-K"，是**链路连通性回归**；评测集判检索质量与生成质量。前者每次重建索引后都要跑，后者改配置后跑。

## 6. 关键落地方案

### 6.1 文档选择标准

**不预先写死文件清单**：公开文件会变（年报逐年更新、网页改版下线），写死的清单半年后可能全部失效。锁定的是「渠道配额 + 四条硬标准 + 逐篇登记」，任何人按同一套标准都能复现出同等难度的语料。

**渠道入口与配额**（与 §3 矩阵一致）：

| 顺序 | 渠道 | 入口 | 配额 | 筛选要点 |
| --- | --- | --- | --- | --- |
| 1 | 扫描件（自制） | 见 §6.3 | 3 | **最先做**——最容易卡住，卡住要重来 |
| 2 | 巨潮资讯网 | `cninfo.com.cn` 信息披露 → 定期报告 → 年度报告 | 12 | 选制造业/科技类，表格密集；100–250 页 |
| 3 | 国家统计局 | `stats.gov.cn` 数据 → 统计年鉴 / 月度数据 | 8 | 优先 XLSX 而非 PDF（多 sheet、合并单元格） |
| 4 | 监管部门规则 | 证监会、金融监管总局官网 → 规则/指引 | 8 | 条款编号密集（"第 X.X 条"），验证 BM25 精确匹配 |
| 5 | 政府政策文件 | `gov.cn` 及部委网站 → 通知/办法/规划 | 12 | 长文档、标题层级 ≥3 级 |
| 6 | 开源项目文档 | 知名中文项目 README / docs（MIT、Apache-2.0） | 5 | 许可明确可再分发，标题树 ≥4 级 |
| 7 | 技术博客 / 帮助中心 | 标注 CC 或"可自由转载"的站点 | 6 | HTML 原格式，含表格与代码块 |
| 8 | DOCX / PPTX | 由 4、5 渠道的 DOCX 版本 + 自制 PPTX 补齐 | 18 | DOCX 12 + PPTX 6；需含标题样式、嵌套列表、内嵌表格 |

**配额与 §3 格式矩阵的对齐校验**：

| 格式（§3） | 数量 | 来自哪个渠道 |
| --- | --- | --- |
| PDF · 扫描件 | 3 | 自制（顺序 1） |
| PDF · 表格密集 | 12 | 巨潮资讯网（顺序 2） |
| PDF · 文本版 | 20 | 监管规则 8 + 政策文件 12（顺序 4、5） |
| XLSX | 8 | 国家统计局（顺序 3） |
| DOCX + PPTX | 18 | 顺序 8（DOCX 12 / PPTX 6） |
| Markdown | 5 | 开源项目文档（顺序 6） |
| HTML | 6 | 技术博客 / 帮助中心（顺序 7） |
| **合计** | **72** | 与 §3 一致 |

两处数字必须能对上——**配额表按渠道切，矩阵按格式切，是同一批语料的两种切法**，对不上说明其中一处算错了。

**每篇的硬性筛选标准**（四选四，缺一不收）：

1. **篇幅**：**按文档类型分档**，不再一刀切——
   | 类型 | 篇幅 |
   | --- | --- |
   | 长文档（上市公司年报、教程手册） | PDF 20–250 页 |
   | 政策通知 / 办法类 | PDF 3–60 页 |
   | DOCX / PPTX | 5–80 页 |

   原标准统一写"PDF 20–250 页"，而 A 股年报普遍 250–320 页、政策通知普遍 3–15 页，
   一刀切会把这两类**同时**误伤：年报大量超限，通知又永远达不到下限。
   分档后的判据仍然明确，只是承认"不同文档的自然长度本就不同"。

2. **结构**：必须含三级以上标题，且至少 1 个三行以上表格（对应覆盖矩阵要触发的链路）
3. **语言**：中文为主体
4. **合规**：**不含个人隐私**——出现身份证号、手机号、个人姓名+住址的文件一律排除

> 标准 2 与 4 在构建脚本里自动跑（`fetch_corpus.check_pdf` / `make_office.audit_text`）。
> 实测这两条**真的会淘汰文件**：巨潮渠道 60 篇初筛只有 12 篇通过，淘汰的 48 篇里
> 36 篇是篇幅超限、12 篇检出手机号。一个从不淘汰的标准等于没有。

**登记**：每篇下载后立即写入 `data/raw/MANIFEST.md`（格式见 §4）。**先登记后使用**，避免"下了一堆最后不知道哪篇是哪篇"。

### 6.2 语料不入库：下载脚本 + checksum 清单

两条理由，任何一条单独都足够：

1. **体积**：72 篇，年报单篇 4–20MB，总量预计 300MB–1GB。GitHub 单文件上限 100MB，且这么大的仓库没人愿意 clone。
2. **许可**：文件"公开可下载"不等于"我们有权再分发"。上市公司年报、政府文件的再分发边界并不总是清晰——把语料塞进公开仓库，等于替这些文件做了一个许可判断，而这个判断不该由本项目来做。

**处置**：

- `scripts/fetch_corpus.py`：按 MANIFEST 里的 URL 批量下载并校验 sha256
- `data/raw/MANIFEST.md`：**进仓库**，作为语料的"指纹清单"——来源 URL、获取日期、公开性质、sha256、页数、预期难点、预期 verdict
- 评审者跑一条命令即可复现语料；即使某天源站下线，MANIFEST 仍能证明"本项目当时用的就是这批文件"

这样既保持了可复现，又不承担再分发风险。**MANIFEST 是资产，语料文件本身不是。**

### 6.3 扫描件：自制 3 份，带难度梯度

自制而非找公开档案，是因为自制的价值恰恰在于**可控**：能确定它无文本层，还能做出难度梯度。

| 份 | 制作方式（程序合成） | 难度特征 | 要验证的链路 |
| --- | --- | --- | --- |
| 1 | 文本渲染为 300dpi 位图，正放 | 干净 | OCR 基础通道 |
| 2 | 同上 + 倾斜 1.5–2.5° + 装订侧渐变阴影 | 中等 | 版面矫正、`ocr_min_chars` 判据 |
| 3 | 同上 + 动态范围压至 42% + 高斯噪点 + 轻微失焦 | 困难 | OCR 质量下限、`on_reject` 拒答分支 |

**扫描件用程序合成，不做物理扫描。** 难度参数写进脚本、可复现，任何人跑一次得到同一批文件；代价是缺少真实纸张纹理与扫描仪 CCD 噪声，这一点在 MANIFEST 的「来源」列如实标注为「自制（程序合成，非物理扫描）」。
但自制的价值恰恰在于**可控**，而程序合成比物理扫描更可控：难度参数写进脚本、
可复现、任何人跑一次得到同一批文件。代价是缺少真实纸张纹理与扫描仪 CCD 噪声——
这一点在 MANIFEST 的「来源」列里如实标注为"自制（程序合成，非物理扫描）"，不假装是扫出来的。

内容源用开源许可文档（CC BY-NC-SA 4.0），不用受版权保护的材料。

**验收标准（必须实测，不能凭目测判断）**：用 `pypdf` 提取文本，确认每页字符数 < `QualityConfig.scanned_chars_per_page`（默认 50），即关卡 1 确实会把它判为扫描件。若某份提取出了文本，说明制作失败（比如存成了"图片+隐藏文字层"的 PDF），必须重做。

### 6.4 `unanswerable`：构造法，不用核对法

人工核对全语料**成本高且不可靠**：证明"某个答案在全语料中不存在"需要人把 72 篇文档通读一遍，而人一定会漏。改用构造法——不问"有没有"，而是**从一开始就构造语料里必然没有的问题**。

三类构造规则，各占三分之一：

| 类型 | 做法 | 例子（假设语料为 2023–2025 年金融与政策文件） |
| --- | --- | --- |
| 越界实体 | 问语料中不存在的实体 | "华南三区的带宽采购单价"（语料只有华东/华北） |
| 越界时间 | 问覆盖年份之外的数据 | "2019 年的研发投入"（语料最早 2023 年） |
| 越界主题 | 问完全无关的领域 | "XR-2400 设备的固件升级步骤" |

**双重校验**（两条都过才算合格）：

1. **机器校验**：拿该问题跑一遍完整检索（向量 + BM25 + rerank），若 **rerank 的最高 `relevance_score` 超过 `RetrievalConfig.unanswerable_rerank_floor`**（默认 0.35），说明语料里其实有相关内容——**丢弃该条重造**，而不是降低阈值
2. **人工校验**：构建者必须能明确写出"为什么它没有"。若自己都说不清为什么没有，说明这条设计得不够干净

**判定纪律**：`unanswerable` 问题被系统"答出来了"，记为**失败**而非成功。一个从不失败的 unanswerable 集合等于没有——这与 §3 里"必须至少 1 篇会被拒绝的文档"是同一个道理。

### 6.5 本版语料构成

**配额 72 篇已全部达成**，且与 §3 格式矩阵逐项对齐（12 + 3 + 20 + 8 + 12 + 6 + 5 + 6 = 72）。

但**达成方式与设计预期不同**，这一点必须写清楚：

| 类别 | 篇数 | 占比 | 构成 |
| --- | --- | --- | --- |
| 真实下载 | 23 | 32% | 开源文档 5（GitHub）+ 上市公司年报 12（巨潮）+ 技术文档页 6（各官网） |
| 程序生成 | 49 | 68% | 扫描件 3 + PDF 文本版 20 + DOCX 12 + PPTX 6 + XLSX 8 |

生成类的**内容**全部取自真实抓取的开源中文技术文档（CC BY-NC-SA 4.0 / Apache-2.0），
程序生成的是**格式**而不是内容；每篇在 MANIFEST 的「来源」列都写明"由开源文档生成"，
不冒充真实下载。评审者可以据此判断哪些结论来自真实世界文档、哪些来自合成格式。

#### 为什么没有全部走真实下载

四个渠道实测受阻，逐条记录——失败原因比成功更有复用价值：

| 渠道 | 现象 | 处置 |
| --- | --- | --- |
| GitHub | Contents API 未认证限额 60 次/小时且**按 IP 计**，第一条请求即 403 | 改走 `codeload` 的 zip 快照：单次 HTTP，重试逻辑可用 |
| 同上 | `git clone` 协议层频繁 `curl 56 schannel: server closed abruptly` | 同上，彻底不用 git 协议 |
| gov.cn | 政策栏目是 JS 渲染，两层 BFS 只挖到 7 个正文页（需 20 篇） | 放弃，改用已抓开源文档生成同格式 |
| 证监会 | "规则"标题点进去是新闻发布稿（693 字），不是规则全文 | 同上 |
| 国家统计局 | 年鉴页面无 Excel 直链（应为 JS 动态加载） | 表格改用开源文档中的真实表格生成 |
| 无头打印 | Chrome / Edge `--headless=new --print-to-pdf` exit=0 但**不产出文件** | 放弃该路径，改用 reportlab 直接生成带文本层的 PDF |

**这个取舍是刻意的**：跟反爬、JS 渲染、无头浏览器较劲，是在把时间花在
**与本项目无关**的问题上——本项目要验证的是解析与检索，不是爬虫对抗。
继续投入的边际收益接近零，于是把预算转向"保证格式覆盖完整"。

代价也要认：**生成文档比真实文档"干净"**。真实年报里有错版、缺页、水印、异常编码，
这些脏东西恰恰是解析器最容易崩的地方。目前的 23 篇真实文档（尤其 12 篇年报）
承担了这部分难度，若后续有余力，应优先提高真实下载的比例而不是增加篇数。

#### 两条配套调整

1. §6.1 篇幅标准**按类型分档**——年报与政策通知的自然长度本就不同，一刀切会同时误伤两端。
2. §6.3 扫描件采用**程序合成**，并在 MANIFEST 如实标注，不假装是物理扫描出来的。

### 6.6 jieba 用户词典

01 §6 把"注入领域术语（产品名、部门名）"作为自研 BM25 的价值之一，03§7.2 把 `user_dict_path` 写进配置，
07§6 要求"用户词典固定并入库"——**但没有任何一处说过这个词典怎么产生，仓库里也没有它。**
自研 BM25 曾把"中文分词可控"作为主要说服力之一，而可控的前提恰恰是这份词典。
（该理由后经实测移出自研立论，见本节末尾与 01 §0。）

**定案：从语料里抽，脚本生成，产物入库。**

| 项 | 内容 |
| --- | --- |
| 脚本 | `scripts/build_user_dict.py`（与语料构建脚本同批，用 `requirements-corpus.txt` 环境） |
| 输入 | `data/raw/` 全部已登记文档的正文（按 MANIFEST 白名单） |
| 方法 | jieba `analyse.extract_tags` 跑 TF-IDF，取 Top-300；再与停用词表、通用词表做差集 |
| 产物 | `data/user_dict.txt`，**进仓库**（满足 07§6 的"固定并入库"） |
| 复现 | 词典内容随语料变化，因此 `MANIFEST.md` 的 sha256 清单变了就必须重跑；脚本输出写进 MANIFEST 附注 |

三条约束：

1. **必须人工过一遍再入库**。TF-IDF 抽出来的会有"参见""合计""本页"这类噪声词，把它们塞进用户词典反而会扭曲分词。这一步约 15 分钟，不能省。
2. **词典文件缺失不得阻断摄取**。降级为 jieba 默认词典 + `BuildReport.warnings: user_dict_missing`（03§7.2）。它是增强项不是前提。
3. **词典变了要进评测存证**。它直接改变 BM25 的召回，因此 `EvalReport` 的存证字段里要带上它的 sha256——否则"同配置不同结果"又多一个解释不了的变量。

**生成结果**

```
白名单语料 71 篇 → 成功抽取 69 篇 / 正文 9,094,515 字符
自动抽取候选 300 词 → 人工过筛保留 87 词
产物 data/user_dict.txt，sha256 = 7233123c8335a7ee
```

抽取失败的 2 篇是扫描件 PDF——**它们没有文本层，抽不到正文是预期行为**，
不影响词典（扫描件的价值在验证 OCR 通道，不在提供术语）。

过筛删掉了约 71% 的候选，绝大部分是代码与 LaTeX 噪声（`boldsymbol` / `frac` /
`import` / `pip` / `torch` / `True` / `None` …）——这些来自代码块与公式，不是术语。
保留下来的 87 词集中在三类：模型与产品名、机器学习术语、库与框架名。

> 这条数据本身也说明了约束 1 为什么不能省：**自动抽取的噪声率高达七成**。
> 若不过筛直接入库，词典就不是"领域术语表"而是"代码标识符表"，
> 而它带来的分词扭曲会让 BM25 的召回质量**低于不用词典**。

**但人工过筛挡不住方向性错误——已实测**

过筛删掉的是噪声词，删不掉"短词切碎长词"。保留下来的 87 词平均长 5.6 字，
正是长复合词的子串，注入后优先级反而更高：

| 口径 | 结果 |
| --- | --- |
| 查询侧 | 78 条评测问题中只改变 **2** 条分词结果，**两条都变差** |
| 索引侧 | 275 条含词典词的单元中，**44 条被切得更碎、仅 1 条切得更整** |

典型破坏：`Qwen2MoeSparseMoeBlock → Qwen2 / Moe / SparseMoeBlock`、
`AutoModelForMultimodalLM → AutoModel / ForMultimodalLM`、
`HuggingFaceEmbeddings → HuggingFace / Embeddings`。

**结论：词典不进自研立论**（01 §0 已同步移出理由项）。方法论是对的（词典入库、带 sha256、
构建流程可复跑，所以这个 44:1 才测得出来），但当前这一版词典是负增益。
修法按成本递增：① 词典改收长词不收短词；② 注入前加子串校验——候选词若是词典中其他词的子串，
或会切碎语料里已有的长 token，则剔除；③ 不注入词典，改在 BM25 打分前做"长词优先"的术语保护。

**改动纪律**：词典属于索引期参数，一改 `retrieval_signature` 就变，与已交付的 A0–A2 实测基线不可比。
因此修词典必须与 A0–A2 全量重跑一起做，不可单独改。

## 7. 构建顺序：数据分批建，评测能力必须早

**推迟的是标注数据的完整规模（60–100 条），不是评测本身。**

### 7.1 三件推到最后就补不回来的事

| 项 | 为什么不能晚 | 晚了会怎样 |
| --- | --- | --- |
| **trace 埋点**（召回明细、各路原始分数、rerank 前后排名） | 它写在生产代码里，不是评测代码 | P8 想算 MRR 时发现历史跑次根本没记排名，只能**全量重跑并重新花钱调 API** |
| **消融首次运行** | 消融 A0–A4 是本项目最核心的说服点，结论必须有机会改变设计 | P8 首次跑出"rerank 收益不显著"时代码已冻结，只会把它写进报告当结论——**先射箭后画靶** |
| **答案粒度定义** | 写 `golden_answer` 会暴露"答案该写一个数还是一句话"，这反过来约束 05 的生成提示词契约 | 推迟定义，提示词写完后再改等于重跑全部实验 |

### 7.2 三阶段方案

| 阶段 | 评测资产 | 规模 | 目的 |
| --- | --- | --- | --- |
| P2 | **mini 评测集** | 20–25 条 | 给开发期提供粗糙信号，让架构决策有依据而不是靠信仰 |
| P3 | 检索指标（recall@K / MRR / hit-rate）+ trace 埋点 + **`sufficiency_vector_floor` 标定** | mini 集（20–25 条） | 前两项见 04§9，纯函数、不依赖 LLM、毫秒级；**标定用"人工判定相关"的候选对的余弦分布定阈值，不标定则检索侧反思能力整体失效** |
| P5 | 生成侧 judge + 消融 runner；**用 mini 集首跑 A0–A4** | 沿用 mini 集 | 此时架构仍可改，结论能真的改变设计 |
| P8 | 扩充至 60–100 条 + 探针集 20 条 + 人工复核 → 复跑消融 → 出报告 | 完整 | 产出可对外引用的数字 |

**mini 集不是临时数据，它是完整集的第一批。** P8 做的是扩充与复核，不是从零开始。这样即便 mini 集里有一部分标注因切分调整而失效，重标 5 条的成本，也远低于"从零标 100 条"或"架构返工"两者中的任何一个。

**mini 集的构成**（缺任何一类都测不出区分度）：

| 类型 | 条数 | 验证什么 |
| --- | --- | --- |
| 表格数值 | 6 | 表格原子化、`table_numeric` 路由 |
| 条款 / 编号精确匹配 | 4 | BM25 的不可替代性 |
| 跨段多跳 | 4 | 查询改写与反思循环 |
| 简单单跳 | 6 | simple 快路径真的省了钱 |
| `unanswerable` | 5 | 拒答分支，构造法见 §6.4 |
| **合计** | **25** | |

**P8 扩充后完成）**：78 条 —— `simple` 51 / `table_numeric` 17 / `multi_hop` 10；按 kind 分 `single_hop` 43 / `table` 17 / `multi_hop` 10 / `unanswerable` 8。新增 53 条的来源覆盖从原来的少数几个扩展到 **12 份 cninfo 年报 + 南瓜书 + happy-llm + self-llm + langchain-chatchat**，并逐条做了锚点机器校验与答案人工复核（见下）。

**标注流程（新增两道机械关卡，都不是走过场）**：

1. **锚点必须能被 `_match_anchor` 解析**。凭语料印象写的 quote 常因 PDF 抽取的空格差异、块头改写而根本不在块里。第一轮校验 53 条里就有 3 条解析失败、11 条命中过宽（>5 个父块家族），全部修掉后才入库。
   - 顺带在这一步抓出 `_match_anchor` 本身的实现缺陷。
2. **unanswerable 必须真的无答案**。用"关键词在语料中出现 0 次"做构造法校验：原拟的两条（`GPU 型号与采购单价`、`PostgreSQL vacuum`）分别命中 6 次与 44 次，不算干净，已替换为出现 0 次的构造（`2026 年第一季度`、`Ingress`、`Redis 集群/槽位`）。

命中宽度分布：47/53 落在 ≤5 个父块家族内；剩下的 6–8 个家族集中在 cninfo 年报——**关键数字在同一份年报里本就重复出现**（利润分配预案、主要会计数据、财务报表三处），这是语料性质而非标注失误，已在评测报告里区分对待。

### 7.3 与 P2 最小临时探针的关系

两者并存，不互相替代：03§10 规定 `run_probe_after_build=True`，即每次建索引后自动跑探针；早期没有正式探针集时该环节是空的，因此 P2 仍需 **3–5 条手写临时探针**（每条只标"来源文件名 + 一句话答案"）。

- **临时探针**：只判"期望来源是否进 Top-K"，每次建索引自动跑——保的是**没坏**
- **mini 评测集**：判检索质量与生成质量，改配置后跑——保的是**变好了**

### 7.4 仍然成立的一条

`07-测试设计.md` 里的 pytest 单元测试与集成测试**不推迟**，随 P0–P7 各阶段同步编写。推迟的只有标注数据的**完整规模**。这两者名字相近但性质完全不同：前者是给代码打分，后者是给模型打分。
